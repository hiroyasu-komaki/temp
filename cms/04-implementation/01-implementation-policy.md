## 2. 作る順番

前の手順ができてから次へ進む。各手順の「できた」の確かめ方を満たしたら次へ。

| 手順 | 作るもの | 正とする設計 | できたの確かめ方 |
|---|---|---|---|
| 1 | SharePoint：リスト・ライブラリ・列・索引・権限、マスタの初期データ | データモデル | 全リストの列名・索引が設計どおり。一般利用者が案件リストに書き込めない。Drafts は本人の項目しか見えない |
| 2 | 共通の子フロー（C01〜C06）と、画面から呼ぶフロー（F01〜F23） | フロー設計、状態遷移 §4・§7 | 状態・実行者が合わない呼び出しに `E_STATE`／`E_FORBIDDEN` を返す。操作記録が残る |
| 3 | 申請用アプリ（申請前）：マイ申請〜申請完了 | 申請画面の紙芝居、業務ドメイン構造 | 下書き保存・自動生成・申請が通る。日英の切り替えが効く |
| 4 | 審議ワークベンチ：W1〜W3、D1〜D14 | 画面設計 §1〜§5、ワークベンチの紙芝居 | 紙芝居の「通しで試す例」が本番でも通る |
| 5 | 申請用アプリ（申請後）：A1・A2、起案者の操作 | 画面設計 §6 | 起案担当者だけにボタンが出る。審議途中の情報が出ない |
| 6 | 定期フロー（S01〜S03）と通知 | フロー設計、状態遷移 §5 | 期限の前日・当日のリマインド、超過の通知、議論要請の受付終了、一時保管の削除が動く |

## 3. 作り方の決まり

| 項目 | 決まり |
|---|---|
| 置き場所 | アプリ2本とフローは1つのソリューションに入れる。接続は接続参照（サービスアカウント）、サイトURL・リスト名は環境変数にする |
| 書き込み | 画面から SharePoint へ直接書かない。必ずフローを呼ぶ（例外は Drafts だけ。ADR-0005） |
| 名前 | リスト・列・フローの名前はデータモデルとフロー設計の英語名のまま。画面の文言は UiStrings から読み、アプリに直書きしない（日英の画面） |
| 検索 | 索引付きの列で、SharePoint 側で絞り込める条件だけを使う（技術スタック 原則5） |
| 部品 | 状態の表示（色・ラベル）とヘッダは、両アプリ共通のコンポーネントにする |
| 保管 | ソリューションを書き出したファイルと、SharePoint の構成を書き出したテンプレートを Git に置く。変更のたびに書き出す |

## 4. 稼働前の確認（受入）

05-test は書かず、ここで代える（決定ログ #24）。本番サイトで試験データを使い、次を通す。

| # | 確かめること | 見る人 |
|---|---|---|
| 1 | 申請 → 論点整理書の回付 → 疑義・修正版 → 確認完了＋確認表の保留ゼロ → 審議待ち | 事務局・審査担当者・起案者役 |
| 2 | 回答依頼 → 審議結果 → 回答書（案）→ 修正依頼 → 内容確認 → 確定 → 受付期限 → 結果確定 → PPM への引き渡し | 事務局・委員長役 |
| 3 | 議論要請 → 招集情報 → 議事録と結果の確定 | 事務局・委員役 |
| 4 | 取り下げ（受付済み・審議中の2通り）と、取り下げ後に操作できないこと | 起案者役 |
| 5 | 権限：一般利用者が書き込めない、ほかの人の下書きが見えない、「案件概要書のみ」の資料が残らない | IT部門 |
| 6 | 非機能要件の目標（画面3秒・書き込み10秒・自動生成90秒）を、案件を増やしたデータで確かめる | IT部門 |

終わったら試験データを消し、稼働日を事務局と決めて利用者へ案内する（案内の内容は 08-operations）。
