## 1. 体制

| 役割 | 担当 | やること |
|---|---|---|
| CMS 管理者 | IT部門（正・副の2名） | マスタの更新、権限の付け外し、障害の一次対応、変更の反映、年1回の削除の承認 |
| 業務の窓口 | 事務局 | 利用者からの問い合わせの受付、業務ルール（期限・委員長など）の変更依頼 |
| サービスアカウントの所有者 | IT部門 | パスワード・ライセンスの管理。退職・異動で止まらないよう個人に紐づけない |

## 2. 稼働の手順（最初の1回）

1. 受入の確認（04-implementation §4）が終わり、試験データを消したことを確かめる。
2. SharePoint グループ（CMS 利用者、事務局、審査担当者、投資委員会、PPM、CMS 管理者）に人を入れる。
3. マスタ（部門、ケイパビリティと審査担当者、設定値の委員長・代理、今年度の休日）を最新にする。
4. 申請用アプリを全員に、審議ワークベンチを関係者に共有し、利用者へ案内する（アプリのリンク、申請の流れ、「添付資料は全員に公開される」「機密案件は CMS で扱わない」の2点）。
5. 稼働日から1週間は、定期フロー（S01・S02）の実行結果を毎日見る。

## 3. 定常の作業

| 頻度 | 作業 | 担当 |
|---|---|---|
| 毎日（自動） | 期限のリマインド・超過の通知（S01）、一時保管の削除（S02） | − |
| 週1回 | フローの実行履歴に失敗がないか見る。失敗があれば §5 | CMS 管理者 |
| 年1回（年度末） | 翌年度の休日を Holidays に入れる | CMS 管理者 |
| 年1回（自動＋承認） | 結果確定・取り下げから3年を過ぎた案件の一覧（S03）を確かめ、承認して削除する | CMS 管理者 |
| 随時 | 人事異動に合わせて、グループ・審査担当者・委員長・代理を更新する | CMS 管理者（事務局の依頼で） |

マスタは SharePoint のリスト画面で直接編集する（画面設計 §1）。設定値（期限の日数など）を変えたら、変更日と理由を決定ログに残す。

## 4. 変更の反映

本番だけで運用するため（決定ログ #23）、次の順に行う。

1. 変更前にソリューションを書き出して Git に置く（戻せる状態を作る）。フローは変更前のコピーを残す。
2. 業務時間外に反映する。
3. 反映後、変更した画面・フローを1件通して確かめる。
4. 不具合があれば、アプリはバージョン履歴で、フローはコピーで元に戻す。
5. 設計に関わる変更は、該当する設計書（と必要なら ADR）を直す。

## 5. 障害のとき

| 事象 | まず見るところ | 対応 |
|---|---|---|
| 登録が失敗する（`E_SYSTEM`） | 該当フローの実行履歴 | 原因を直して利用者に再操作を依頼する。途中まで書けていないかを確かめる |
| 通知が届かない | 通知フローの実行履歴、サービスアカウントの状態 | 未送の通知を手で送る |
| 全体が使えない | Microsoft 365 のサービス正常性 | 事務局経由で利用者へ周知。止まっていた日数だけ期限を延ばす（非機能要件：RTO 2営業日） |
| 誤って消した・上書きした | SharePoint のごみ箱・バージョン履歴 | 1日前の状態まで戻す（RPO 1日） |
| サービスアカウントが止まった | ライセンス・パスワード・接続の状態 | 復旧後、接続参照を付け直す。書き込みと通知がすべて止まるため最優先で対応する |

## 6. 引き継ぎ資料

担当が替わるときは、本ドキュメント一式、Git（ソリューションと SharePoint のテンプレート）、サービスアカウントの管理情報の所在、決定ログの保留課題を渡す。
