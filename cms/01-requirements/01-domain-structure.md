# 業務ドメイン構造 ─ 申請（案件概要書）の構造

- **出典**: IT投資ポートフォリオ管理の制度資料にある「IT投資案件概要書（様式）」を本件用に写して改変したもの。事実項目は 05章 §A と `copilot/guide_issue-brief.md` §00。申請の手順は [ADR-0004](../02-architecture/05-adr/0004-intake-power-apps-and-ai-generated-proposal.md)
- **最終更新**: 2026-09-23

案件概要書の項目は**本書を正とする**。元の様式が改訂されても自動では追従しない。取り込む場合は本書を更新し、[一次資料](../00-overview/03-source-materials.md) §3 に記録する。

## 1. 対象ドメインの全体像

申請は **申請メタデータ・案件概要書（8セクション）・手元資料・通知先・内容確認** からなる。

申請で起案者が行うのは、事実の提出までである。論点整理は申請を受け取った後に事務局が Copilot で行い（Step1）、その結果を起案者に共有する。申請画面では論点整理を行わない。

| # | 名称 | 目的（何のための情報か） | 入力 | 必須 |
|---|---|---|---|:--:|
| M | 申請メタデータ | 案件を特定し、審議の区分と担当を決める | 起案者 | ✅ |
| 1 | 目的・背景 | 何のための投資かを委員会が把握する | AI→起案者 | ✅ |
| 2 | 期待効果 | 起案部門が見込む効果 | AI→起案者 | ✅ |
| 3 | スコープ | 何をやり、何をやらないか | AI→起案者 | ✅ |
| 4 | 事実項目 | 起案部門の外・将来に及ぶかを判断するための事実。申請後に事務局が行う論点整理で使う | AI→起案者 | ✅ |
| 5 | 主要ステークホルダー | 意思決定者と関与者 | AI→起案者 | ✅ |
| 6 | 概算予算 | 初期・運用の費用 | AI→起案者 | ✅ |
| 7 | 想定スケジュール | 開始・完了とマイルストーン | AI→起案者 | ✅ |
| 8 | 主要リスク | 起案部門が認識しているリスク・制約 | AI→起案者 | |
| A | 手元資料 | 自動生成の入力。原本として保管し、申請後の論点整理でも参照する | 起案者 | ✅ |
| S | 添付ファイルの提出 | 手元資料を案件の資料として公開するか、案件概要書だけを出すかを起案者が決める | 起案者 | ✅ |
| N | 通知先 | 申請の状況・ステータスの変化を共有する関係者のメーリングリスト。承認や確認のためのものではない | 起案者 | |
| C | 内容確認 | 起案者が内容を確認したことの記録。申請の条件 | 起案者 | ✅ |

「AI→起案者」＝自動生成で値が入り、起案者が確認・修正する。

**元の様式から変えた点**

| 元の様式 | 本書 | 理由 |
|---|---|---|
| 基本情報（案件ID〜期間） | 案件ID・提案日は自動。開始・完了時期は §7 へ | 起案者が最初に入れるのは最低限にする |
| （無し） | §4 事実項目を追加 | 申請後の論点整理で使う事実（05章） |
| ROI・投資回収期間・TCO | 削除（入力も計算もしない） | 意思決定に影響しないため |
| 案件タイプの自己申告 | 削除 | 不要 |
| 添付資料のチェックリスト | 手元資料の添付（§A）に置き換え | 添付そのものが入力になる |
| 提出欄（提案責任者・部門長の署名） | 通知先（§N、複数登録）と内容確認チェック（§C） | 申請内容の承認は取らない。関係者への状況共有に使う |

## 2. 分類・類型の定義

### 審議区分（申請メタデータ）

| コード | ラベル | 説明 |
|---|---|---|
| EXEC | 執行開始 | 予算に計上済みの案件の執行開始の判断 |
| NEW | 年度途中の新規 | 予算編成後に発生した新規案件 |

年次の予算申請は CMS で受け付けない（決定ログ #21）。

### 新規／更新の別（§4）

| コード | ラベル |
|---|---|
| NEW | 新規構築 |
| RENEW | 既存システムの更新 |
| MOD | 既存システムの改修・機能追加 |

## 3. 分岐ルール

| 条件 | 表示・入力の変化 |
|---|---|
| §4 新規／更新の別 = 新規構築 | 「現行製品の保守期限」は「該当なし」を既定にする |

**画面の順序**: M → A（添付）→ 自動生成 → 1〜8（確認・修正）→ N → S → C → 申請。自動生成の前に 1〜8 を手入力で埋めてもよい。

**再生成**: 2回目以降に自動生成ボタンを押すと、確認ダイアログを出したうえで **1〜8 の全項目を上書きする**（起案者の入力・修正は失われる）。

**PDF 出力**: 確認・修正画面と確認・申請画面から、その時点の案件概要書（申請メタデータ・添付資料名・§1〜8）を A4 の PDF に出力できる。申請前は「下書き（未申請）」と明示し、未入力の項目は「（記載なし）」と出す。出所や AI 生成の表示は含めない。

**下書き保存**: 申請前の内容はいつでも下書きとして保存でき、後から再開できる。下書きは起案担当者だけが見られる。下書きの段階では必須チェックを行わない。

### N: 通知先

| 項目キー | ラベル | 型 | 必須 | AI | 選択肢・制約 | 備考 |
|---|---|---|:--:|:--:|---|---|
| notifyRecipients | 通知先 | person（複数） | | — | 社内ユーザー・メールが有効な社内グループ（配布リスト等）。件数の上限なし。社外のアドレスは登録できない（決定ログ #21） | 起案担当者と提案責任者は自動で含める（削除不可） |

- 通知先には、申請の受付と、ステータスの変化（Step の移行、回答書の確定、会議の招集、承認結果）を通知する。
- 通知先は申請後も起案担当者が追加・削除できる。
- 通知は状況の共有に限る。承認・確認の操作はできない。
- 閲覧：案件リストを参照できる人は、案件概要書・論点整理書・回答書・提出された添付ファイルをすべて見られる。通知先だけに見せる情報はない（決定ログ #16）。

### S: 添付ファイルの提出

| 項目キー | ラベル | 型 | 必須 | AI | 選択肢・制約 | 備考 |
|---|---|---|:--:|:--:|---|---|
| attachPolicy | 添付ファイルの提出 | select（ラジオ） | ✅ | — | 添付ファイルも含めて申請する／案件概要書のみを申請する。既定値なし（必ず選ばせる） | 確認・申請画面で選ぶ |

- 「含めて申請する」：手元資料を案件の資料として保存し、案件リストを参照できる人全員に公開する。
- 「案件概要書のみ」：手元資料は提出しない。案件概要書の出所表示（資料名・見出し）は記録として残る。
- **一時保管**（決定ログ #17）：添付したファイルは、まず CMS の一時保管ライブラリに置く。見られるのはアップロードした本人と CMS だけ。**アップロードから1日たったファイルは、定期処理（1日1回）で自動削除する。**「添付ファイルも含めて申請」を選んで申請したときは、その時点で案件の資料へ移す（移したファイルは削除対象から外れる）。
- 削除したファイルは SharePoint のごみ箱に残り、保持期間が過ぎると消える。ごみ箱の中身が管理者から見えることは許容する（決定ログ #18）。
- 下書きのまま1日を過ぎて再開した場合、一時保管のファイルは消えている。再生成や「含めて申請」をするには、もう一度添付してもらう（画面で案内する）。
- 画面に注意書きを出す：「添付したファイルは、案件リストを参照できる人全員に公開されます。社外秘の見積や個人情報を含む資料を添付する場合は注意してください。」

### 自動生成のルール（AI）

| # | ルール |
|---|---|
| G1 | 手元資料に書かれている内容だけで値を設定する。推測で補わない。読み取れない項目は空欄にする |
| G2 | 選択肢の項目は、選択肢の中からだけ選ぶ。当てはまらなければ空欄 |
| G3 | 各項目の値に、出所（資料名と見出し・ページ）を付けて返す。画面では項目ごとに出所を表示する |
| G4 | 評価的な表現（「全社的に重要」等）を事実項目に書かない |
| G5 | 項目ごとに「AI生成／AI生成を修正／起案者入力」を記録する。申請時点の状態を保存し、事務局が区別できるようにする |
| G6 | 複数の資料で値が食い違うときは、両方を出所付きで示し、起案者に選ばせる（どちらが正しいかは判断しない） |

G1・G3・G6 は、申請後に事務局が行う論点整理の出所の書き方・食い違いの扱いと揃えている（論点整理の指示書 §00）。
