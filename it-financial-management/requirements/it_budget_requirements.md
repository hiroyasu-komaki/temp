## 1. 目的・背景

現状、IT部門の予算管理は静的なExcelでの積み上げ集計に依存しており、契約更新や資産の増減があるたびに手作業でシートを作り直す運用になっている。特にM365ライセンス費用については、契約更新月にIT部門の損益（PL）が一括計上により乱高下し、月次の予実管理が機能しない課題が確認されている（前払費用（BS）を用いた平準化モデルにより解消済み）。

この経験を踏まえ、IT部門の予算管理全体を「契約・資産・要員といった事実を記録したマスタデータから、予算を計算ロジックにより機械的に導出する」方式（Single Source of Truth／SSOT型の予算管理）に切り替えることで、以下を実現することを目的とする。

- マスタデータさえ正しく維持されていれば、誰が計算しても同じ予算数値が得られる（冪等性）
- 予算の誤りの原因を「計算ロジック」ではなく「マスタデータの品質」に一本化できる
- 契約・資産の増減に応じて予算が自動的に更新され、手作業での再構築が不要になる

あわせて、期首に確定した予算に対し、会計システムの**実績**と今期の**着地見込み**を月次で対比・管理できることを目的に含める（v0.6で追加。8.2参照）。チャージバック・ショーバック等の管理会計の仕組みは、現時点では対象としない。

## 2. 対象範囲（スコープ）

### 2.1 対象とする予算（In Scope）

IT部門の「Run予算」（運用・維持のための経常的な予算）を対象とする。具体的には次の4つのマスタ、および経費予算（後述）から構成される。

| マスタ / 区分 | 内容 |
|---|---|
| 契約マスタ | SaaS・保守・通信・業務委託等の契約に基づく費用 |
| 固定資産マスタ | 端末・ネットワーク機器等、購入し資産計上する物品の減価償却費 |
| 組織・要員マスタ | 正社員のFTE按分人件費、および稼働単価が開示されている外部人材費用 |
| 経費予算（従来方式） | T&E、教育費、出張、イベント、謝礼、買い切りソフトウェア、クラウド利用料の完全変動部分等 |
| 移管予算（2027年度〜） | 各ファンクションからGDSへ移管されたIT予算。移管元ファンクションのコストセンターのまま、Opex_Budgetに入力する（前提21、6.4） |

上記の予算は、実績・着地見込みとの月次対比（8.2）の対象とする。

### 2.2 対象外とする予算（Out of Scope）

| 区分 | 理由 |
|---|---|
| プロジェクト・新規投資予算（Grow/Transform予算） | 契約等の確定事実からの導出ではなく、ROIや優先順位に基づく意思決定プロセスに属するため、本モデリング手法とは性質が異なる。別途プロジェクト予算のガバナンスで管理する。**ただし、プロジェクトにアサインされた要員の人件費はRun予算に含める**（前提11）。プロジェクトの開発部分は別途請負契約を締結し、Grow/Transform予算側で予算化する |
| リース資産マスタ | 現時点でリース契約が存在しないため、今回は実装しない。将来リース契約が発生した時点で会計方針（オンバランス処理の要否）を確認のうえ、別途要件定義する |
| チャージバック・ショーバック | いずれ必要になるが、現時点では運用しない。チャージバック比率の項目は将来に備えて残し、既定値0とする（前提16） |

> **境界条件の注意**：プロジェクトが完了し本稼働に入った後の費用（導入したSaaSのライセンス費用、保守費用等）は、Run予算側（契約マスタ等）に引き渡される。引き渡しのタイミング・手続きは運用ルールとして別途定める必要がある（本書「11. 未確定事項」参照）。

マスタデータ（契約・固定資産・組織要員）が「事実」の記録であり、予算計算エンジンはそこから決定論的に月次の費用を算出する。経費予算（T&E等、クラウド変動費を含む）は従来どおり人による見積もり・入力に依拠し、移管予算は移管元が作成した月次の金額をそのまま取り込む。実績は各リージョンの会計システムから取り込み、予算・着地見込みと対比する。コストセンター・勘定科目・プロジェクト・為替レートの4マスタは、各マスタ／出力の共通ディメンション（軸）として参照される補助マスタであり、費用そのものを生む「事実」データではない。

## 4. 用語定義

| 用語 | 定義 |
|---|---|
| Run予算 | 運用・維持のための経常的な予算（本書の対象） |
| Grow/Transform予算 | 新規投資・変革のための予算（本書の対象外、プロジェクト予算として別管理） |
| SSOT (Single Source of Truth) | 予算計算の唯一の正となる入力データ源。本書では契約マスタ・固定資産マスタ・組織要員マスタを指す |
| 前払一括型契約 | 契約金額を契約開始月に一括でキャッシュアウトし、前払費用（BS）として資産計上した上で、一定期間（通常12ヶ月）かけて均等償却する契約類型 |
| 月額固定型契約 | 毎月一定額が請求され、前払処理を要さずそのまま月次のPLに計上する契約類型 |
| 業務委託単価型 | 稼働率・単価により費用が変動する業務委託契約（フリーランス、常駐型SE等）。契約マスタには単価情報のみを登録し、予算計上は組織・要員マスタ側でFTEに準じた按分により行う |
| チャージバック | IT部門が一旦全額を負担した費用のうち、**IT部門外**の利用部門に再請求（付け替え）する部分。IT部門の予算総額から控除される。本システムでは控除が目的であり、再請求先の識別・金額提示は行わない。**現時点では運用しない**（前提16） |
| 配賦（アロケーション） | IT部門が負担する費用を、GDS内のサブファンクション（15区分）のコストセンターに割り当てること。IT部門の予算総額は変動しない。チャージバックとは明確に区別する。リージョンをまたぐ配賦は行わない（前提20） |
| FTE (Full Time Equivalent) | 従業員の稼働割合を表す指標。1.0が専任稼働相当 |
| ESU (Extended Security Updates) | Windows Server等、サポート終了後もセキュリティ更新を有償で継続する契約 |
| コストセンター | 会計上の費用計上単位。仕訳ごとに指定し、セグメント別PLの作成に用いる。ファンクションとサブファンクションは、いずれもコストセンターを細分化した区分である |
| ファンクション | 部門。営業、研究、生産、本社（財務経理・人事等）、GDS等 |
| サブファンクション | ファンクション内の管理単位。GDSではリージョン（日本／北米／EMEA）×機能組織（アプリケーション／インフラ／データ／セキュリティ／ガバナンス）の15区分 |
| リージョン | 日本／北米／EMEA。それぞれ単体で財務報告を行う。EMEA配下の欧州各国はEMEAに集約して扱う（前提18） |
| 現地勘定科目 | 各リージョンの会計システム上の勘定科目。リージョンごとに体系が異なる。予算は現地勘定科目で作成・提出する（前提19） |
| GlobalCOA | 現地勘定科目をグローバルで集約するための2階層目の勘定科目 |
| 管理会計区分 | GlobalCOAを管理会計の観点で集約する3階層目の区分（人件費、販売管理費等） |
| 当初予算 | 期首に確定した予算。期中は変更しない（8.2） |
| 修正予算 | 期中に正式に承認された予算の増減を当初予算に加えたもの |
| 実績 | 各リージョンの会計システムで月次に確定した計上額 |
| 着地見込み | 締め済み月の実績＋未経過月の見込み。月ごとに版として保存する |
| 現地通貨 | 契約・取得・給与等が実際に発生している通貨（円・ドル・ユーロ・ポンドのいずれか） |
| 表示通貨 | 出力時にユーザーが選択する集計・表示上の通貨（現地通貨のまま、または単一通貨に換算） |

## 5. 前提条件（今回の検討で確定した事項）

| # | 項目 | 決定内容 |
|---|---|---|
| 1 | 会計年度 | 暦年ベース（1月〜12月）。FY25 = 2025年1月〜12月 |
| 2 | 予算対象期間 | 複数年ローリング（3〜5年）。契約マスタの複数年契約（例：M365のFY25〜27）をそのまま活用し、継続的に先の年度まで見通す運用 |
| 3 | 固定資産の減価償却方法 | 定額法・社内耐用年数基準（法定耐用年数とは別に、管理会計上の耐用年数を用いる） |
| 4 | 予算アウトプットの粒度 | サブファンクション別（リージョン×機能組織）の予算、GDS全体の総額、勘定科目別集計（現地勘定科目／GlobalCOA／管理会計区分の3階層）のすべてに対応する |
| 5 | クラウド利用料の扱い | コミット契約部分（AWS Savings Plans、Azure予約等）は契約マスタの月額固定型として扱う（実態は毎月払い＋未達差額精算のため）。完全な変動部分は経費予算で扱う |
| 6 | 買い切り型ソフトウェアライセンス | 金額の大小や会計上の資産計上／一括経費の別に関わらず、予算上は簡便化のため経費予算として扱う |
| 7 | ESU（拡張セキュリティ更新） | 前払一括型契約として契約マスタに計上する（複数年での段階的値上げは、既存の複数年契約ロジックでそのまま対応可能） |
| 8 | 業務委託の扱い | 月額固定で請求されるものは契約マスタ（月額固定型）。稼働管理・単価が開示されるもの（フリーランス、常駐型SE等）は組織・要員マスタに外部人材として計上し、契約マスタ側の単価情報を参照キーで紐付ける |
| 9 | 通貨 | 円・ドル・ユーロ・ポンドの4通貨を扱う。各マスタの金額は発生時の現地通貨で保持し、出力時に「現地通貨表示」と「単一通貨への換算表示」の両方に対応する |
| 10 | コストセンター構造 | 会計上のコストセンターは、ファンクション（部門）とサブファンクションに細分化される。GDSのサブファンクションは日本・北米・EMEAの3リージョン×アプリケーション・インフラ・データ・セキュリティ・ガバナンスの5機能組織＝15区分。各マスタの配賦先は会計上のコストセンターコードで持つ |
| 11 | プロジェクト人件費の扱い | 要員がプロジェクトにアサインされている場合も、その人件費（正社員・外部人材を問わず）はRun予算として計上する。プロジェクトの開発部分は別途請負契約を締結し、Grow/Transform予算側で予算化する |
| 12 | 契約終了日の入力ルール | 書面上の契約終了日ではなく、**実際に契約が終了する時期**を入力する。更新を前提とした自動延長ロジックは実装しない。終了予定がない契約は空欄とし、予算期間の最終月まで継続計上する |
| 13 | 前払一括型の登録単位 | 1回の前払支払につき1行で登録する。複数年契約は契約年度ごとに行を分ける（既存M365モデルの登録方式を踏襲）。同一契約の束ね表示には契約グループIDを用いる |
| 14 | BS（貸借対照表）予算 | 前払費用残高・期末帳簿価額等のBS予算は**出力対象外**とする。計算エンジンは月次のCFとPLのみを算出する |
| 15 | 消費税の扱い | 金額は原則税抜で入力する。税区分の厳密な管理・税額計算は本システムの対象外とし、税込入力が混在しても運用上許容する |
| 17 | 予算の入力単位 | すべての予算はOpex_Budgetに**月別12列**で入力する（v0.6までの上期・下期の2列は廃止）（6.4参照） |
| 16 | チャージバックの管理粒度 | チャージバックは**比率のみ**を保持する。目的はIT部門の予算からの控除であり、再請求先への金額提示は行わないため、再請求先を識別するコード・マスタは持たない。**現時点では運用せず、比率は既定値0とする**（将来必要になった時点で運用を開始する） |
| 18 | リージョン | 日本・北米・EMEAの3リージョン。EMEA配下の欧州各国はEMEAに集約し、国別のセグメント・勘定科目は扱わない |
| 19 | 勘定科目の階層 | 現地勘定科目（リージョンごと）→ GlobalCOA → 管理会計区分の3階層。予算は**現地勘定科目**で作成・提出する。GlobalCOA・管理会計区分は集計用の階層として扱う |
| 20 | リージョンをまたぐ配賦 | 行わない。費用は計上（支払・取得・雇用）するリージョンのコストセンターに計上する。グローバル契約は、まとめて支払うリージョンに全額計上する（例：Microsoft契約は日本）。国をまたいで配置される要員はいないため、人件費も所属リージョン内で完結する |
| 21 | 移管予算のコストセンター | 2027年度から各ファンクションより移管されるIT予算は、当面、**移管元ファンクションのコストセンター**のまま管理する |
| 22 | 予実・着地見込み | 当初予算は期首に確定した版を凍結し、実績・着地見込みと月次で対比する。比較はPL額で、コストセンター×現地勘定科目×月の粒度で行う（8.2） |
| 23 | 入力の運用 | 入力ブックはSharePointのチームサイト上の1ファイルとし、北米・EMEA・各サブファンクションの担当者を含む全員が同じシートを共同編集する。項目名は英語とし、日本語名と日英の説明を項目定義シートに置く（ADR-011） |
| 24 | 入力の分担 | 共有台帳の予算入力シートはOpex_Budgetの1枚に一本化する。契約・固定資産・組織要員のドライバーは入力者ユーティリティで管理し、Exportを値で貼り付ける（6.5、ADR-012） |

## 6. マスタデータ要件

### 6.0 共通ディメンションマスタ

契約マスタ・固定資産マスタ・組織要員マスタから共通して参照される、配賦・集計軸の基礎データ。

**コストセンターマスタ**

| 項目 | 説明 |
|---|---|
| コストセンターコード | 会計上のコストセンターコード（一意キー） |
| リージョン | 日本／北米／EMEA |
| ファンクション | GDS、営業、研究、生産、本社 等 |
| サブファンクション | ファンクション内の管理単位。GDSは機能組織（アプリケーション／インフラ／データ／セキュリティ／ガバナンス） |
| コストセンター名 | 表示用の名称 |

GDSのコストセンターは、リージョン×機能組織の15サブファンクションで構成する（前提10）。契約マスタ・固定資産マスタ・組織要員マスタ・経費予算・移管予算の「配賦先」は、すべてこのコストセンターコードを参照する。移管予算を管理するため、**移管元ファンクションのコストセンター**も登録する（前提21）。チャージバック先（IT部門外の利用部門）は、移管元として登録したものを除き含まない。

**勘定科目マスタ**

| 項目 | 説明 |
|---|---|
| リージョン | 日本／北米／EMEA |
| 現地勘定科目コード | リージョンの会計システム上の科目コード。本マスタのキーは「リージョン＋現地勘定科目コード」 |
| 現地勘定科目名 | 減価償却費、通信費、業務委託費、支払手数料 等 |
| GlobalCOAコード | 2階層目の勘定科目 |
| GlobalCOA名 | |
| 管理会計区分 | 3階層目の区分（人件費、販売管理費 等） |

契約マスタ・固定資産マスタ・組織要員マスタ・経費予算・移管予算の「勘定科目コード」は、すべて**現地勘定科目コード**とし、本マスタを参照する（前提19）。リージョンは配賦先コストセンターから決まるため、配賦先のリージョンに存在しない科目を指定した行は入力エラーとする。

**プロジェクトマスタ**

| 項目 | 説明 |
|---|---|
| プロジェクトコード | 一意キー |
| プロジェクト名 | |
| 負担コストセンターコード | コストセンターマスタを参照。本プロジェクトにアサインされた要員の人件費を計上するコストセンター |
| 期間 | プロジェクトの開始月・終了月 |

組織・要員マスタのFTE配分先としてプロジェクトを指定した場合、その人件費は**本マスタの負担コストセンターに配賦**される（前提11）。プロジェクトコードは分析用の補助軸として保持し、コストセンター別配賦表の集計単位そのものにはしない。

**為替レートマスタ**

| 項目 | 説明 |
|---|---|
| 通貨コード | USD／EUR／GBP／JPY |
| 会計年度 | レートを適用する年度（予算レートは期首固定のため年度単位で持つ） |
| 対円レート | 表示通貨への換算に用いるレート |
| レート区分 | **予算レート（期首固定）を既定とする**（ADR-005）。予実比較では予算・実績・着地見込みのいずれも予算レートで換算し、為替変動を差異に含めない（8.2）。実績レート・月次スポットレートは将来の為替影響分析用に追加可能な構造としておく |

出力時に表示通貨（現地通貨のまま、または指定した単一通貨）を選択できるようにし、単一通貨換算を選んだ場合はこの為替レートマスタのレートで換算する。マスタ自体の金額はすべて発生時の現地通貨で保持し、換算は集計・表示の段階でのみ行う（マスタの原本性を保つため）。

### 8.2 予実・着地見込み管理

事業年度の予算と実績を対比し、今期の着地見込みを月次で管理する。

**数値の区分**

| 区分 | 内容 | 更新 |
|---|---|---|
| 当初予算 | 期首に確定した予算。確定時の計算結果を版として保存し、期中は変更しない | 年1回 |
| 修正予算 | 期中に正式に承認された予算の増減（個別移管分の受け入れ、追加承認等）を当初予算に加えたもの。当初予算とは別に保持する | 承認の都度 |

| 着地見込み | 締め済み月の実績＋未経過月の見込み。月ごとに版（YYYYMM）として保存する | 毎月 |

**表示と入力（共有台帳の `Budget_vs_Actual` シート）**

- 予算は `Opex_Budget`、実績は `Actuals` から数式で自動表示する。`Opex_Budget` は予算確定後に固定し、`Actuals` は予算管理者が会計システムのデータを毎月手で貼り付ける。
- コストセンター×現地勘定科目ごとに1ブロック（8行）を置く：Budget／Actual／Variance vs Budget／Forecast (input)／Actual + Forecast／Prior Month Forecast／Variance vs Prior Month／Rationale。上の3行で実績の差異を確認し、見込みを入力すると次の3行で見込みの差異が分かり、Rationaleでその理由をまとめて見る。Actual + Forecastの実績部分はActual行から転記する。ブロックのキーは予算確定後にITファイナンスが設定する。
- 着地見込み（Actual + Forecast）は、締め月までは実績、以降は見込み行の値（空欄なら予算額）とする。
- 差異（Variance）は、各月とYTDが「実績−予算」、MTG（Month to Go：締め月より後の残り期間）が「見込み−予算」、FYがその合計。MTGの差異は、残り期間が予算どおり積み上がるか、予定外の支出がありそうかを示す。Variance vs Prior Monthは（実績＋見込み）−前月見込み。理由（Rationale）は1行で、月の列に各月の理由、YTD列とMTG列にそれぞれの合計に対するコメントを書く。
- 上部で会計年度・締め月・表示通貨を指定する。ブロックに入っていない予算・実績はチェック欄に表示する。

**比較のルール**

| # | ルール |
|---|---|
| 1 | 比較はPL額で行う（CFは比較しない） |
| 2 | 比較の粒度はコストセンター×現地勘定科目×月とする。リージョン・ファンクション・サブファンクション、GlobalCOA・管理会計区分は集計軸として使う |
| 3 | 予算・実績・着地見込みは、いずれも予算レート（期首固定）で換算して比較し、為替変動を差異に含めない |
| 4 | 差異の説明は、閾値（率・金額）を超えた行に限って求める |
| 5 | 計上月のずれ（請求書の遅延等）による差異を減らすため、各リージョン経理の未払計上（発生主義）の運用を確認しておく |

**出力**

| 出力 | 内容 |
|---|---|
| 予実対比表（Budget_vs_Actual） | 月別・YTD・MTG・FYについて、予算・実績・実績＋見込みと差異、その理由 |
| 前月見込みとの比較 | Prior Month Forecast行に前月時点の実績＋見込みを表示する。`Prior_Forecast` シートに、Power QueryでActual + Forecast行の控えを取る。ITファイナンスが毎月、①Prior_Forecastを更新、②実績を貼り付け、③締め月を進める（控えの更新は必ず実績の貼り付けより前。このクエリは「すべて更新」の対象外にする） |

**月次サイクル**：各リージョン経理の月次締め → 実績の取り込み → 着地見込みの更新 → 集約・報告。日程は運用で定める。

## 10. 技術選定（決定済み・`it_budget_adr.md` 参照）

**Windows版 Excel + Power Query + Power Pivot** を採用することを決定した（ADR-001）。マスタブックと計算ブックを物理的に分離し（ADR-002）、月次展開はPower Query（M言語）、集計・通貨換算はDAXメジャーで実装する（ADR-004）。決定の根拠・却下した選択肢・将来の移行パスは `it_budget_adr.md` を参照のこと。

以下は選定時に用いた考慮事項である（記録として残す）。

| 観点 | 考慮点 |
|---|---|
| データ量 | 契約数・資産数・要員数が今後どの程度の規模になるか（数十件〜数百件で収まるか、それ以上か）によって、Excelの数式ベース集計（SUMPRODUCT等）で十分か、Power Query/Power Pivotやデータベースを要するかが変わる |
| 計算ロジックの複雑性 | 契約種別ごとの分岐、FTEの複数配分先按分、コストセンター別・勘定科目別の多軸集計、多通貨換算など、ロジックが積み上がるほどExcel数式の保守性は低下する。VBA、Power Query（M言語）、外部スクリプト（Python等）による計算処理の分離も選択肢になる |
| 更新頻度・同時編集 | 複数人がマスタを同時に更新する運用があるか（Excelはロック・排他制御に弱い） |
| 監査証跡 | マスタの変更履歴（誰が・いつ・何を変更したか）を残す必要があるか |
| 他システムとの連携 | 契約管理システム、固定資産台帳、人事システム等、既存システムからのデータ連携（手動転記／自動連携）の要否 |
| 可視化・レポーティング | コストセンター別・勘定科目別集計をダッシュボード化する場合、Excel単体よりBIツール（Power BI等）との連携が有利な場合がある |
