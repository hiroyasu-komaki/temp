# IT Materiality フレームワーク ─ 外部性を測り、所有し、予算に接続する

> **この章の位置づけ**：Layer 2 設計 ／ 03 設計A：判断ルール。分析①（01）に応答する。投資判断の第3の軸、共通層のオーナー設定、判定と予算配分の接続、段階導入。何を・どの軸で判断するかを決める。
> **前章**：[02 分析②：審議機構の層](02_committee-structural-analysis.md)　**次章**：[04 設計B：運営プロセス](04_process-redesign.md)

前章までに、分権的IT投資の下で生じる4つの症状は、いずれも**意思決定者の視野の外に便益・費用が漏れること**から演繹されることを確認した。
経済学が示す処方箋は、意識改革ではなく **①測定　②所有権の設定　③インセンティブの再設計** である。本フレームワークは、この三点を制度として実装する。

---

## 01 設計要件と、それに対する回答

| 要件 | 内容 | FRAMEWORK ANSWER |
|---|---|---|
| **要件1　測定** | 外部性は当事者から見えない。見えないものは判断の場に上がらない。まず**視野の外に出た便益・費用を可視化する尺度**が要る。 | **投資判断に第3の軸「共通性・持続性」を導入する** |
| **要件2　所有権** | 共通基盤・アーキテクチャ健全性に**所有者がいない**。所有者がいなければ、誰も測らず、誰も供給せず、誰も請求できない。 | **IT部門を共通層のオーナーとし、測定責務と起案権を負わせる** |
| **要件3　インセンティブ** | 尺度を作っても、**予算の出所と決定権が変わらなければ判断は変わらない**。評価軸は判断者の利害を動かさないからである。 | **Materiality の判定を予算配分プロセスに接続する** |

## 02 IT Materiality の意思決定領域（What）

「重要性（Materiality）」とは、限られた経営資源を前提に、**どこにどれだけの投資・統制・運用品質を割り当てるか**を決める尺度である。IT領域を6つに分け、それぞれに問いと判断基準を定義する。

| 領域（Domain） | 問い（What） | 主な判断基準 | 適用の結果 |
|---|---|---|---|
| ① 投資（Investment） | 何に投資を優先するか？ | 事業価値／ROI・リスク低減・法規制対応・**共通性・持続性 ★**・実現可能性 | 投資の優先順位／予算計上／共通層での供給 |
| ② リスク（Risk） | どのリスクを許容するか？ | 発生確率・影響度（財務・業務・レピュテーション）・許容期間／許容レベル | リスク許容レベル／対策の優先順位 |
| ③ 統制（Compliance） | どこまで統制を求めるか？ | 法令・規制・システム重要度・データの機微性・監査要求 | 統制の強さ・深さ／適用範囲 |
| ④ 運用（Operational） | どこまで運用品質・可用性を求めるか？ | 業務インパクト・可用性要求・利用者数／頻度・RTO／RPO | SLA・運用品質レベル／体制の強弱 |
| ⑤ データ（Data） | どのデータを重点管理するか？ | 利用範囲／重要業務・法規制／機微性・品質要求レベル・ライフサイクル | データ分類・管理レベル／品質基準・保管期間 |
| ⑥ ベンダー（Vendor） | どのベンダーを重点管理するか？ | 年間支出額・依存度／代替難易度・リスク（財務・情報・運用） | 管理の強さ・頻度／契約条件・モニタリング |

## 03 要件1への回答 ─ 投資判断の第3の軸

既存の2軸は、いずれも**単一施策を、それ単独で、当期の視点から評価する静的な軸**である。この2軸だけでは、外部性を持つ投資は構造的に評価から脱落する。

| 軸 | 問い | 内容 | 脱落するもの |
|---|---|---|---|
| **軸1　事業価値** | やれば、何が得られるか？ | 売上・生産性・コスト削減／戦略との整合性／ROI・NPV | 便益が自部門の外に及ぶ投資は、自部門の取り分だけでは常に過小評価される。 |
| **軸2　リスク低減・法規制対応** | やらなければ、何を失うか？ | 法令・規制対応／セキュリティ／事業継続・可用性 | EOL・技術的負債は「発生確率が低い」と評価されるため、毎年、優先順位で負け続ける。 |

### 軸3　共通性・持続性（NEW）

**この投資の便益・費用は、どこまで自部門・当期の外に及ぶか？**

軸3は、外への及び方によって **基盤性**（他部門へ及ぶ）と **負債**（将来へ及ぶ）の2つに分かれ、それぞれ3つの要素で見る。

| 区分 | 要素 | 申請者に聞く事実 | IT部門が見ること |
|---|---|---|---|
| **基盤性**<br>他部門へ及ぶ | 受益範囲 | 利用部門・利用者数・対象業務 | 受益が、申請した部門の外に広がるか |
| | つながり | 接続する既存システムと連携方式、扱うデータ（マスタ・全社データ等） | 全社のデータや連携の要に触れるか。疎結合を保てるか |
| | 前提依存 | 聞かない（IT部門が依存関係の台帳から見る） | この投資を前提にしている、他の計画やシステムがあるか |
| **負債**<br>将来へ及ぶ | 保守期限 | 新規か更新か、現行製品の保守期限（EOL） | 先送りすると、期限切れの緊急対応にならないか。この投資自体が負債の返済ではないか |
| | 標準からの逸脱 | 聞かない（IT部門が構成と連携方式から読む） | 全社標準の技術・連携方式・データ定義から外れていないか |
| | 重複と個別運用 | 運用・保守の体制と契約先 | 似た機能がすでにないか。個別の運用・改修や、後からの共通化が将来の費用にならないか |

判定の深さは段階的に上げる（§06）。**初年度**は、6要素を見たうえで基盤性・負債の2問（§05 ステップ7 の Q1・Q2）に Yes／No と理由で答える。**次年度以降**は、台帳を根拠に要素ごとの程度を評価する。

> **設計原則：スコアは申請者に付けさせない。** 依存関係・EOL・標準は事業部門から原理的に見えず、かつ評価が予算に直結する以上、自己申告には必ずバイアスがかかる。**申請者に求めるのは「事実」、要素ごとに評価しスコア化するのは IT部門**（審議の場では、事務局のIT部門側担当が素点を付け、委員会が確定する。04 §2.2）。

## 04 要件2への回答 ─ 共通層のオーナーを定める

### IT部門を「共通層のオーナー」として定義する

共通基盤・アーキテクチャ健全性・共有資源に所有者がいないことが、放置の直接の原因である。したがって本フレームワークは、IT部門に次の**責務と権限を同時に**付与する。

- **【責務】** 全社の技術資産の状態を把握し、外部性を測定する唯一の主体となる（EOL台帳・アーキテクチャ標準・依存関係の保持）
- **【権限】** 共通性・持続性スコアを付与し、共通層への投資を自ら起案できる

### なぜ IT部門でなければならないか

外部性とは、**当事者から見えない便益・費用**のことである。見えない者に測らせるのは論理的に矛盾する。全部門のシステム・依存関係・保守状況を横断的に見ている主体は、組織上IT部門のみである。

**裏を返せば** ── この軸を導入するとは、IT部門が「全社の技術資産の状態を把握している唯一の主体」になると**約束する**ことに等しい。台帳を持たなければ、この枠組みは成立しない。

## 05 要件3への回答 ─ 判定を予算配分に接続する

尺度を作っただけでは効かない。**支払うのが事業部門である限り、「うちは払わない」が彼らの合理的判断であり続ける。** 判定は、予算プロセスの中に組み込まれてはじめて機能する。

| レーン | # | ステップ | 内容 |
|---|---|---|---|
| **事業部門** | 1 | 投資予算案の申請 | 各部門が次年度のIT投資予算を申請する |
| | 2 | 施策概要の申請 | 便益・必要性・重要性を定量／定性で記載。アイデア段階でも事業価値が見込めるものは申請する |
| | 3 | 事実項目の記入<br>（要件1の実装） | 利用部門・利用者数・対象業務／連携する既存システムと連携方式／対象データ／新規か更新か／現行製品の保守期限／運用・保守の体制と契約先。**スコアではなく事実のみを求める** |
| **IT ＋ 経営** | 4 | 全社での優先度議論 | 全部門の申請を横並びで比較し、ITと経営が優先度を決定する |
| | 5 | 予算計上の可否<br>（判定） | 採択案件は事業部門予算として計上される |
| | 6 | 不採択案件のプール | 「自部門価値が小さい」と判断された施策が滞留する。**この中に、外部性ゆえに落ちた案件が含まれる** |
| **IT部門予算** | 7 | 救済判定 ─ 2つの問い<br>（軸3を適用） | **Q1：今やらないと、来年以降に他の何かが困るか？（基盤性）**<br>**Q2：今やらないと、将来の費用が増えるか？（負債）**<br>両方Yes＝最優先／片方Yes＝候補／両方No＝拾わない（＝単に自部門価値が小さいだけの案件） |
| | 8 | IT枠での計上 | 枠の範囲内で救済する。**判定理由を必ず文書に残す**（初年度は精緻さより説明可能性を優先） |
| | 9 | IT部門による起案<br>（別枠が必要） | 全社基盤（ID管理・データ基盤・統合基盤）は**どの部門も申請しないため、救済枠には載ってこない**。IT起案枠がなければ、正の外部性の問題は解けない |

> **救済枠の定義を、最初に宣言する：** 救済枠は「惜しかった案件の敗者復活」でも「政治的配慮の調整弁」でもない。**事業部門の視野では正当に評価できない案件を、全社視点で拾い直すための枠**である。この定義を先に固定しなければ、救済枠は必ずごね得ルートに変質する。

> **共通層への付け替え：** 事業部門が起案した案件でも、審議で共通層に当たる（受益が起案部門の外に広く及ぶ基盤である）と判断したものは、IT部門が管理する共通層予算（ステップ9のIT起案枠と同じ枠）に付け替えて計上する。起案部門の予算に負わせたままでは、便益が外に漏れる分だけ投資が過小になるためである。

### 年次の予算編成と、個別案件の審議（04）の関係

上の9ステップは、年に一度の予算編成で**予算枠と優先順位**を決める仕組みである。予算に計上された案件の執行開始の判断（案件概要書に対する採択可否）と、年度途中に発生した新規案件の審議は、投資委員会が [04 の審議プロセス](04_process-redesign.md) で行う。軸3の判定は、両方で同じ物差しを使う。


> **定式化**：軸3と予算接続が式の上で何をしているか（判断主体の差し替えによる内部化）は、[付録：外部性と共通性の定式化](../appendix/math_externality-formalization.md) の D を参照。

## 06 段階導入 ─ 判定機構であると同時にデータ収集機構である

台帳が整っていないことは制約であるが、同時に**台帳を作るための唯一の機会**でもある。精緻な尺度を待つのではなく、粗い判定から始めて台帳を育てる。

### PHASE 1 ／ 初年度 ── 台帳なし ─ 2問判定で始める

- 共通性は、6要素（§03）を見たうえで「基盤性」「負債」の2問に Yes／No と理由で答えて、IT部門が仕分ける
- 前提依存・標準からの逸脱は、台帳が整うまでIT部門が把握している範囲で見る
- スコアの厳密さは求めない。**判定理由の記録を必須とする**
- 事業部門からは**スコアではなく事実**を集める
- **集まった申請書の束が、そのまま台帳の初版になる**

### PHASE 2 ／ 次年度以降 ── 台帳あり ─ 要素ごとの本格判定へ

- EOL台帳、アーキテクチャ標準、依存関係を整備する
- 2問の Yes／No から、台帳を根拠にした6要素ごとの程度の評価に移る
- 救済枠・起案枠の実績（他部門への波及効果）を可視化する
- **実績を根拠に、共通層予算枠の拡大を要求する**

## 07 4つの症状は、どこで解かれるか

| 症状 | 分類 | 本フレームワークの打ち手 | 解消の可否と、その理由 |
|---|---|---|---|
| 負債が溜まる | 負の外部性 | 軸3の負債（保守期限・標準からの逸脱・重複と個別運用）＋救済判定 Q2 | **解ける。** 隠れた費用を測り、判断の場に載せれば、経営は判断できる。案件は事業部門から申請されており、俎上には載っている |
| 基盤が育たない | 正の外部性／公共財 | IT起案枠（ステップ9）<br>＝共通層の公的供給 | **救済枠だけでは解けない。** どの部門も申請しない以上、不採択プールに存在しない。可視化しても、支払う主体がいないという問題は残る。**供給主体を別に立てるしかない** |
| IT部門が飽和する | コモンズの悲劇 | Materiality による優先度の全社一元化＋要求の可視化＋**ShowBack** | **部分的に解ける。** 優先度判定を全社一元化すれば「全件最優先」は成立しなくなる。共有資源の**利用量は ShowBack で可視化する**（Ostromの成立条件）。割当のルールは、可視化した利用量を根拠に別途設計する |
| 是正の起点がない | 情報の非対称性 | 申請者＝事実／IT＝評価の分離＋申請書からの台帳構築 | **解ける。** 測定責務をIT部門に置き、自己申告バイアスを構造的に排除する。台帳が育てば、Phase 2 で判定精度が上がる |


> **共有資源の利用：ShowBack は行い、ChargeBack は行わない。**
> IT部門が一元的に契約・負担している共有資源（データセンター、クラウド契約など）は、部門別の利用量と費用を可視化する（ShowBack）。利用部門への課金（ChargeBack）は行わない。
>
> - 課金すると、部門が共通基盤を離れて個別の基盤を持つ方向に動き、標準からの逸脱を促しうる
> - 課金額の根拠となる外部費用を、現時点の測定精度では正しく定められない
> - 事業部門が予算を保有する構造では、課金は部門間の予算移転と交渉を伴い、取引費用が大きい
>
> ShowBack は部門の損得計算を直接は変えない。役割は、利用量を根拠に全社での優先度議論と割当のルール設計を始められる状態を作ることにある（定式化は[付録](../appendix/math_externality-formalization.md) の D-5）。

## 結び ─ このフレームワークが本質的に行っていること

IT Materiality フレームワークは、投資評価表の項目を増やす取り組みではない。**分権的IT投資が構造的に取りこぼしてきた「視野の外の便益・費用」を、測定可能にし、所有者を定め、予算配分に接続する制度**である。
経済学が外部性に対して処方してきたもの ── **測定（内部化）、所有権の設定、公的供給** ── を、企業内部の予算制度に翻訳したものにほかならない。

> **導入にあたっての留意：** 本フレームワークは、次の二つが揃わなければ形骸化する。
>
> **① IT部門が台帳を持つこと。** 測定責務を負う以上、台帳のない状態は約束不履行である。初年度は粗くてよいが、育てる計画がなければならない。
>
> **② 救済枠とIT起案枠の両方が確保されること。** 救済枠のみでは「負債が溜まる」しか解けず、「基盤が育たない」は次年度も繰り返される。
