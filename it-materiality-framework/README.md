# materiality — IT Materiality Framework

共通基盤への過小投資、技術的負債の蓄積、投資委員会の機能不全は、いずれも規律や意識の問題ではなく、外部性から演繹される構造的必然である ── という診断と、それに対する制度設計、実際に社内へ出す文書をまとめたコンセプト資料。
**扱わないもの**：予算・審議の構造以外の要因（人材不足・スキル・ベンダー依存、委員の資質・組織風土など）と、CMS・AIエージェントの実装詳細（画面仕様・ツール選定）。

## 目的

本資料は、IT投資における**共通基盤の不足**や**技術的負債**といった構造的課題を、経済学の「**外部性**」という視点から捉え直し、それを解くための枠組みを提示する。各部門が自部門の損得の範囲で合理的に判断する限り、共通基盤は誰も供給せず、負債は先送りされ、共有資源は使い潰される（**コモンズの悲劇**）。これを避けるため、IT部門が全社的な視点で**所有権と測定責務**を担うことを提唱する。

具体的には、従来の事業価値・リスク低減に加えて「**共通性・持続性**」を第3の判断軸に導入し、その判定を予算配分に直接結びつける**制度設計**への転換を求める。あわせて審議プロセスを**非同期・文書駆動型**へ再設計し、事実と評価の分離とAIエージェントの活用によって、意思決定の**質と速度**を同時に高める。

最終的には、IT部門が**技術資産の番人**として権限と責任を明確にし、持続可能なIT投資構造を築くための実務的なガイドラインとなることを目指す。

## 3層の構成

層が変われば読者が変わり、使う言葉も変わる。

### LAYER 1　理論・分析 ── なぜそうなるのか

> **この層のルール**　経済学の言葉で書く。特定部門を名指ししない。処方箋は「型」の提示までで止め、具体的な制度案は設計層に渡す。

| 章 | 内容 |
|---|---|
| [00 理論](chapters/00_externality-and-commons.md)<br>外部性とコモンズの悲劇 | 正／負の外部性、コモンズの悲劇、フリーライダー問題の定義と、処方箋の型（Pigou・Coase・Ostrom）。自社の話は出てこない共通の土台。 |
| [01 分析①：予算配分の層](chapters/01_it-investment-market-failure.md)<br>IT投資予算を事業部門が保有する構造下で、何が起きるか | 問い：予算を誰が持つか。① 基盤が育たない ② 負債が溜まる ③ IT部門が飽和する ④ 是正の起点がない。<br>**導く要件：測定／所有権／インセンティブ再設計** |
| [02 分析②：審議機構の層](chapters/02_committee-structural-analysis.md)<br>投資委員会という審議機構の下で、何が起きるか | 問い：決定を誰が・どこで作るか。① 会議が判断の場にならない ② 資料が膨らむ ③ 決定が遅れる ④ 承認が終点になる。<br>**導く要件：チャネル／生産主体／時間軸の分離** |
| [付録：外部性と共通性の定式化](appendix/math_externality-formalization.md) | 00・03 の補足。コモンズの悲劇・公共財の過小供給・異時点間の外部性を簡単なモデルで書き下し、共通性を入れた後の判断の式を示す。本文は数式なしで読める。 |

01 と 02 は別問題ではない。予算構造の外部性を是正するために置かれた機構が、その内部で同じ外部性を再生産している ── **同一の根の、二つの発現層**である。

### LAYER 2　設計 ── どう解くか

> **この層のルール**　理論は再説明せず参照にとどめる。実装詳細には踏み込まず、「何を確定させる必要があるか」までを書く。分析層の症状と一対一で対応させる。

| 章 | 内容 |
|---|---|
| [03 設計A：判断ルール](chapters/03_it-materiality-proposal.md)<br>IT Materiality フレームワーク | 01 に応答。投資判断の第3の軸、共通層のオーナー設定、判定と予算配分の接続、段階導入。**何を・どの軸で判断するか。** |
| [04 設計B：運営プロセス](chapters/04_process-redesign.md)<br>投資委員会プロセス改善企画 | 02 に応答。非同期・文書駆動の4ステップ、権限分離、CMS、AIエージェント事務局と、その内在リスク（R1〜R3）。**誰が・どう回すか。** |

**未決の設計論点**：Q1 エージェント設定の所有／Q2 軽レーンの監査（04 §5.3）。

### LAYER 3　実践 ── 実際に相手へ渡すもの

> **この層のルール**　経済学用語を一切使わない。「フレームワークに基づき」とも書かない。判断根拠は毎回、その案件の言葉で述べる。設計の未完了部分は滲ませない。

| 章・付録 | 内容 |
|---|---|
| [05 実践](chapters/05_practice-operations.md)<br>事業部門への依頼と、起案者への回答 | 次年度IT投資予算の申請プロセス（事実項目の新設、IT枠での救済判定）と、Step1 論点整理書を作る文書（copilot/）の解説。集めた事実は台帳となり、分析層へ実証データとして戻る。 |
| [論点整理書テンプレート](copilot/sheet_issue-brief_template.md) | Step1 文書の雛形。A4一枚で、審議する論点ごとに共通性の要素 × ケイパビリティを示す（proposal p.5〜9 に対応）。 |
| [論点整理の指示書](copilot/guide_issue-brief.md)<br>[Copilotエージェント指示](copilot/agent_issue-brief_instructions.md) | 申請Formと添付の案件概要書から、論点整理書の草案を Copilot で作るための判断基準（知識ファイル）と、エージェントの設定・指示文。Copilot は chapters を参照できないため、必要な前提は指示書に書き込んである。 |
