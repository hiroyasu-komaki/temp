# IT Management データソース作成手順書

参照モデル（`vs_capability_map.xlsx`）を雛形にして、当社の実態に合わせた「当社版」のデータソースを作る手順です。対象は Manage IT / Digital Solutions（L2はIT4ITの4つのVS：S2P／R2D／R2F／D2C）です。

整理された資料（業務フロー、システム台帳、EA資料など）が手元にない状態から始めることを前提にしています。

## 0. 基本の考え方

| 原則 | 内容 |
|---|---|
| 白紙から作らない | 参照モデルの各行について「当社にあるか・誰がやっているか」を確認していく。ゼロから書き起こすと、粒度も網羅性もぶれる |
| 説明文書がなければ記録をたどる | 業務を説明した文書がなくても、支払・契約・ログ・チケット・承認・バリデーションの記録は残っている。何をしているかは記録から起こし、人には確認するだけにする |
| 確認状態を必ず残す | 各行を「参照（未確認）／確認済み／当社で追加／該当なし」のどれかにする。参照モデルとの差が、後の考察の主な材料になる |
| 該当なしは削除しない | 当社で行っていない項目、担い手やシステムがない項目も、行を残して「該当なし」と記録する。それ自体がギャップを示す |
| 設計ルールは参照モデルと同じ | 1行1項目、VS L4の入力・出力情報が正本、アプリは種類の単位、ケイパビリティの定義は独立（README「設計ルール」） |

## 1. 手元の材料と使い道

| 材料 | 取り出すもの | 主に作るデータソース |
|---|---|---|
| 組織図・IT部門の担当者 | IT部門の組織と分掌、担当者ごとの業務、委託先の窓口 | バリューストリーム（実施者）、ケイパビリティ（担い手）、ケイパビリティレベル |
| 会計の支払・契約データ | IT関連の勘定科目の支払明細（取引先・摘要・金額）、保守・ライセンス・SaaS・業務委託の契約書 | アプリケーション（現状システム）、情報オブジェクト（ベンダー・契約）、費用の重み |
| 管理画面・ツール | Entra IDのエンタープライズアプリとサインインログ、M365のライセンス、端末管理の台帳、クラウドのサブスクリプション、チケットの種別と件数 | アプリケーション、VS L4（R2F・D2Cの実際の流れ）、件数・利用者数の重み |
| GxP・J-SOXの文書 | CSV対象システム一覧、CSVのSOP、バリデーション文書（URS〜報告書）、IT全般統制の規程・RCM・評価結果、監査指摘 | VS L4（R2D・R2F・D2C）、情報オブジェクト（GxP・統制の記録）、ケイパビリティレベル |

VSのL2ごとに、主に使う材料は次のとおりです。

| VS L2 | 主な材料 | 見込み |
|---|---|---|
| S2P 戦略・ポートフォリオ | 中期計画・予算資料・稟議書、CIO・IT企画との面談 | 文書が最も少ない。面談が中心になる |
| R2D 要件定義・開発・配備 | CSVのSOP、バリデーション文書、IT全般統制（開発・保守）、委託契約 | 文書で大半が埋まる |
| R2F 利用申請・提供 | チケットの種別、Entra ID、M365、IT全般統制（アクセス管理） | 記録から起こせる |
| D2C 検知・是正 | チケット（インシデント・変更）、監視ツール、IT全般統制（運用・管理）、定期レビュー記録 | 記録から起こせる |

IT全般統制の4つの領域（開発・保守／運用・管理／アクセス管理などの安全性の確保／外部委託の契約管理）と、CSVのSOPには、R2D・R2F・D2Cの手順がかなり書かれています。まずここから始めます。

## 2. 作業の全体像

| フェーズ | 作るもの | 主な材料 | 目安 |
|---|---|---|---|
| 0 準備 | 当社版xlsx、証跡台帳、面談相手の一覧 | 組織図 | 1週 |
| 1 現物の棚卸し | 現状システム一覧、ベンダー・契約一覧、文書一覧 | 会計・契約、管理画面、GxP・J-SOX | 2週 |
| 2 バリューストリーム | L3の確認、L4と入力・出力情報 | GxP・J-SOX、ケースの追跡、面談 | 3週 |
| 3 情報オブジェクト | 用語集と分類 | フェーズ2の入力・出力情報 | 1週 |
| 4 ケイパビリティ | L1〜L3の確認、担い手 | 組織図、面談 | 1週（フェーズ2と並行） |
| 5 アプリケーション | 現状システムとアプリ種類の対応 | フェーズ1 | 1週 |
| 6 関係 | 関係シートと二軸分析シート | フェーズ2〜5 | 1週 |
| 7 ケイパビリティレベル | 現状レベル・重要度 | すべての材料、面談 | 1〜2週 |
| 8 検証 | 整合チェック、スライドの更新 | — | 1週 |

進める順番：0 → 1 → 2と4（並行）→ 3 → 5 → 6 → 7 → 8。担当1〜2名で10〜12週が目安です。

## 3. フェーズ別の手順

### フェーズ0 準備

1. 参照モデルをコピーして当社版を作る（例：`vs_capability_map_asis.xlsx`）。参照モデルは変更しない。
2. 当社版に次の列を追加する。

   | シート | 追加する列 |
   |---|---|
   | 5つのデータソースすべて | 確認状態、根拠（証跡ID） |
   | バリューストリーム（L4の行） | 実施者（部署・委託先）、使用システム、頻度・件数 |
   | ケイパビリティマップ（L3の行） | 担い手（現状）：社内部署／委託先／なし |
   | ケイパビリティレベル | 現状レベル、目標レベル、重要度、根拠 |

3. 作業用のシートを2つ追加する。
   - **証跡台帳**：証跡ID、資料名、入手元、日付、保管場所。以降、根拠はすべてこのIDで書く。
   - **現状システム**：フェーズ1で作る（列はフェーズ1を参照）。
4. 組織図から面談相手の一覧を作る。ケイパビリティL2（28件）ごとに担当者を1名割り当てる。委託先が担っている領域は、社内の窓口を割り当てる。
5. 範囲を決める。
   - IT部門が管理するシステムだけか、事業部門が独自に契約しているシステムも含むか。
   - GxPの対象範囲（GMP・GQP・GVP・GLP・GCPのどこまでを含むか）。

完了条件：当社版xlsx・証跡台帳・面談相手の一覧がそろい、範囲が決まっている。

### フェーズ1 現物の棚卸し

人に聞く前に、記録から「実際にあるもの」を集めます。

1. **支払から**：会計システムから、IT関連の勘定科目の過去24か月の支払明細を出す。対象はソフトウェア、保守料、通信費、支払手数料、業務委託費、リース料など（当社の科目名は経理に確認する）。取引先×摘要で名寄せし、製品・サービス・委託ごとの年間金額を出す。
2. **契約から**：保守・ライセンス・SaaS・業務委託の契約書を集め、次を記録する。
   - 対象システム
   - 委託の範囲と形態（請負／準委任）
   - 期間
   - SLAの有無
   - 再委託の有無
3. **管理画面から**：
   - Entra ID：エンタープライズアプリ（SSO連携しているアプリ）の一覧と、サインインログから出したアプリごとの利用者数（ログが保存されている期間の分）
   - M365：ライセンスの種類と割当数
   - 端末管理：端末の台数と、配布しているソフトウェア
   - クラウド：サブスクリプション（アカウント）とリソースの一覧
   - チケットツール：チケットの種別（カテゴリ）と、過去12か月の種別ごとの件数
4. **GxP・J-SOXから**：
   - CSV対象システムの一覧（GxP区分・カテゴリ）
   - IT全般統制の対象システム
   - システムごとの手順書・記録の一覧
5. **名寄せ**：1〜4を突き合わせて「現状システム」シートにまとめる。

   | 列 | 内容 |
   |---|---|
   | システムID | SYS-001から連番 |
   | システム名／製品・サービス名／ベンダー | 社内の呼び名と製品名を両方書く |
   | 主な利用部門・システムオーナー | |
   | 利用者数・年間費用 | サインインログ、支払明細から |
   | 契約形態 | 保守／ライセンス／SaaS／業務委託 |
   | GxP区分・ITGC対象 | CSV一覧、ITGC対象一覧から |
   | 出現した材料 | 支払／契約／SSO／CSV一覧／ITGC（どれに出たか） |
   | アプリ種類ID | フェーズ5で記入 |
   | 根拠 | 証跡ID |

6. **食い違いを確認する**：材料の一部にしか出てこないシステムは、担当者に確認する。
   - 支払はあるがSSOにない：使われていない、またはSSOを通さずに使われている。
   - SSOにあるが支払がない：無償、または事業部門が支払っている。
   - CSV一覧にあるが契約がない：保守切れ、または内製。

   Excelや共有フォルダで運用している台帳・管理表もシステムとして登録し、備考に「表計算」と書く。

完了条件：現状システムのすべての行に根拠があり、材料間の食い違いが解消しているか、理由が記録されている。

### フェーズ2 バリューストリーム

L1・L2は参照モデルのまま使います（IT4ITの4つ）。L3は参照の15件を確認し、L4を当社の実態に置き換えます。

1. **文書からL4の下書きを作る**：CSVのSOP、IT全般統制の規程・RCMから手順を抜き出し、参照のL4に対応付ける。一致するものは確認状態を「確認済み」にし、根拠に証跡IDを書く。
2. **ケースを追跡する**（文書がない部分）：直近の実例を1件選び、記録を最初から最後まで追う。

   | VS L2 | 追跡するケース | 追う記録 |
   |---|---|---|
   | S2P | 直近の予算編成で承認されたIT案件1件 | 起案資料 → 稟議 → 予算 → 投資判断 |
   | R2D | 直近に稼働したシステム（GxP・非GxPを1件ずつ） | 稟議 → 委託契約 → URS → 設計書 → テスト記録 → バリデーション報告書 → リリース判定 |
   | R2F | アカウント申請1件、PC・ソフトウェア申請1件 | 申請チケット → 承認 → 設定 → 通知 → 費用計上 |
   | D2C | インシデント1件、変更1件、GxPシステムの定期レビュー1件 | 検知 → チケット → 対応 → 変更記録 → 再発防止 |

   各ステップで次を記録する：何をしたか（L4名）、入力、出力、実施者、使ったシステム、承認者、根拠。
3. **面談で確認する**：担当者に下書きを見せ、抜け・順番・名前だけを確認してもらう。白紙から質問しない（面談の進め方は4章）。
4. **参照と突き合わせる**：参照のL4ごとに、確認状態を「確認済み／当社で追加／該当なし」のどれかにする。該当なしの行は削除せずに残す。

書き方のルール：

- L4は「目的語＋動詞」で、1人の担当者が一続きの作業で終えられる粒度にする。
- 入力・出力情報は、ファイル名や帳票名ではなく情報の名前で書く（例：「アカウント申請書.xlsx」ではなく「サービス要求」）。実際のファイル名は根拠に残す。
- 関連法令・規制は、根拠となる文書（SOP・ITGC規程）が求めているものを書く。

完了条件：すべてのL4に入力・出力・実施者・根拠があり、参照のL4のすべてに確認状態が付いている。

### フェーズ3 情報オブジェクト

1. フェーズ2のL4から入力・出力情報を全件抜き出し、名寄せする。同義語と状態の違いは1つにまとめる（例：申請中・承認済みのサービス要求 → サービス要求）。
2. 参照の50件に対応付ける。IDは参照のものを流用し、追加分は領域の接頭辞（MST・STR・DEV・GXP・SVC・OPS・SEC・SRC）で連番を振る。
3. 分類を付ける。
   - 領域、データ種別
   - 関連法令・規制：CSV対象システムで作成・保存される記録は「GxP」、IT全般統制の証跡は「金商法」、委託の発注・検収は「取適法」
   - 個人情報
4. オーナー（作成するケイパビリティL2）は、フェーズ4の後で確定する。

注意：情報オブジェクトの一覧を先に作ってVS側に当てはめない。VS L4の入力・出力情報が正本で、情報オブジェクトはそれを取りまとめたものです（README「設計ルール」）。

完了条件：L4の入力・出力情報のすべてが、いずれかの情報オブジェクトに対応している。

### フェーズ4 ケイパビリティ

フェーズ2と並行して進めます。

1. 参照のL3（70件）を一覧にし、組織図と分掌から担い手（社内部署／委託先／なし）の仮説を当てる。
2. L2ごとに担当者と30分面談し、L3ごとに次を確認する。
   - この仕事を当社で行っているか。
   - 誰が行っているか。委託先はどこか。
   - 何ができあがるか（成果物）。
3. 当社に固有の能力は追加する。★は参照と同じ基準で付ける（GxP、IT外部委託・取適法、IT全般統制に固有のもの）。担い手がいないL3も削除せず、担い手を「なし」とする。

注意：

- ケイパビリティの定義には、組織名・VS・システム名を書かない。担い手は定義ではなく「担い手（現状）」の列に書く。
- 組織図をそのままケイパビリティにしない。1つの部署が複数の能力を担うことも、1つの能力を複数の部署が担うこともある。

完了条件：すべてのL3に確認状態と担い手が入っている。

### フェーズ5 アプリケーション

1. 現状システムの各行に、アプリ種類ID（APP-01〜26）を付ける。1つのシステムが複数の種類を兼ねる場合は、すべて書く（例：ITSM製品で構成管理も行う → APP-09・APP-10）。
2. アプリ種類ごとに、対応する現状システムの数を集計する。
   - 0件：その機能を支えるシステムがない（手作業・表計算で行っているか、行っていない）
   - 1件：標準的な状態
   - 2件以上：同じ機能のシステムが重複している
3. 参照にない種類が出たら追加する（例：RPA、生成AI基盤）。
4. 種類はあってもシステムが0件の行は削除しない。

完了条件：現状システムのすべての行にアプリ種類IDがあり、アプリ種類ごとの件数が出ている。

### フェーズ6 関係

関係は推測で埋めず、フェーズ2で記録したL4の実施者・入力・出力・使用システムから起こします。

| シート | 作り方 | 根拠 |
|---|---|---|
| VS×ケイパビリティ関係 | L4ごとに、中核の作業を担うL3を「主」、下支えするL3を「支援」とする | フェーズ2の実施者、フェーズ4の担い手 |
| ケイパビリティ×情報オブジェクト | L4の出力を、そのL4で「主」のL2の「C」にする。入力は「R」にする | フェーズ2の入力・出力 |
| ケイパビリティ×アプリケーション | L4の使用システムのアプリ種類を、そのL4で「主」のL2に対応付ける。中核の業務で使うものは「●」、一部で使うものは「○」 | フェーズ2の使用システム、フェーズ5 |
| アプリケーション×情報オブジェクト | 参照モデルと同じく、ケイパビリティ経由で導く。複数のアプリで「C」になる情報は、実際にどのシステムで更新しているかを管理画面やインタフェースで確認し、備考に書く | 管理画面 |

VS×ケイパビリティのマトリクスは、関係シートから数式で集計されるので直接入力しません。

完了条件：関係の各行が、フェーズ2のいずれかのL4の記録にさかのぼれる。

### フェーズ7 ケイパビリティレベル

1. 評価の単位はL2（28件）。参照の成熟度の定義（共通定義と、L2ごとのレベル1〜5の記述）をそのまま使う。
2. 自己申告ではなく、証跡で判定する。

   | レベル | 判定に使う証跡 |
   |---|---|
   | 2 管理された | 案件・システムごとの計画と記録がある |
   | 3 定義された | 全社標準の手順があり、運用されている（IT全般統制の評価結果・監査で確認） |
   | 4 定量的に管理された | 指標を定期的に測定し、報告している |

3. 規制上の最低水準（★のL2の多くはレベル3）を下回るL2をはっきり示す。
4. 重要度（高・中・低）を付ける。判断材料は次の4つ。
   - 規制（GxP・J-SOXの対象か）
   - 年間費用（フェーズ1）
   - チケット件数（フェーズ1）
   - 利用者数（フェーズ1）

完了条件：すべてのL2に現状レベル・重要度・根拠がある。

### フェーズ8 検証と引き渡し

整合チェックの項目：

- 数式の列に「（IDなし）」が出ていない（IDの重複・参照切れがない）。
- すべてのL4に、入力・出力・実施者・根拠がある。
- すべての情報オブジェクトに「C」が1つ以上あり、オーナーのL2が「C」になっている。
- 確認状態が「参照（未確認）」の行が残っていない。
- 現状システムのすべての行にアプリ種類IDがある。
- すべてのケイパビリティL2に現状レベルがある。

参照モデルとの差分の集計（考察の主な材料になる）：

| 差分 | 意味 |
|---|---|
| VS L4・ケイパビリティL3の「該当なし」 | 当社で行っていない業務・能力 |
| 担い手が「なし」の能力 | 誰も責任を持っていない能力 |
| システムが0件のアプリ種類 | 手作業・表計算に頼っている機能 |
| システムが2件以上のアプリ種類 | 重複しているシステム |
| 実際に複数のシステムで更新される情報オブジェクト | 正本が決まっていないデータ |
| 規制上の最低水準を下回るL2 | 規制対応上の優先課題 |

最後に、`vs_capability_map_overview.pptx` の件数・図を当社版に合わせて更新します。

## 4. 面談の進め方

- 下書きを見せて直してもらう。白紙の質問はしない。
- 1回30分、ケイパビリティL2またはVS L3の単位で行う。
- 聞いた内容は、記録（チケット・承認・文書）で裏付けてから「確認済み」にする。裏付けがなければ根拠に「面談（日付・相手）」と書く。

| 対象 | 質問の例 |
|---|---|
| VS L4 | この順番で合っているか／抜けている作業はあるか／それぞれ誰が行い、何を受け取って何を渡すか／どのシステム・表計算を使うか／承認は誰か |
| ケイパビリティL3 | この仕事を当社で行っているか／誰が（どの委託先が）担っているか／成果物は何か／規程・手順書はあるか |
| レベル | 手順は全社で共通か、案件や委託先ごとに違うか／結果を指標で測っているか／直近の監査・評価で指摘はあったか |

## 5. よくある落とし穴

| 落とし穴 | 対策 |
|---|---|
| 組織図をそのままケイパビリティにする | 定義は「何ができるか」で書き、組織は担い手の列に書く |
| 「該当なし」の行を削除する | 残して確認状態で区別する。削除すると差分が見えなくなる |
| ファイル名や帳票名を情報オブジェクトにする | 情報の名前で書き、ファイル名は根拠に残す |
| 製品名でアプリを定義する | 種類で定義し、製品は現状システムのシートに書く |
| 面談で聞いただけで「確認済み」にする | 記録で裏付ける。裏付けがなければ根拠に面談と明記する |
| 最初から完璧を目指す | 「参照（未確認）」のままでも先に進めてよい。確認状態で区別し、フェーズ8で残りを潰す |
