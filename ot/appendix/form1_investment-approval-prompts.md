# 付録1　IT投資案件 承認ルーティング判定プロンプト集

> **種別**:記入して使う業務様式(プロンプト)
> **参照元**:`../chapters/03_decision-criteria.md`(判定ロジック)、`../chapters/04_operation.md`(運用フロー)

## 目的

生産本部のIT投資案件リスト(Excel:案件名・案件概要・概算費用・実施しない場合のリスク)に、承認ルート判定に必要な項目を追加するための2段階プロンプト。

- プロンプト1:既存4項目から、判定に必要な8項目を推定して追加する
- プロンプト2:生産ITによるレビュー・修正後のリストに、判定フローのロジックを適用して承認ルートを確定する

2つは続けて実行せず、プロンプト1の出力を生産ITメンバーと共有・精査したうえで、プロンプト2を実行する運用を想定している。

---

## プロンプト1:分類項目の推定追加

```
あなたは製造業のIT/OTガバナンスに詳しいアナリストです。以下のIT投資案件リストの各行について、
記載内容(案件名・案件概要・概算費用・実施しない場合のリスク)から、下記8つの追加項目を可能な
範囲で推定してください。

# 前提知識
- ERP: 国内はmcframe、海外拠点はMicrosoft Dynamics 365(D365)
- 生産管理システム(mcframe)はERPを中核とし、MESの一部機能(進捗管理・作業実績集計等)を
  カバーする場合があるが、品質管理・保全管理・設備連携・トレーサビリティ等は対象外のことが多い
- MES/SCADA/PLCの構成は拠点により異なり、標準化されていない可能性がある

# 追加すべき項目と選択肢

| 項目 | 選択肢 |
|---|---|
| 対象レイヤー(ISA-95) | ERP / MES(標準機能) / MES(工場固有) / SCADA・PLC / フィールド機器 / 複合 / 不明 |
| 全社影響範囲 | 単一工場限定 / 複数拠点 / 全社(海外含む) / 不明 |
| 全社システムとの接続有無 | 有 / 無 / 不明 |
| マスタデータへの影響 | 有 / 無 / 不明 |
| セキュリティ・ネットワーク影響 | 有 / 無 / 不明 |
| 継続コストの負担部門 | IT予算 / 生産本部予算 / 両方 / 不明 |
| 投資規模区分 | 概算費用から次の区分に分類: 〜100万円 / 100万〜1,000万円 / 1,000万〜1億円 / 1億円以上 / 不明(概算費用が未記載・TBDの場合) |
| 規制・安全要件 | 有 / 無 / 不明 |

# 判定ルール
- 記載内容から明確に読み取れない場合は、無理に「有」「無」等と断定せず「不明」を選んでください。
- 各項目の判定根拠を「推定根拠」列に1文で簡潔に記載してください。
- 判定の確からしさを「確信度」列に高/中/低で記載してください
  (記載内容から直接読み取れる場合は高、案件名・概要からの一般的な推測は中〜低)。
- 事実と推測を混同せず、あくまで人間(生産IT)がレビューする前提の"たたき台"として出力してください。

# 出力形式
- Markdownのテーブル形式で出力してください。
- 列の順序: 案件名 / 案件概要 / 概算費用 / 実施しない場合のリスク / 対象レイヤー(ISA-95) /
  全社影響範囲 / 全社システムとの接続有無 / マスタデータへの影響 / セキュリティ・ネットワーク影響 /
  継続コストの負担部門 / 投資規模区分 / 規制・安全要件 / 推定根拠 / 確信度
- 元のデータ(案件名・案件概要・概算費用・実施しない場合のリスク)は改変せずそのまま転記してください。
- 行の順序は入力データの順序を維持してください。

# 入力データ
(ここにExcelからコピーした案件リストを貼り付けてください。
案件名・案件概要・概算費用・実施しない場合のリスクの4列を想定)
```

## プロンプト2:承認ルートの判定

```
あなたは製造業のIT/OTガバナンスに詳しいアナリストです。以下は、生産ITメンバーがレビュー・修正
した、対象レイヤーや影響度などの項目が確定済みのIT投資案件リストです。この情報をもとに、下記の
判定フローに従って各案件の承認ルートを判定してください。

# 判定フロー
1. Q1(承認主体候補の決定)
   - 対象レイヤーが「ERP」または「MES(標準機能)」→ 承認主体候補 = IT部門
   - 対象レイヤーが「MES(工場固有)」「SCADA・PLC」「フィールド機器」→ 承認主体候補 = 生産本部
   - 対象レイヤーが「複合」または「不明」→ 承認ルート = 要協議(レイヤー未確定)。以降の判定は
     行わない。

2. Q2(影響度チェック)
   次のいずれかに該当する場合 → 承認ルート = 共同承認。ここで確定し、Q3・Q4は判定しない。
   - 全社影響範囲が「複数拠点」または「全社(海外含む)」
   - 全社システムとの接続有無が「有」
   - マスタデータへの影響が「有」
   共同承認の場合、承認主体候補が一次承認を行い、もう一方の部門が合議承認、その後最終決裁という
   順序とする。

3. Q2'(影響度が判定不能な場合)
   Q2の3項目に「有」該当がなく、かつ1つ以上が「不明」の場合
   → 承認ルート = 共同承認(判定材料不足)。ここで確定し、Q3・Q4は判定しない。

4. Q3(セキュリティゲート)
   Q2・Q2'に該当せず、セキュリティ・ネットワーク影響が「有」または「不明」の場合
   → 承認ルート = 承認主体候補の単独承認 + IT部門セキュリティ審査(着手前提。実質的にIT部門が先)

5. Q4(安全衛生ゲート)
   Q2〜Q3に該当せず、規制・安全要件が「有」または「不明」の場合
   → 承認ルート = 承認主体候補の単独承認 + 安全衛生部門等の関与

6. いずれにも該当しない場合 → 承認ルート = 承認主体候補の単独承認で完結

# 「不明」の扱いの原則
判定材料が「不明」の場合は、必ず保守側(重いルート)に倒す。軽いルートに倒して見落とすリスクを
避けるためである。判定理由欄には、どの項目が不明であったかを明記すること。

# 出力形式
- Markdownのテーブル形式で出力してください。
- 既存の列はすべて保持し、末尾に以下の2列を追加してください。
  - 承認ルート: 「IT部門単独」「生産本部単独」「共同承認(IT部門→生産本部)」
    「共同承認(生産本部→IT部門)」「共同承認(判定材料不足)」
    「生産本部単独+IT部門セキュリティ審査」「IT部門単独+IT部門セキュリティ審査」
    「生産本部単独+安全衛生部門関与」「要協議(レイヤー未確定)」等、判定結果に応じた
    具体的な表記としてください。
  - 判定理由: どのQで確定したか、根拠となった項目の値を1文で記載してください。
- 投資規模区分・継続コストの負担部門は、この判定ロジックには使用しません。既存の稟議規程で
  最終決裁者の階層を決めるための参考情報として、そのまま残してください。
- 行の順序は入力データの順序を維持してください。

# 入力データ
(ここに、プロンプト1の出力を生産ITが精査・修正した後のリストを貼り付けてください)
```
