# 付録1　IT投資案件 承認ルーティング判定プロンプト集

> **種別**:Excelファイルを添付して使う業務様式(プロンプト)
> **参照元**:`../chapters/03_decision-criteria.md`(判定ロジック)、`../chapters/04_operation.md`(運用フロー)

## 目的

生産本部のIT投資案件リスト(Excel)に、承認ルート判定に必要な項目を追加するための2段階プロンプト。

- プロンプト1:入力Excelの列を同定したうえで、判定に必要な8項目を推定して列を追加し、Excelで出力する
- プロンプト2:生産ITによるレビュー・修正後のExcelに、判定フローのロジックを適用して承認ルートを確定し、Excelで出力する

2つは続けて実行せず、プロンプト1の出力を生産ITメンバーと共有・精査したうえで、プロンプト2を実行する運用を想定している。

入力Excelの列名は案件ごとに異なる前提であり、プロンプト側で列の意味を同定する。入出力はいずれもExcelファイルで、元データは改変しない。

## プロンプト1:分類項目の推定追加

```
あなたは製造業のIT/OTガバナンスに詳しいアナリストです。添付のExcelファイル(IT投資案件リスト)を
読み込み、承認ルート判定に必要な8項目を推定して列を追加し、Excelファイルとして出力してください。

# 前提知識
- ERP: 国内はmcframe、海外拠点はMicrosoft Dynamics 365(D365)
- 生産管理システム(mcframe)はERPを中核とし、MESの一部機能(進捗管理・作業実績集計等)を
  カバーする場合があるが、品質管理・保全管理・設備連携・トレーサビリティ等は対象外のことが多い
- ISA-95のLevel3はMESだけでなく、品質(LIMS/QMS)・保全(CMMS/EAM)・在庫(WMS)の各システムを含む
- MES/SCADA/PLCの構成は拠点により異なり、標準化されていない可能性がある

# ステップ1:入力列の同定
=============================================================

入力Excelには、以下4つの意味を持つ列が含まれているはずだが、列名は異なる可能性が高い。
ヘッダ名と実際のセルの中身の両方を見て、どの列がどれに当たるかを同定すること。

| 求める意味 | 想定される列名の例 | 中身から見た同定の手がかり |
|---|---|---|
| 案件名 | 案件名 / 件名 / テーマ / 施策名 / プロジェクト名 / 名称 | 各行を識別する短いテキスト(概ね30字以内) |
| 案件概要 | 概要 / 内容 / 施策内容 / 説明 / 背景 / 目的 | 案件名より長い自由記述 |
| 概算費用 | 概算費用 / 予算 / 金額 / 投資額 / 費用 / コスト | 数値または金額表記。ヘッダやセル書式の単位(円/千円/百万円)も確認する |
| 実施しない場合のリスク | リスク / 未実施リスク / 課題 / 影響 / 実施しない場合の影響 | リスク・課題を述べた自由記述 |

- ヘッダ行が1行目にない場合(タイトル行や空行が上にある場合)は、実データの開始行を特定してから同定する。
- 該当する列が見つからない意味については「同定不可」とし、以降の推定でその情報は使わない。
- 同定結果は出力の前に必ず本文で報告すること(例:「案件名 ← B列『施策テーマ』」)。

# ステップ2:追加項目の推定
=============================================================

## 追加する8項目と選択肢

| 項目 | 選択肢 | 推測強度 |
|---|---|---|
| 対象レイヤー(ISA-95) | ERP / MES(標準機能) / MES(工場固有) / SCADA・PLC / フィールド機器 / 複合 / 不明 | 強 |
| 全社影響範囲 | 単一工場限定 / 複数拠点 / 全社(海外含む) / 不明 | 中 |
| 全社システムとの接続有無 | 有 / 無 / 不明 | 中 |
| マスタデータへの影響 | 有 / 無 / 不明 | 弱 |
| セキュリティ・ネットワーク影響 | 有 / 無 / 不明 | 中 |
| 規制・安全要件 | 有 / 無 / 不明 | 強 |
| 継続コストの負担部門 | IT予算 / 生産本部予算 / 両方 / 不明 | 弱 |
| 投資規模区分 | 〜100万円 / 100万〜1,000万円 / 1,000万〜1億円 / 1億円以上 / 不明 | 強 |

## 推測強度の意味

- **強**:思い切って推測してよい。手がかりが間接的でも、最も可能性の高い選択肢を選ぶ。
  「不明」とするのは手がかりが皆無の場合に限る。誤りは人間のレビューで容易に気づける項目であるため、
  「不明」を並べるより踏み込んだ方が有用である。
- **中**:相応の手がかりがあるときのみ推測する。下表に「どちらへ倒すか」の指示がある場合はそれに従う。
  手がかりが弱ければ「不明」とする。
- **弱**:偽陽性・偽陰性の双方を避けたい項目。記載から直接読み取れる場合のみ判定し、
  それ以外はすべて「不明」とする。ここで無理に推測してはならない。

## 項目別の推測方法

| 項目 | 強度 | 推測方法・判断キーワード | 「不明」とする条件 |
|---|---|---|---|
| 対象レイヤー(ISA-95) | 強 | 次のキーワードで機械的に対応付ける。**ERP**=mcframe / D365 / 基幹システム / 会計 / 購買 / 原価 / 受注 / 生産計画 / MRP。**MES(標準機能)**=MES標準機能 / パッケージ標準 / 標準機能の範囲。**MES(工場固有)**=個別開発 / スクラッチ / アドオン / カスタマイズ / 特定工場向けの実績収集や作業指示。**SCADA・PLC**=PLC / シーケンサ / SCADA / HMI / DCS / 監視盤 / 制御盤。**フィールド機器**=センサー / カメラ / ロボット / 計測器 / バーコードリーダ / IoTゲートウェイ。複数レイヤーの語が併存し主従が判断できない場合は「複合」 | 手がかりとなる語が一切ない場合のみ |
| 全社影響範囲 | 中 | 「全社」「グローバル」「海外」「全拠点」「標準化」「横展開」→ 全社(海外含む)。2つ以上の工場名・拠点名 → 複数拠点。単一の工場名・ライン名のみが明示 → 単一工場限定。**「広い側」の手がかりを優先する**(工場名があっても「標準展開」「他拠点にも適用」の語があれば複数拠点以上とする) | 工場名・拠点名の記載がなく、範囲を示す語もない場合 |
| 全社システムとの接続有無 | 中 | 「連携」「インターフェース」「I/F」「取込」「連動」「データ受渡し」が、ERP・基幹・全社ネットワーク・全社マスタと結びついていれば「有」。対象レイヤーがERPまたはMES(標準機能)であれば「有」寄りに判断する。対象レイヤーがSCADA・PLC/フィールド機器で、連携を示す語が一切ない場合は「無」 | 上記いずれにも当たらない場合 |
| マスタデータへの影響 | 弱 | 「コード体系」「マスタ」「品目登録」「採番」「統合」「名寄せ」「マスタ移行」が明示されていれば「有」。「既存マスタは変更しない」旨が明示されていれば「無」 | 上記の明示がない場合はすべて「不明」。案件概要から読み取れることは稀であり、推測してはならない |
| セキュリティ・ネットワーク影響 | 中 | 「クラウド」「SaaS」「リモート」「VPN」「外部接続」「インターネット」「無線」「Wi-Fi」「遠隔監視」「ベンダー保守接続」「データセンター」→ 有。外部と接続しない設備・機器の置換のみと読める場合は「無」 | 判断材料がない場合。**判定フローのQ3では「不明」も「有」と同様に扱われるため、根拠なく「無」としないこと** |
| 規制・安全要件 | 強 | 「安全」「労安」「労働安全衛生」「防爆」「消防」「法対応」「法改正」「環境」「排水」「排ガス」「騒音」「省エネ法」「GMP」「FDA」「トレーサビリティ義務」→ 有。「実施しない場合のリスク」に人身事故・法令違反・操業停止命令・行政処分の記載があれば「有」 | 上記の語が一切なく、リスク欄も業務効率・コスト・納期のみに言及している場合は「不明」ではなく「**無**」と判定してよい |
| 継続コストの負担部門 | 弱 | 負担部門・予算科目が明示されている場合のみ判定する | 上記の明示がない場合はすべて「不明」。組織の予算慣行に依存し、案件情報からは決まらない |
| 投資規模区分 | 強 | 概算費用の数値を円に換算して機械的に区分する。これは推測ではなく変換である。単位はヘッダの表記(千円/百万円)またはセル書式から判断し、判断した単位を推定根拠に明記する。範囲表記(例:500〜800万円)は上限値で区分する | 概算費用列が同定できない、または値が空欄・TBD・「−」等の場合のみ |

## 全体の原則

- 事実と推測を混同しない。本出力はあくまで人間(生産IT)がレビューする前提の"たたき台"である。
- 強度「弱」の項目で「不明」が多くなるのは設計どおりであり、無理に埋めない。
- 強度「強」の項目で「不明」を多用しない。手がかりが薄くても最有力の選択肢を選ぶ。
- 元データの値は絶対に書き換えない。

## Excelファイルの要件

- 入力ファイルの既存シート・既存列・既存行を一切改変しない(値・順序・書式のすべて)。
- 追加列のヘッダは太字とし、背景色を既存列と変えて区別できるようにする。
- ヘッダ行でウィンドウ枠を固定する。追加列は折り返し表示とし、列幅を内容に合わせて調整する。
- 値が「不明」のセルは背景を薄いグレーにし、目視で拾えるようにする。
- 出力ファイル名は、入力ファイル名の拡張子直前に `_分類済` を付したものとする。

## 本文で報告する内容(3〜6行程度)

1. ステップ1の列同定結果(どの列をどの意味に割り当てたか。同定不可の列があればその旨)
2. 概算費用の単位をどう判断したか
3. 「不明」が多く出た項目とその理由(データ側の記載不足か、強度設定によるものか)

表そのものを本文に再掲する必要はない。Excelファイルを出力すること。
```

## プロンプト2:承認ルートの判定

```
あなたは製造業のIT/OTガバナンスに詳しいアナリストです。添付のExcelファイルは、生産ITメンバーが
レビュー・修正した、対象レイヤーや影響度などの項目が確定済みのIT投資案件リストです。
下記の判定フローに従って各案件の承認ルートを判定し、Excelファイルとして出力してください。

# ステップ1:入力列の確認
判定に使う次の6列がヘッダ名で存在することを確認する。
対象レイヤー(ISA-95) / 全社影響範囲 / 全社システムとの接続有無 / マスタデータへの影響 /
セキュリティ・ネットワーク影響 / 規制・安全要件

- 列名が完全一致しない場合は、意味が一致する列を同定して用い、その対応付けを本文で報告する。
- 上記6列のうち1つでも同定できない場合は、判定を行わず、どの列が見つからなかったかを報告して終了する。
- 選択肢外の値(表記ゆれ・空欄)が入っているセルは「不明」として扱い、該当する行と列を報告する。

# ステップ2:判定フロー
1. Q1(承認主体候補の決定)
   - 対象レイヤーが「ERP」または「MES(標準機能)」→ 承認主体候補 = IT部門
   - 対象レイヤーが「MES(工場固有)」「SCADA・PLC」「フィールド機器」→ 承認主体候補 = 生産本部
   - 対象レイヤーが「複合」または「不明」→ 承認ルート = 要協議(レイヤー未確定)。以降の判定は
     行わない。

2. Q2(影響度チェック)
   次のいずれかに該当する場合 → 承認ルート = 共同承認。ここで確定し、Q3・Q4は判定しない。
   - 全社影響範囲が「複数拠点」または「全社(海外含む)」
   - 全社システムとの接続有無が「有」
   - マスタデータへの影響が「有」
   共同承認の場合、承認主体候補が一次承認を行い、もう一方の部門が合議承認、その後最終決裁という
   順序とする。

3. Q2'(影響度が判定不能な場合)
   Q2の3項目に「有」該当がなく、かつ1つ以上が「不明」の場合
   → 承認ルート = 共同承認(判定材料不足)。ここで確定し、Q3・Q4は判定しない。

4. Q3(セキュリティゲート)
   Q2・Q2'に該当せず、セキュリティ・ネットワーク影響が「有」または「不明」の場合
   → 承認ルート = 承認主体候補の単独承認 + IT部門セキュリティ審査(着手前提。実質的にIT部門が先)

5. Q4(安全衛生ゲート)
   Q2〜Q3に該当せず、規制・安全要件が「有」または「不明」の場合
   → 承認ルート = 承認主体候補の単独承認 + 安全衛生部門等の関与

6. いずれにも該当しない場合 → 承認ルート = 承認主体候補の単独承認で完結

# 「不明」の扱いの原則
判定材料が「不明」の場合は、必ず保守側(重いルート)に倒す。軽いルートに倒して見落とすリスクを
避けるためである。判定理由欄には、どの項目が不明であったかを明記すること。

# ステップ3:Excelでの出力

## 追加する列(元データの最終列の右隣から、この順序で)
1. 承認ルート … 次のいずれかの表記を用いる。
   「IT部門単独」「生産本部単独」「共同承認(IT部門→生産本部)」「共同承認(生産本部→IT部門)」
   「共同承認(判定材料不足)」「IT部門単独+IT部門セキュリティ審査」
   「生産本部単独+IT部門セキュリティ審査」「IT部門単独+安全衛生部門関与」
   「生産本部単独+安全衛生部門関与」「要協議(レイヤー未確定)」
2. 判定理由 … どのQで確定したか、および根拠となった項目名とその値を1文で記載する
   (例:「Q2: 全社システムとの接続有無=有 のため共同承認」)

## Excelファイルの要件
- 入力ファイルの既存シート・既存列・既存行を一切改変しない(値・順序・書式のすべて)。
- 「承認ルート」列は値に応じてセル背景色を分ける。共同承認系=オレンジ系、単独承認系=青系、
  要協議=グレー系。追加ゲート付き(セキュリティ審査/安全衛生部門関与)は太字にする。
- ヘッダ行でウィンドウ枠を固定し、追加列は折り返し表示・列幅を内容に合わせて調整する。
- 出力ファイル名は、入力ファイル名の拡張子直前に `_判定済` を付したものとする。

## 本文で報告する内容
- 承認ルート別の件数(集計表)
- Q2'(判定材料不足)および要協議となった案件の件数と案件名。これらは項目を確定させたうえで
  再判定すればルートが軽くなる可能性がある旨を添える
- 投資規模区分・継続コストの負担部門は、この判定ロジックには使用していない旨(既存の稟議規程で
  最終決裁者の階層を決めるための参考情報として、列はそのまま残すこと)
```
