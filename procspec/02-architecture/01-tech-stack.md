## 3. 中核となる設計原則

### 原則1: スキーマ単一ソース

**Zodスキーマを1つ定義し、フロント検証とAPI検証で共有する** `[資料]`（助言 §3-2）。

- **要求すること**: 型・検証の定義は `packages/schema` にのみ置く。フロント（React Hook Form）とAPI（`ZodValidationPipe`）は同じスキーマを参照する。
- **禁止すること**: フロントとAPIで検証ロジックを二重に書くこと。
- **例外**: なし。

→ [ADR-0002](./05-adr/0002-schema-single-source.md)。実装で守られている `[実装]`。

### 原則2: スキーマ駆動レンダリング

**セクション/項目定義をコードで一元管理し、UIがそれを解釈して描画する** `[資料]`（助言 §3-2）。

- **要求すること**: 様式の項目・分岐はUIコンポーネントに埋め込まず、`STEP_DEFS`／`STEP_RULES`／`CONTRACT_TYPES` の定義に寄せる。
- **狙い**: 様式の改訂（項目追加・条項変更）を**コード改修なしに定義変更で**回せるようにする `[資料]`。
- **将来**: DB／管理画面からの読込に置換可能な形を維持する（プランBのテンプレ管理画面）`[資料]`。

> **現状は原則が部分的にしか守られていない** `[実装]`。ステップの**順序と表示**は定義駆動だが、**各ステップの入力フォームはコンポーネントにハードコードされている**（`Step0Fields`／`Step4Fields`／`StepSlaFields` 等が個別実装）。
> つまり「セクションを増やす」には**コンポーネントの追加実装が必要**であり、助言が意図した「定義追加のみ」には達していない。
> → 拡張時の実際のコストは [拡張性への配慮 §4](./04-extensibility.md) を参照。**ここを誤解すると、プランBのセクション追加工数を過小評価する。**

### 原則3: サービス層分離（AI差し込みの受け口）

**ドラフト取得/更新の処理を service 層に分離し、controller に直書きしない** `[資料]`（助言 §5-2、開発方針 §6）。

- **要求すること**: NestJS の controller は入出力の変換のみ。ビジネスロジック・トランザクション境界は service に置く。
- **狙い**: プランCで AIオーケストレーション（下書き生成・RAG検索）を差し込む際、controller を触らずに済むようにする `[資料]`。

実装で守られている `[実装]`（`CasesService` / `DraftsService` / `AuditService`）。

## 4. 環境ごとの構成差分

| 項目 | 開発 | ステージング | 本番 | 切替方法 |
|---|---|---|---|---|
| DB | SQLite（`file:./dev.db`） | **未定** | PostgreSQL | `schema.prisma` の provider ＋ `DATABASE_URL` `[実装]` |
| 回答本体 `data` | `String`（JSON文字列） | 未定 | `Json`（jsonb） | Prisma の型変更＋マイグレーション `[実装]` |
| 認証 | `x-user-email` ヘッダ | 未定 | OIDC/SSO | `DevAuthGuard` の差し替え `[実装]` |
| CORS | `origin: true` | 未定 | 許可オリジン限定 | `main.ts` `[実装]` |
| ファイルストレージ | 未導入 | 未定 | S3互換 | — |

> **ステージング環境が存在しない** `[実装]`。WBS 1.1「開発基盤・CI/CD・環境構築」（14人日）が未着手 `[資料]`。

**差分によるリスク** `[推定]`

| 差分 | 開発中に検出できないこと |
|---|---|
| SQLite ↔ PostgreSQL | JSON型の扱い、トランザクション分離レベル、同時実行時の挙動、生成列・ビューの動作 |
| 仮認証 ↔ OIDC | トークン検証、セッション管理、ロールのクレーム取得 |
| CORS 全許可 ↔ 限定 | プリフライト・クレデンシャル送信の問題 |

→ **これらは本番移行時にまとめて顕在化する。** ステージング環境の早期整備が [バックログ](../06-roadmap/02-backlog.md) の上位項目である理由。
