# ADR-0006: ORM に Prisma を選ぶ

- **ステータス**: 承認
- **決定日**: 不明 `[未確認]`
- **決定者**: **不明** `[未確認]`
- **復元の確度**: ❌ **復元できず**
- **関連**: [技術スタック §2](../01-tech-stack.md)、[データモデル §9](../02-data-model.md)

## 背景（Context）

助言 §3-3 は ORM について **「Prisma または Drizzle。マイグレーション管理必須」** とのみ述べ、**どちらを推奨するかを示していない** `[資料]`。開発方針 §3 も同じ文言を繰り返している `[資料]`。

つまり、**この選択はプロジェクト側に委ねられていた。**

## 検討した選択肢（Options）

> **⚠️ 実際に比較検討された記録は無い。** 以下は一般的な比較として補ったもの `[推定]`。

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| **A. Prisma** | スキーマ定義言語 → クライアント生成 | 宣言的スキーマが読みやすい。マイグレーション・Studio が揃う。**provider 切替でDB変更が容易** | 生成ステップが必要。複雑なクエリで型が効きにくい |
| B. Drizzle | TypeScript でスキーマを定義 | SQL に近く軽量。生成ステップ不要 | エコシステムが Prisma より小さい |
| C. TypeORM 等 | NestJS との親和性 | NestJS 公式ドキュメントの例が豊富 | 助言が挙げていない |

## 決定（Decision）

**選択肢A（Prisma）が採用されている。** `@prisma/client@^6`、`prisma/schema.prisma`、Prisma Migrate。

## 理由（Rationale）

> ### ❌ **意図は復元できなかった。**
>
> 助言は両論併記であり、**選定の根拠となる記述が一次資料に存在しない。** コードコメントにも理由の記載は無い `[実装]`。
>
> 結果から推測される理由 `[推定]`:
>
> - `schema.prisma` の provider 切替により、**SQLite → PostgreSQL の移行が容易に見えた**（→ [ADR-0004](./0004-sqlite-for-development.md) と整合する）
> - 宣言的なスキーマファイルが、後追いでの構造把握に有利（実際、本ドキュメントの [データモデル](../02-data-model.md) は `schema.prisma` から直接起こせた）
> - 採用実績・情報量が多い
>
> **いずれも推測。** 実装者に確認できれば確度が上がる。

## 影響（Consequences）

**受け入れているトレードオフ** `[推定]`

- スキーマ変更のたびにクライアント生成が必要（開発フローに組み込まれている `[実装]`）
- 複雑な集計クエリでは生SQLに落とす必要がある。**[ADR-0001](./0001-jsonb-hybrid-data-model.md) が想定する「生成列/ビューでの抽出」を Prisma でどう扱うかは未検証**

**実装での状況** `[実装]`

| 項目 | 状態 |
|---|---|
| スキーマ定義 | `apps/api/prisma/schema.prisma` に一元化 ✅ |
| マイグレーション | `20260724123008_init` の1件のみ |
| トランザクション | `$transaction` を使用（`DraftsService.patch`）✅ |
| シード | `prisma/seed.ts` |
| **命名規則・運用ルール** | **未定義** `[未確認]` |

**この決定が前提になる後続作業**

- PostgreSQL 移行時、`Json` 型への変更と生成列の扱いを Prisma でどう実現するか検証する（→ [ADR-0004](./0004-sqlite-for-development.md)）
- マイグレーションの命名規則・本番適用手順・ロールバック方針を定める（→ [データモデル §9](../02-data-model.md)）

**見直す条件（トリガ）**

> **本決定は理由の記録が無いが、変更コストは高い。** 「理由が無い＝変えてよい」と「変えるのが安い」は別問題である。

- **積極的に変更する理由は無い。** 現状で問題が観測されていない
- ただし以下の場合は再評価してよい:
  - jsonb の高度なクエリ（生成列・GINインデックス・部分更新）が Prisma で扱いにくいと判明した場合
  - Prisma のクライアント生成が CI/開発フローのボトルネックになった場合
- **移行するなら早いほどよい。** マイグレーション履歴が積み上がるほどコストが上がる
