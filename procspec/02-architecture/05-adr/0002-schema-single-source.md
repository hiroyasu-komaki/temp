# ADR-0002: Zodスキーマをフロント/APIの単一ソースにする

- **ステータス**: 承認
- **決定日**: 不明 `[未確認]`
- **決定者**: **不明** `[未確認]`
- **復元の確度**: ✅ **資料あり**
- **関連**: [技術スタック §3](../01-tech-stack.md)、設計助言 §3-2

## 背景（Context）

様式2 は項目数が多く、契約類型による分岐もある。回答本体を JSON で保持する（→ [ADR-0001](./0001-jsonb-hybrid-data-model.md)）ため、**DBレベルの型保証が効かない。** 検証をどこで担保するかを決める必要があった。

一般的な構成では、フロントの入力検証とAPIの受信検証を別々に書く。この場合、片方だけ更新されて**検証がずれる**という不具合が生じやすい。 `[資料]`（助言 §3-2）

## 検討した選択肢（Options）

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| A. フロント・APIで別々に検証を書く | 各層で独立に実装 | 各層の都合に最適化できる | **定義がずれる。** 項目追加時に二重作業 |
| **B. Zodスキーマを共有パッケージに置き両層で使う** | `packages/schema` を単一ソースに | 型と検証がずれない。項目追加が1箇所 | 共有パッケージのビルドが必要。層の結合度が上がる |
| C. OpenAPI からコード生成 | 契約定義から型を生成 | 言語非依存。ドキュメントが正 | 生成の仕組みが必要。Zodほど柔軟な検証は書けない |

> 選択肢Cは助言が「OpenAPIで契約を先に定義」を推奨している `[資料]` ことから、比較対象として補った `[推定]`。**実際に比較検討された記録は無い。**

## 決定（Decision）

**選択肢B を採用する。** `packages/schema` に Zod スキーマを定義し、フロント（React Hook Form + `@hookform/resolvers`）と API（`ZodValidationPipe`）が同じスキーマを参照する。

## 理由（Rationale）

`[資料]` 助言 §3-2 が明示している:

> Zodスキーマを1つ定義し、**フロントの検証とバックの検証を同一スキーマから共有**する（`zod` を API 側でも利用）。項目数が多いこのフォームでは、スキーマ駆動で「フィールド定義→レンダリング→検証→保存」を統一するのが保守性の鍵。

[ADR-0001](./0001-jsonb-hybrid-data-model.md) で DB の型保証を手放しているため、**アプリ層のスキーマが唯一の防波堤になる。** 二重定義は許容できない。

## 影響（Consequences）

**受け入れるトレードオフ**

- `packages/schema` を変更したら**再ビルドが必要**（`npm run build:schema`）。忘れると古い定義を参照する `[実装]`
- フロントとAPIが同じ型定義に結合する。片方だけ別の検証をしたい場合に工夫が要る

**実装での状況** `[実装]`

| 項目 | 状態 |
|---|---|
| `CaseAnswerDataSchema` を両層で使用 | ✅ 守られている |
| `CreateCaseSchema` / `DraftPatchSchema` | ✅ 同上 |
| `ZodValidationPipe` で全エンドポイント検証 | ✅ 守られている |
| React Hook Form での使用 | ◐ **一部は素の `useState` で実装されている** |

> **フロント側で React Hook Form が全面的には使われていない** `[実装]`。`setField` による直接的な state 更新が主体。
> このため**フロント側のリアルタイム検証が実質機能していない**（型は効くが、Zod の検証ルールが入力時に走らない）。
> 意図的な簡略化か実装漏れかは不明 `[未確認]`。→ [検証・エラー設計](../../03-detail-design/04-validation-and-errors.md)

**副作用: 検証の緩さ**

`CaseAnswerDataSchema` は autosave で部分入力を許すため**全項目 optional** `[実装]`。これは正しい判断だが、**「提出時の厳しい検証」を別スキーマとして用意する必要がある。** 現在それが存在しない。

→ 提出フロー実装時に `CaseAnswerSubmitSchema` 等を追加すべき `[推定]`。[バックログ](../../06-roadmap/02-backlog.md)

**この決定が前提になる後続作業**

- 提出時検証スキーマの追加
- OpenAPI 定義の作成時、Zod スキーマから生成することを検討する（二重管理を避けるため）`[推定]`

**見直す条件（トリガ）**

- フロントとAPIで別言語・別チームになった場合、選択肢C（OpenAPI 起点）へ移行を検討する
- **本決定は現時点で見直す理由が無い。** 資料・実装とも一貫している
