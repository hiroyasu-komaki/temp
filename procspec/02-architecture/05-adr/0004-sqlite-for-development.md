# ADR-0004: 開発DBに SQLite を使う

- **ステータス**: 承認（**要再検討**）
- **決定日**: 不明 `[未確認]`
- **決定者**: **不明** `[未確認]`
- **復元の確度**: ❌ **復元できず**
- **関連**: [データモデル §6](../02-data-model.md)、[技術スタック §4](../01-tech-stack.md)

## 背景（Context）

設計助言 §3-1・§4 は本番DBとして **PostgreSQL（回答本体は jsonb）** を明示している `[資料]`。
一方、実装は開発用に **SQLite** を採用し、`schema.prisma` の provider 切替と `DATABASE_URL` 差し替えで PostgreSQL へ移行できる形にしている `[実装]`。

見積書の前提条件に「クラウド環境・CI/CD等の基盤が調達済みまたは並行調達可能なこと」とあり `[資料]`、**実装着手時点でこれらが揃っていなかった可能性が高い** `[推定]`。

## 検討した選択肢（Options）

> **⚠️ 以下は後追いで構成した選択肢であり、実際に比較検討された記録は無い。** `[推定]`

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| A. 開発も PostgreSQL | 各自ローカルに立てる（Docker 等） | 環境差分ゼロ。移行リスクなし | 初回セットアップの負担 |
| **B. 開発は SQLite、本番は PostgreSQL** | Prisma の provider 切替 | ゼロセットアップ | **環境差分。DB固有機能を検証できない** |
| C. 共有の開発用DBサーバ | チーム共通インスタンス | 本番同等かつ各自の負担なし | 環境払い出し待ち。相互干渉 |

## 決定（Decision）

**選択肢B が採用されている。** 開発は SQLite（`file:./dev.db`）、本番は PostgreSQL(jsonb) を前提とする。

## 理由（Rationale）

> ### ❌ **意図は復元できなかった。**
>
> 一次資料に該当する記述はなく、コードコメントも「開発用: SQLite（ゼロセットアップ）」と**結果を述べるのみで理由の記載がない** `[実装]`。関係者への確認も未実施。
>
> 実装当時の状況から推測される理由 `[推定]`:
>
> - クラウド環境・CI/CD基盤が未払い出しで、共有DBを用意できなかった（見積書の前提条件が未充足）
> - MVP を短期で動かすことが優先され、環境構築の手間を避けた
> - Prisma が provider 切替を提供しており、移行が容易に見えた
>
> **いずれも推測。** 実装者に確認できれば確度が上がる。→ [decision-log](../../_templates/decision-log.md)

## 影響（Consequences）

**受け入れているトレードオフ** `[推定]`

| 差分 | 開発中に検出できないこと |
|---|---|
| JSON の扱い（`String` vs `jsonb`） | jsonb 演算子・インデックス・生成列の動作。**[ADR-0001](./0001-jsonb-hybrid-data-model.md) が想定する「生成列/ビューでの抽出」が一切検証されていない** |
| トランザクション分離レベル | 同時実行時の挙動。**楽観ロック（[ADR-0003](./0003-optimistic-lock-append-version.md)）の競合検知が本番で同じに動く保証がない** |
| 型・制約の厳密さ | SQLite は型が緩い。PostgreSQL で制約違反になるデータが通ってしまう |
| 同時接続 | SQLite は書き込みが直列化される。**性能特性が全く異なる** |

**移行に必要な作業** `[実装]`

1. `schema.prisma` の provider を `postgresql` に変更
2. `CaseAnswer.data` を `String` → `Json` に変更
3. **アプリ側の `JSON.parse`/`JSON.stringify` を全て除去**（`CasesService.toDto`、`DraftsService.patch` に散在）
4. `DATABASE_URL` を差し替え、マイグレーションを作り直す
5. 既存データがあれば移行

> **3 が見落とされやすい。** `schema.prisma` のコメントは 1・4 のみ言及しており、アプリ側の改修に触れていない `[実装]`。
> **移行手順書は存在しない。** → [バックログ](../../06-roadmap/02-backlog.md)

**この決定が前提になる後続作業**

- ステージング環境（PostgreSQL）の整備 — **これが無い限り、差分に起因する不具合は本番で初めて出る**
- CI での PostgreSQL に対するテスト実行（テスト自体が未整備）

**見直す条件（トリガ）**

> **本決定は理由の記録が無いため、変更の障害と見なさない。** 以下のいずれかを満たす場合、選択肢A または C へ移行してよい。

- **クラウド環境が払い出された時点**（選択肢C が実行可能になる）
- **[ADR-0001](./0001-jsonb-hybrid-data-model.md) の「生成列/ビューでの抽出」を実装する時点** — SQLite では検証できないため、この機能に着手するなら先にDBを揃えるべき
- **性能検証（WBS 3.7）に着手する時点** — SQLite では性能特性が全く異なり、測定に意味がない
- 開発者が Docker で PostgreSQL を立てる負担を許容できるなら、**今すぐ選択肢A へ移行してよい**

**推奨** `[推定]`: 上記のうち最も早く到来するのは「性能検証」または「ステージング整備」。**どちらも本番リリース前に必須**であり、その時点で移行が発生する。
**移行を後ろに倒すほど、SQLite 前提のコードが増えてコストが上がる。** 早期の移行を推奨する。
