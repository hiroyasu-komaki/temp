# ADR（Architecture Decision Records）

> **本ADR群は後追いで復元したもの。** procspec は先に実装され、設計判断の記録は一切残っていなかった。
> 各ADRの「理由」は、一次資料・コードコメント・実装の状況から復元している。**復元できなかったものは「復元できなかった」と明記している。**

---

## 復元の確度

| 確度 | 意味 | 扱い |
|---|---|---|
| ✅ **資料あり** | 一次資料またはコードコメントに理由が明記されている | 設計判断として尊重する |
| ◐ **部分的** | 大枠の理由は資料にあるが、具体値・細部の根拠が不明 | 不明部分は変更してよい |
| ❌ **復元できず** | 理由の記録が一切ない | **変更の障害と見なさない。合意なしで再検討してよい** |

## 「❌ 復元できず」のADRの扱い

**これらは失敗の記録ではなく、成果物である。** 理由が残っていないという事実が記録されていることで、次の開発者は「触ってよい箇所」を知ることができる。

- **合意を取り直す必要はない。** 元の合意が存在しないため。
- **各ADRの「見直す条件」を確認する。** 条件を満たしていれば、改めて選択肢を評価してよい。
- ただし**変更コストは別問題**。理由が無いことと、変えるのが安いことは違う。

特に **[ADR-0007](./0007-hardcoded-step-components.md) は要再検討**。設計原則（スキーマ駆動レンダリング）と実装が食い違っており、**プランB/Cのセクション追加工数に直接影響する。**
