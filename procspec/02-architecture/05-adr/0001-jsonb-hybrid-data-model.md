# ADR-0001: 回答本体をJSONで保持するハイブリッド構成

- **ステータス**: 承認
- **決定日**: 不明（実装時期は2026-07-24 前後 `[実装]`）
- **決定者**: **不明** `[未確認]`
- **復元の確度**: ✅ **資料あり**
- **関連**: [データモデル](../02-data-model.md)、設計助言 §4

## 背景（Context）

様式2 調達仕様書は多数のセクション・項目からなり、**様式の改訂が想定される** `[資料]`。また契約類型によって記入項目が変わる。

これらをすべてリレーショナルな列として展開すると、様式改訂やプランB/Cでの項目追加のたびにマイグレーションが必要になる。一方、すべてを非構造化データにすると、一覧の検索・絞り込み・集計ができない。 `[資料]`（助言 §4）

## 検討した選択肢（Options）

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| A. 全項目を列に展開 | 各セクションの項目を専用列に | 検索・集計が自然。型が効く | 様式改訂ごとにマイグレーション。項目数が多く列が肥大 |
| B. 全体をJSONで保持 | 案件テーブルにJSONを1列 | 改訂に完全に強い | 検索・集計・一覧表示ができない |
| **C. ハイブリッド** | メタは列、回答本体はJSON | 改訂に強く、必要な検索性は確保 | 二重管理の同期が必要 |

> 選択肢A・Bは助言に明示されていない。**ハイブリッドが「正規化と柔軟性のバランス」として推奨されており** `[資料]`、対比としてA・Bを補って記載した `[推定]`。

## 決定（Decision）

**選択肢C を採用する。** `cases` に案件・提出のメタを列で正規化し、回答本体は `case_answers.data` に JSON で保持する。

## 理由（Rationale）

`[資料]` 助言 §4 が明示している:

- 回答をJSONにすることで、様式のセクション構成を**フロント/APIのスキーマ定義と一致させられる**（→ [ADR-0002](./0002-schema-single-source.md)）
- 様式改訂やプランB/Cでの項目追加を**マイグレーション不要**で吸収できる
- 集計・検索が必要な項目（予算合計・類型・稼働率など）は、**生成列やビューで後から抜き出せる**

## 影響（Consequences）

**受け入れるトレードオフ**

- JSON 内の項目は DB レベルで型チェックされない。**アプリ側のスキーマ検証が唯一の防波堤**になる（→ ADR-0002 が前提）
- 検索・集計が必要になった項目は、その都度 生成列/ビューへの抽出作業が発生する
- **一部の値が二重に保持される** `[実装]`。`title`/`period`/`primary` は JSON と `cases` 列の両方にあり、`DraftsService.patch` の中で同期している

**実装での逸脱**

| 項目 | 助言 | 実装 | 出所 |
|---|---|---|---|
| 開発DBの型 | `jsonb` | **SQLite の `String`**（JSON文字列） | `[実装]` → [ADR-0004](./0004-sqlite-for-development.md) |
| `evaluations` テーブル | 独立テーブル（`locked` 列付き） | **作らず `data.eval` に内包** | `[実装]` |
| `clauses` テーブル | 独立テーブル | **未実装** | `[実装]` |
| `secondary_types` | `cases` の `text[]` 列 | **未実装** | `[実装]` |

> **`evaluations` を独立テーブルにしなかった理由は不明** `[未確認]`。
> 助言は `locked` 列による凍結制御を想定しており、**凍結がプランB以降だからJSONに内包した**という判断は筋が通る `[推定]`。
> ただし**プランBで凍結制御を実装する際、`data.eval` から `evaluations` テーブルへのデータ移行が必要になる。** この移行コストは見積WBS 2.7「凍結制御」12人日に含まれているか不明 `[未確認]`。

**この決定が前提になる後続作業**

- [ADR-0002](./0002-schema-single-source.md)（スキーマ単一ソース）— JSON の中身を保証する唯一の手段
- 生成列/ビューの設計（本番PostgreSQL移行時）
- プランBの凍結制御実装時の `evaluations` 移行

**見直す条件（トリガ）**

- 回答本体の項目を横断的に集計・検索する要件が常態化した場合、主要項目の列への抽出を検討する
- **プランBの凍結制御着手時**、`data.eval` を独立テーブルへ移すか、JSON のまま凍結を実装するかを改めて判断する（この判断は先送りされている）
- `cases` への非正規化コピーが3項目を超えたら、同期の仕組みを見直す `[推定]`
