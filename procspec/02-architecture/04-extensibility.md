# 拡張性への配慮

- **出典**: 設計助言 §6 `[資料]` / 開発方針 §6 `[資料]` / 実装の棚卸し `[実装]`
- **最終更新**: 2026-07-25

> **本ファイルが、本ドキュメント群の中核成果物である。**
> 後追い文書化の目的は「拡張準備」であり、その問いは **「次の機能追加は、どこを触れば済むのか」**。
>
> 後追いで書く強みは、**「拡張を阻害している箇所」を予測ではなく事実として書けること**（→ §4）。新規開発時の同名ドキュメントとの最大の違いはここにある。

---

## 1. 基本方針

プランAは「まず作って終わり」ではなく、**B/Cへの土台** `[資料]`（開発方針 §6）。Aの実装がB/Cの追加実装を阻害しないことを、あらゆる設計判断の基準にする。

**ただし過剰設計はしない。** 「今は作らないが、後で足すときに手戻りしない形」を選ぶに留める。

## 3. 確保済みの拡張ポイント（詳細）

### 3-1. `Attachment` の先取り列 ✅ 意図が明確

```
scanStatus         String?  // pending|clean|infected
provisionCondition String?  // unconditional|nda_required
```

**コードコメントに「B/C向けの拡張列（Aでは未使用。§6 拡張性への配慮に基づき先取りして確保）」と明記されている** `[実装]`。

> **本プロジェクトで唯一、先取りの意図がコードに残っている箇所。** 他の未使用要素の判断に迷ったとき、この書き方を基準にするとよい。
> **理由が書かれていない未使用列は、いずれ「使われていない」として削除される。**

**Bでの使い方**: ウイルススキャン結果の保持と、NDA締結状況に応じたダウンロード制御 `[資料]`（助言 §3-5）。

⚠️ **ただし添付機能そのものが未実装** `[実装]`。列だけあってテーブルは空。プランAスコープ内の未実装項目（WBS 2.3・12人日）。

### 3-2. `User.role` と `CaseStatus`

```
UserRole:   creator | dept_head | vmo | viewer
CaseStatus: draft | submitted | vmo_review | approved | returned
```

いずれも助言 §3-4 のロール定義・ワークフロー定義に対応する `[資料]`。**値の定義は済んでいるため、遷移とロール判定を足すだけで機能する** `[推定]`。

⚠️ **ロール定義と状態定義が対応していない** `[実装]`:
`dept_head`（所属長承認）に相当する状態が `CaseStatus` に無い。所属長承認が業務フローのどこに入るか不明 `[未確認]`。
→ [状態遷移設計](../03-detail-design/03-state-transitions.md)、[ロールと権限 §1](../01-requirements/05-roles-and-permissions.md)

### 3-3. サービス層の分離 ✅

`CasesService` / `DraftsService` / `AuditService` にロジックが置かれ、controller は薄い `[実装]`。
助言 §5-2 の「API側にAI層を置き、LLM呼び出し・RAG検索・出力整形・ガードレールを担う」`[資料]` を差し込む余地がある。

**Cでの使い方**: `DraftsService` の前後にAI処理を挟む／並列サービスとして `AiDraftService` を追加する `[推定]`。

### 3-4. 定義の外出し（類型・ステップ順序）✅

`CONTRACT_TYPES` / `STEP_RULES` / `STEP_DEFS` はコード内定数として外出しされている `[実装]`。

| 拡張作業 | 必要な作業 |
|---|---|
| 契約類型を追加する | `CONTRACT_TYPES` に1行追加。**主分類が既存（A/B/C/D/G）なら完全に定義追加のみ** ✅ |
| 主分類を新設する | `CONTRACT_TYPES` ＋ `STEP_RULES` に追加。定義追加のみ ✅ |
| 分岐ルールを変更する | `STEP_RULES` の配列を編集。定義追加のみ ✅ |
| **セクションを追加する** | **→ §4-1。定義追加では済まない** ❌ |

## 4. 拡張を阻害している箇所 ★後追い文書化の中核

> **以下は予測ではなく、実装から確認した事実である。** `[実装]`

### 4-1. 入力フォームがステップごとにハードコードされている ★最大の阻害要因

**問題**: 助言は「様式の改訂を**コード改修なしに設定変更で**回せる」スキーマ駆動レンダリングを求めている `[資料]` が、実装では各ステップの入力フォームが個別Reactコンポーネント（`Step0Fields`／`Step4Fields`／`StepSlaFields`／`Step5Fields`／`Step11Fields`）として書かれている `[実装]`。

**セクションを1つ追加するのに必要な作業** `[実装]`

| # | 作業 | 種別 |
|---|---|---|
| 1 | `STEP_KEYS` / `STEP_DEFS` / `STEP_RULES` に追加 | 定義追加 ✅ |
| 2 | `CaseAnswerDataSchema` に項目追加 | 定義追加 ✅ |
| 3 | **入力コンポーネントを新規実装** | **コード実装** ❌ |
| 4 | **ウィザードの描画分岐に登録** | **コード実装** ❌ |
| 5 | **`step-status.ts` の `switch` に判定を追加** | **コード実装** ❌ |
| 6 | **プレビュー画面に表示を追加** | **コード実装** ❌ |

**影響**

- プランB/Cで残りのセクション（6〜10、12〜14）を追加する場合、**6〜9セクション分のコンポーネント実装が発生する** `[推定]`
- **プランBの「テンプレ管理画面」（WBS 2.8・14人日）が成立しない。** 管理画面から様式を変更するには、選択肢A（汎用エンジン）が前提

**改修コストの見積** `[推定]`

| 対応 | 内容 | 概算 |
|---|---|---|
| **推奨: 部分的な汎用化** | 既存3パターン（自由記述／チェック→条件付き詳細／行テーブル）を汎用部品として抽出し、定義から描画できるようにする | 8〜13人日 |
| 全面的なエンジン化 | WBS 1.4「スキーマ駆動フォームエンジン」の完全実装＋既存8セクションの移行 | 26人日＋移行 |
| 現状維持 | セクション追加のたびに個別実装 | 1セクションあたり 2〜3人日 × 追加数 |

**3セクション以上追加するなら、部分的な汎用化のほうが安い** `[推定]`。

→ 詳細は [ADR-0007](./05-adr/0007-hardcoded-step-components.md)

### 4-2. i18n の受け口が無い

**問題**: 文言がすべて JSX / 定義内に日本語直書き `[実装]`。`next-intl` 等の i18n 基盤は未導入。

**影響**: プランB の i18n（WBS 1.8・10人日）着手時、**全文言の抽出作業が発生する。**

⚠️ **さらに深刻な問題**: 助言は「現行の `data-ja/data-en` を辞書ファイルへ**機械的に移行**」を想定している `[資料]` が、**現存するプロトタイプに `data-ja/data-en` が1件も無い** `[実装]`（→ [一次資料との対応 §4-3](../00-overview/03-source-materials.md)）。
**つまり移行元の EN 文言が存在しない。** 10人日の見積は「機械的移行」を前提としており、**EN翻訳の作成工数が含まれていない可能性が高い** `[推定]`。

**緩和策** `[推定]`: 文言を JSX に直書きせず、セクションごとの定数オブジェクトにまとめておくだけでも、後の抽出が容易になる。**新規実装分から適用する。**

### 4-3. `cases` への非正規化コピーの同期

**問題**: `title` / `contractPeriod` / `primaryType` が JSON と `cases` 列に二重保持され、`DraftsService.patch` の中でのみ同期している `[実装]`。

**影響**: `cases` を直接更新する経路（案件メタ更新API、管理画面、バッチ）が増えると、同期漏れが起きる `[推定]`。

**緩和策**: 同期処理をサービス層の1箇所に集約する／PostgreSQL 移行後は生成列に置き換える `[推定]`。

### 4-4. 提出フローが無いため、後続機能の土台が無い

**問題**: `CaseStatus` は定義されているが**遷移APIが無く、状態が常に `draft`** `[実装]`。

**影響**: 以下がすべてブロックされる。

| 機能 | プラン | 依存する理由 |
|---|---|---|
| 承認ワークフロー本実装 | B | 状態遷移が前提 |
| 凍結制御 | B | 「VMO承認をもって凍結」= 状態遷移が起点 `[資料]` |
| 差戻し理由の記録 | B | 差戻し遷移が前提 |
| 提出時の必須検証 | A | 提出という契機が無い |

→ **プランAスコープ内の未実装項目（WBS 2.5・8人日）。B の前提。** [バックログ §1](../06-roadmap/02-backlog.md)

### 4-5. 自動テストが0件

**問題**: テストが1件も無い `[実装]`。

**影響**: **拡張時の回帰を検知できない。** 特に楽観ロック（`DraftsService.patch`）とステップ状態判定（`step-status.ts`）はロジックが集中しており、変更の影響が読みにくい `[推定]`。

→ **拡張準備という目的において、テストの不在は §4-1 に次ぐ阻害要因。** 触るのが怖いコードは拡張されない。

## 5. 新規実装・変更時のチェックリスト

> レビュー時に使う。判定できる項目のみ。

**セキュリティ（最優先）**

- [ ] 案件を扱うエンドポイントに**所有者チェック**を入れたか？（→ [ロールと権限 §5](../01-requirements/05-roles-and-permissions.md)）
- [ ] 認可判定を**サーバ側**で行っているか？（フロントの表示制御は認可ではない）

**拡張性**

- [ ] 様式項目の追加を、**テーブル変更ではなく `packages/schema` の定義追加**で吸収できたか？
- [ ] 将来使う列を先取りする場合、**コメントで理由を残したか？**（理由の無い列は削除される）
- [ ] ビジネスロジックを controller に直書きせず **service 層**に置いたか？
- [ ] 新しい入力パターンを作るとき、**既存3パターンで表現できないか**検討したか？（→ §4-1）
- [ ] 文言を JSX に直書きせず、**後で辞書化しやすい単位**にまとめたか？（→ §4-2）

**データ**

- [ ] `cases` への非正規化コピーを**増やしていない**か？（→ §4-3）
- [ ] 集計・検索が必要な値を、JSON から適切に抽出しているか？

**品質**

- [ ] 簡易実装・既知の制限を [バックログ](../06-roadmap/02-backlog.md) に登録したか？
- [ ] 設計判断を変えた場合、[ADR](./05-adr/) を追加したか？

## 6. AIを差し込む前提（プランC）

- AI/RAGインフラ（ベクトルDB等）はAでは導入しない `[資料]`。ただし**API層にAIオーケストレーション用の差し込み口（インターフェース）だけは意識**する `[資料]`
- **AIは「下書き・助言・セルフレビュー」まで。確定・承認・提出は人** `[資料]`（助言 §5-3）
- 生成物には「AI下書き（要確認）」の由来を表示し、監査ログにも記録する `[資料]`
- **評価項目・配点や標準条項の凍結ルールをAIに破らせない** `[資料]`。公平性に関わる領域はAIの権限外

**現状の差し込みやすさ** `[推定]`: サービス層が分離されているため、`DraftsService` への処理挿入は容易。
ただし**フロント側は `setField` による直接更新が主体**で、「AIの提案をプレビューし、ユーザーが承認して反映する」`[資料]` というフローの受け口が無い。**Cで書き戻しUIを作る際、フロントの状態管理の見直しが必要** `[推定]`。

## 7. 凍結制御を見据えた設計（プランB）

- 評価項目（11）・標準条項は「VMO承認をもって凍結」「開札後変更不可」が要件 `[資料]`
- **UIだけの制御にせず、サーバ側フィールドロック＋変更履歴**として実装する `[資料]`（助言 §3-4）
- Aでは凍結制御を持たないが、**監査ログと版管理でその土台がある** `[資料]`

⚠️ **課題**: 評価配点は `case_answers.data.eval` に内包されており、助言が想定する `evaluations` テーブル（`locked` 列）が存在しない `[実装]`。
→ **Bの凍結制御実装時に、JSONのまま凍結するか、独立テーブルへ移行するかの判断が必要。** データ移行が発生する場合、WBS 2.7（12人日）に収まるか要確認 `[未確認]`。
→ [ADR-0001](./05-adr/0001-jsonb-hybrid-data-model.md)

## 8. アンチパターン（避けること）

| アンチパターン | 何が起きるか | 代わりにすること |
|---|---|---|
| 様式項目をリレーショナルな専用列へ細かく展開する | 様式改訂・B/C項目追加でマイグレーションが必要になる | JSON＋スキーマ定義に寄せる `[資料]` |
| 認可・凍結・監査をフロントだけで制御する | 調達の公平性・説明責任を満たせない | サーバ側で担保する `[資料]` |
| controller にビジネスロジックを直書きする | AI/ワークフロー差し込み時に手戻りする | service 層に置く `[資料]` |
| **理由を書かずに未使用の列・定義を追加する** | 後で「使われていない」として削除される | コメントで先取りの理由を残す `[実装]`（`Attachment` の先例） |
| **新しいステップに専用コンポーネントを追加し続ける** | §4-1 の負債が増え、テンプレ管理画面が遠のく | 既存3パターンでの表現を先に検討する `[推定]` |
| **`cases` への非正規化コピーを増やす** | 同期漏れが起きる | 生成列/ビューでの抽出を検討する `[推定]` |

## 9. 過剰設計の線引き

**今回やらないと決めた抽象化** `[推定]`

| 抽象化 | やらない理由 | 必要になったら |
|---|---|---|
| 完全なスキーマ駆動フォームエンジン | 26人日規模。既存8セクションの作り直しも伴う | セクション3つ以上の追加、またはテンプレ管理画面の着手時（→ §4-1） |
| プラグイン機構・汎用ワークフローエンジン | 要求が具体化していない。様式2 専用システムである | — |
| マルチテナント対応 | 社内単一組織での利用が前提 `[推定]` | 他組織への展開が決まったら |

> **「拡張性のため」を口実にした先行実装をしない。** §4 に挙げた阻害要因は、いずれも**具体的な次段階の機能（テンプレ管理・i18n・承認ワークフロー）に紐づいている**から対処するのであって、一般論としての拡張性のためではない。

## 10. 拡張準備としての優先順位

> **本ドキュメントの目的（拡張準備）に対する結論。**

| 順 | 対応 | 理由 | 概算 |
|:--:|---|---|---|
| 1 | **所有者チェックの実装** | 拡張以前に運用できない。実IdPを待たず今すぐ可能 | 1〜2人日 `[推定]` |
| 2 | **自動テストの整備**（楽観ロック・step-status・主要フロー） | **触るのが怖いコードは拡張されない。** 以降の全作業の前提 | WBS 1.10 の一部 |
| 3 | **提出フロー（状態遷移API）** | B の承認・凍結・差戻しすべての土台（→ §4-4） | WBS 2.5（8人日） |
| 4 | **入力部品の部分的な汎用化** | セクション追加・テンプレ管理画面の前提（→ §4-1） | 8〜13人日 `[推定]` |
| 5 | ステージング環境と PostgreSQL 移行 | 環境差分の顕在化を前倒しする（→ [ADR-0004](./05-adr/0004-sqlite-for-development.md)） | WBS 1.1 の一部 |
| 6 | 版の刈り込み方針の決定 | 決めずにリリースするとデータが不可逆に膨らむ（→ [ADR-0003](./05-adr/0003-optimistic-lock-append-version.md)） | 方針決定＋実装 |

1〜3 は**プランAスコープ内**で、いずれも見積に計上済み `[資料]`。4 は**スコープ外の追加投資**だが、プランB を見据えるなら B 着手前に行うほうが安い `[推定]`。
