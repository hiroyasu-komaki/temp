## 3. 主要エンドポイントの詳細

### POST `/cases`

**リクエスト** — `CreateCaseSchema` `[実装]`

```json
{ "title": "（必須・1文字以上）", "contractPeriod": "", "primaryType": "A-2", "dept": "" }
```

**レスポンス** — `CaseDto`

```json
{ "id": "uuid", "caseNo": "C-2026-0001", "title": "", "contractPeriod": "",
  "primaryType": "A-2", "status": "draft", "updatedAt": "ISO8601",
  "version": 1, "data": { } }
```

**処理順序** `[実装]`

1. 案件番号を採番（`C-{年}-{件数+1 を4桁ゼロ埋め}`）
2. `cases` を作成し、同時に `case_answers` の初版（`version=1`, `isCurrent=true`）を作成。初版には `title`/`period`/`primary` のみ格納
3. 監査ログ `case.create` を記録

> ⚠️ **採番が「件数+1」** `[実装]`。同時に2件作成すると **`caseNo` が衝突し unique 制約違反になる**。
> 「実運用では専用シーケンス採番に置き換える想定の簡易実装」とコードコメントに明記されている `[実装]`。→ [バックログ](../06-roadmap/02-backlog.md)
>
> **年をまたぐ問題も未対処** `[推定]`: 件数は全期間の総数のため、`C-2027-0051` のように年と連番が対応しない。

### GET `/cases`

`createdById = 自分` で絞り、`updatedAt` 降順。現在版を含めて返す `[実装]`。
**ページングなし。** 案件が増えると全件返却になる `[実装]`。

### GET `/cases/:id`

**認可チェックが無い。** ID を知っていれば誰の案件でも取得できる `[実装]`。

### PATCH `/drafts/:caseId`

**リクエスト** — `DraftPatchSchema` `[実装]`

```json
{ "version": 3, "data": { "s1_text": "...", "b_init": 1000000 } }
```

**レスポンス**: `{ "version": 4, "updatedAt": "ISO8601", "data": { マージ後の全体 } }`

**処理順序**（トランザクション内・タイムアウト15秒）`[実装]`

1. 現在版を取得（無ければ 404）
2. `version` 不一致なら **409 Conflict**（`{ message, currentVersion }`）
3. 既存データに `patch.data` を浅いマージ（`{...before, ...patch.data}`）
4. 旧版を `isCurrent=false` に更新
5. `version+1` の新版を作成
6. `cases` のメタ列（`title`/`contractPeriod`/`primaryType`）を同期
7. 監査ログ `draft.patch` を記録（`fieldPath` は変更キーのカンマ連結、`before`/`after` は**全体**）

> ⚠️ **マージが浅い（shallow merge）** `[実装]`。`sla` / `eval` などの配列は**丸ごと置換**される。
> フロントが配列全体を送っているため現状は動作するが、**真のフィールド単位差分を実装する際にこの前提が問題になる** `[推定]`。
>
> ⚠️ **クライアントは実質フォーム全体を送っている** `[実装]`。助言 §3-6 は「変更フィールドのみ」を想定 `[資料]`。
> → [バックログ](../06-roadmap/02-backlog.md)

## 4. autosave フロー

```
入力イベント（setField）
  → デバウンス 800ms（AUTOSAVE_DEBOUNCE_MS）
  → PATCH /drafts/:caseId  body: { version, data }
  → レスポンス { version, updatedAt, data }
  → フロントは version を更新（楽観ロック）
```

| 項目 | 値 | 根拠 |
|---|---|---|
| デバウンス | **800ms** `[実装]` | **不明。** 助言は「1〜2秒」`[資料]`、プロトタイプは 700ms `[資料]`。**どちらとも異なる** `[推定]` |
| リトライ | **なし** `[実装]` | — |
| タイムアウト | 指定なし（fetch 既定） `[実装]` | — |

**失敗時の挙動** `[実装]`

| 失敗ケース | クライアントの挙動 |
|---|---|
| 409（競合） | 競合バナー表示 → 「最新を取得」で再取得し version をリセット。**未保存の直近変更は失われる** |
| その他のエラー | `saveState = "error"` を表示するのみ。**再送しない。入力内容の退避もしない** |

> ⚠️ **保存失敗時にユーザーの入力が失われる。** 本システムの中核価値は「途中保存できる」ことにあるため、これは**原則2の趣旨に反する欠落** `[推定]`。
> 助言 §2-3 も「送信失敗時のローカル退避（IndexedDB）→復帰時サーバ同期を保険で持たせるとなお良い」としている `[資料]`。
> → [バックログ](../06-roadmap/02-backlog.md)

## 7. 現状の既知の問題（まとめ）

| # | 問題 | 影響 | 出所 |
|---|---|---|---|
| 1 | **所有者チェックが無い** | 他人の案件を閲覧・改ざん可能 | `[実装]` |
| 2 | 案件番号が「件数+1」採番 | 同時作成で衝突 | `[実装]` |
| 3 | autosave が実質フォーム全体送信 | 帯域・版サイズの無駄 | `[実装]` |
| 4 | 保存失敗時に入力が失われる | 中核価値の毀損 | `[実装]` |
| 5 | 監査ログに全体スナップショットを保存 | ログ肥大 | `[実装]` |
| 6 | 一覧にページングが無い | 件数増で劣化 | `[実装]` |
| 7 | OpenAPI 定義が無い | 契約が暗黙 | `[実装]` |
| 8 | レート制限・入力サイズ上限が無い | リソース枯渇 | `[実装]` |
| 9 | CORS が `origin: true` | 開発向け設定のまま | `[実装]` |

すべて [バックログ](../06-roadmap/02-backlog.md) に登録済み。
