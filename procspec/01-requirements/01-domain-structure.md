## 1. 対象ドメインの全体像

様式2 調達仕様書は、事業部門が作成し VMO（Vendor Management Office）が発行前にチェックする調達文書。

**セクション構成については資料間に不一致がある。** → [一次資料との対応 §4-4](../00-overview/03-source-materials.md)

| 資料 | セクション数 |
|---|---|
| 設計助言・見積書・開発方針 | 14セクション `[資料]` |
| `Form2_Prototype_Improved.html`（現存するプロトタイプ） | **8セクション** `[資料]` |

**現行の定義は Improved 版の8セクションに一致する** `[実装]`。14セクションの定義書は一次資料に存在しない（→ [欠落資料](../00-overview/03-source-materials.md) §3）。

| キー | No | 名称 | 目的（応札者が何を判断するための情報か） | 出所 |
|---|---|---|---|---|
| `0` | 0 | 案件情報・類型 | すべての起点。契約類型を選ぶと記入すべきステップに絞り込まれる | `[資料]` |
| `1` | 1 | 目的・背景 | 応札者が提案の前提を置くための情報 | `[資料]` |
| `2` | 2 | 現行環境 | 応札者が見積の土台にする現状 | `[資料]` |
| `3` | 3 | 要求事項 | 「何を」「なぜ」を書く。「どうやって」は応札者が提案する | `[資料]` |
| `4` | 4 | 非機能要件 | 性能・可用性・セキュリティ等。該当をチェックし値を入れる | `[資料]` |
| `sla` | 4-2 | SLA | 指標・目標・測定方法・未達措置を行で管理 | `[資料]` |
| `5` | 5 | 制約・予算 | 期限・予算・技術標準。予算は自動集計 | `[資料]` |
| `11` | 11 | 評価項目と配点 | 競争で何を評価するか。配点は合計100 | `[資料]` |
| `review` | ✓ | 提出前確認 | 入力内容を確認し提出する | `[資料]` |

> **セクション番号が 5 → 11 と飛んでいる。** 6〜10 は様式2 に存在するが Improved 版で省かれたものと思われる `[推定]`。この欠番が、14セクション説の傍証になる。

## 2. 契約類型

| コード | ラベル | 主分類 |
|---|---|---|
| A-2 | SaaS利用（エンタープライズ） | A |
| A-1 | IaaS/PaaS利用 | A |
| C-1 | システム開発委託（請負） | C |
| C-3 | アジャイル開発 | C |
| D-1 | IT運用保守 | D |
| D-2 | マネージドサービス | D |
| B-2 | サブスクリプションライセンス | B |
| G-2 | SES | G |

出所: プロトタイプの `TYPES` をそのまま資産化 `[資料]`。

**主分類の導出**: コード先頭1文字（`"A-2"` → `"A"`）を主分類とし、これでステップ構成が決まる `[実装]`。

> **コード体系の全体像は不明。** A/B/C/D/G は存在するが E・F が欠けている。調達部門の既存分類体系に由来すると思われるが、定義書が無い `[未確認]`。**プランB/Cで類型を追加する際に、コード体系の規則が分からないと採番できない。**

## 3. 類型分岐ルール

主分類ごとに、記入すべきステップの順序を定義する `[資料]`。

| 主分類 | ステップ順序 | 省かれるステップ |
|---|---|---|
| A | 0 → 1 → 2 → 3 → 4 → sla → 5 → 11 → review | なし |
| C | 0 → 1 → 2 → 3 → 4 → sla → 5 → 11 → review | なし |
| D | 0 → 1 → 2 → 4 → sla → 5 → 11 → review | 3（要求事項） |
| B | 0 → 1 → 3 → 4 → 5 → 11 → review | 2（現行環境）、sla |
| G | 0 → 1 → 3 → 5 → 11 → review | 2、4、sla |

**未選択時**: ステップ `0` のみを提示する `[実装]`。これがプログレッシブ開示の起点 `[資料]`。

> **各類型で特定のステップを省く業務上の理由は資料に記載がない** `[未確認]`。読み取れる範囲では:
> - D（運用保守）で 3（要求事項）を省く → 運用は「何を」より SLA が主 `[推定]`
> - B（ライセンス）で 2（現行環境）と SLA を省く → 調達物が製品であり現行環境に依存しない `[推定]`
> - G（SES）で 4（非機能）も省く → 役務提供であり成果物の非機能要件が無い `[推定]`
>
> **いずれも推定。業務側への確認が必要。** 誤っていると、必要なセクションが提示されない／不要なセクションを書かせることになる。

## 4. 項目定義

### セクション 0: 案件情報・類型

| 項目キー | ラベル | 型 | 必須 | 備考 |
|---|---|---|:--:|---|
| `title` | 件名 | text | ✅ | 案件作成時に必須（`CreateCaseSchema`）`[実装]` |
| `period` | 契約期間 | text | − | 自由記述。日付ピッカーではない `[実装]` |
| `primary` | 契約類型 | select | − | `CONTRACT_TYPES` から選択 |

### セクション 1〜3: 自由記述

| 項目キー | ラベル | 型 | 必須 |
|---|---|---|:--:|
| `s1_text` | 目的・背景 | textarea | − |
| `s2_text` | 現行環境 | textarea | − |
| `s3_text` | 要求事項 | textarea | − |

### セクション 4: 非機能要件（チェック該当 → 値入力）

| チェック | 該当時の入力項目 | 型 |
|---|---|---|
| `ck_perf` 性能 | `nf_perf` 応答秒数／`nf_perf_u` 同時利用者数 | number |
| `ck_avail` 可用性 | `nf_avail` 稼働率%／`nf_rto` RTO時間／`nf_rpo` RPO時間 | number |
| `ck_sec` セキュリティ | `nf_sso` SSO要否（boolean）／`nf_log` ログ保管年数 | boolean / number |
| `ck_reg` 規制 | `reg_gxp` / `reg_pi` / `reg_sox` | boolean |
| — | `nf_note` 補足 | textarea |

### セクション 4-2: SLA（行テーブル）

`sla: SlaRow[]` — 各行は `metric`（指標）／`target`（目標値）／`measure`（測定方法）／`penalty`（未達措置）。すべて text `[実装]`。

### セクション 5: 制約・予算

| 項目キー | ラベル | 型 |
|---|---|---|
| `b_init` / `b_run` / `b_lic` | 初期費用／運用費用／ライセンス費 | number |
| `d_rfp` / `d_go` | RFP期限／稼働希望日 | date |
| `s5_text` | 技術標準・制約 | textarea |

### セクション 11: 評価項目と配点（行テーブル）

`eval: EvalRow[]` — 各行は `criterion`（評価項目）／`weight`（配点 0〜100）／`viewpoint`（評価観点）。

**既定4行**: 技術・実現性 40 ／ コスト 30 ／ 体制・実績 20 ／ 提案の具体性 10 `[実装]`

> この配点が組織の標準配点なのか、実装時の例示なのかは**不明** `[未確認]`。調達の公平性に直結するため、業務側の確認が必要。

## 5. ドメインルール・整合性制約

| # | ルール | 対象 | 現在の扱い | 出所 |
|---|---|---|---|---|
| 1 | 評価配点の合計は 100 | `eval[].weight` | UI上で合計表示・適否バッジ。**保存はブロックしない** `[実装]` | `[資料]` |
| 2 | 予算は費目の自動集計 | `b_init`+`b_run`+`b_lic` | 表示のみ。保存はしない `[実装]` | `[資料]` |
| 3 | 評価項目はVMO承認をもって凍結、開札後変更不可 | `eval` | **未実装。** UI文言に「プランB以降」と明記 `[実装]` | `[資料]` |
| 4 | 件名は必須 | `title` | 案件作成時のみ検証。以降は空でも保存可 `[実装]` | `[実装]` |
| 5 | RFP期限 < 稼働希望日 | `d_rfp`, `d_go` | **未実装**（整合性チェック無し） | `[推定]` |

検証の実装方針は [検証・エラー設計](../03-detail-design/04-validation-and-errors.md)。
