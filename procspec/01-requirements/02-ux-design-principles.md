# UX設計原則

- **出典**: 設計助言 §2 `[資料]`
- **最終更新**: 2026-07-25

> トライアルで出た4つの不満（→ [プロダクトビジョン §2](../00-overview/01-product-vision.md)）は、いずれも現行モックが「状態を持たない静的1枚もの」であることに起因する `[資料]`。
> UIの微調整ではなく、以下3点を**構造として**実装する。

---

## 原則1: プログレッシブ開示

**対応する課題**: #1「入力項目が多くて面倒」／ #2「どこに何を書けばよいか分からない」

> 全項目を一度に見せず、類型選択 → 必要なセクションだけを順に案内する `[資料]`

**この原則が要求すること**

- 最初は **0. 案件情報 → 契約類型** だけを提示する。ここが全体の分岐点なので、他を見せない `[資料]`
- 類型を選ぶと、`STEP_RULES` に従って**そのユーザーに必要なステップだけ**を左ナビに生成する `[資料]`
- 1画面＝1セクションに絞り、スクロール量をそのセクション分に限定する `[資料]`
- 上部に進捗インジケータ、左にステップ一覧＋状態バッジ（未着手／記入中／完了）を常時表示 `[資料]`
- **全体プレビュー／印刷用の1枚表示モードを併設する。** ウィザードは入力用、1枚表示はレビュー・PDF出力用と役割を分ける `[資料]`

**守れているかの判定基準**

- [ ] 契約類型を選ぶまで、他のセクションが一切見えないこと
- [ ] 1画面のスクロール量が1セクション分に収まること
- [ ] 現在地・全体の進捗・各ステップの状態が常に見えること
- [ ] 全体を俯瞰したいときに1枚表示へ切り替えられること

**現在の実装** `[実装]`: 4項目とも満たしている。ステップ状態は `none`／`part`／`done` の3値。

---

## 原則2: サーバ状態を持つ下書き（autosave＋再開）

**対応する課題**: #4「途中で保存できない」

> 入力は常時サーバに保存され、いつ中断しても続きから書ける `[資料]`

**この原則が要求すること**

- **常時オートセーブ**を標準にする。ユーザーに「保存ボタンを押す」責任を負わせない `[資料]`
- 入力停止からデバウンスしてサーバへ保存し、「◯分前に保存済み」を表示 `[資料]`
- **案件（ドラフト）単位のリスト画面**で、ステータス別に一覧・再開できる `[資料]`
- **楽観的ロック**（バージョン列）で多重編集・上書き事故を防ぐ。競合時は409で「新しい版があります」を提示 `[資料]`

**守れているかの判定基準**

- [ ] 保存ボタンを一度も押さずに、中断・再開ができること
- [ ] 保存の成否がユーザーに見えること
- [ ] 競合が起きたとき、データを黙って失わないこと

**現在の実装** `[実装]`: デバウンス800ms、楽観ロック、409競合検知と「最新を取得」導線あり。

> **注意**: 助言 §2-3 は「明示的な『下書き保存』ボタンも併置（心理的安心・オフライン復帰時の手動トリガ用）」を推奨しているが、**未実装** `[実装]`。
> また「送信失敗時のローカル退避（IndexedDB）→復帰時サーバ同期」も「必須ではない」としつつ推奨しているが未実装 `[実装]`。
> **保存失敗時に入力内容が失われる**（→ [検証・エラー設計 §8](../03-detail-design/04-validation-and-errors.md)）。原則2の趣旨に照らすと、これは埋めるべき欠落 `[推定]`。

> **補足（重要）**: 現存するプロトタイプは既に `localStorage` で保存している（→ [一次資料との対応 §4-2](../00-overview/03-source-materials.md)）。
> **したがって本原則の価値は「保存できること」ではなく「サーバ状態であること」にある** — 端末をまたいだ再開、競合制御、監査、他ロールからの参照。この点を見失うと、原則2の実装判断を誤る `[推定]`。

## 原則3: 入力を「書かせる」から「選ばせる」へ

**対応する課題**: #3「テキスト入力ばかりで手間」

> 定型・半定型は部品化し、本質的に自由な記述だけを textarea に残す `[資料]`

**この原則が要求すること**

| 対象 | 部品化の方針 | 出所 |
|---|---|---|
| 非機能要件（4） | 該当をチェック → 該当項目だけ数値/選択入力。自由記述は「補足」欄に降格 | `[資料]` |
| SLA（4-2） | 指標・目標値・測定方法・未達措置を**行テーブル**（追加/削除可能）に | `[資料]` |
| 予算（5-2） | 費目テーブル＋**自動合計**（電卓不要）。3桁区切り・全角半角補正 | `[資料]` |
| 期日（5-1, 12） | `type=text` を**日付ピッカー**へ | `[資料]` |
| 評価配点（11） | 行テーブル＋**合計100の自動チェック** | `[実装]` |
| 選択肢＋「その他」 | 既にチェック/ラジオ化されている良い部分を全セクションに広げる | `[資料]` |
| 例文（プレースホルダ） | 入力欄を圧迫しないよう、ガイド文・トグルに寄せる | `[資料]` |

**守れているかの判定基準**

- [ ] 数値・日付・選択肢で表せる項目が textarea になっていないこと
- [ ] 繰り返し構造が1つの大きな textarea になっていないこと
- [ ] 自動計算できる合計を、ユーザーが手で計算していないこと

**現在の実装と未達** `[実装]`

| 項目 | 状態 |
|---|---|
| 非機能・SLA・予算・配点の部品化 | ● 実装済み |
| 予算の自動合計 | ● 実装済み |
| 配点合計100の自動チェック | ● 実装済み |
| 期日の日付ピッカー | ● 実装済み（`type=date`） |
| **予算の3桁区切り・全角半角補正** | ○ **未実装**（表示のみ `toLocaleString`、入力補正なし） |
| **契約期間の日付化** | ○ **未実装**（`period` は自由記述テキストのまま） |
| **選択肢＋「その他」パターンの横展開** | ○ **未実装** |
| **例文のトグル表示** | ○ **未実装**（ガイド文は常時表示） |

## 迷子をさらに防ぐ仕掛け

| 仕掛け | 内容 | 実装 | 出所 |
|---|---|:--:|---|
| セクションの目的明示 | 各ステップ冒頭に「何のためにあるか」を1〜2行 | ● | `[資料]` |
| 必須/任意の明確化 | インライン検証。空欄でも次へ進めるが未完はナビにバッジで残す | ◐ | `[資料]` |
| **強制ブロックしない** | 下書き文化を尊重し、未完でも進める | ● | `[資料]` |
| 提出前セルフチェック（AI） | VMOが見る7観点をAIが事前レビュー | − | `[資料]` プランB以降 |

> **「必須/任意の明確化」が未達** `[実装]`。ステップ状態バッジ（`none`/`part`/`done`）はあるが、**項目単位の必須表示とインライン検証が無い。**
> 現状の `done` 判定は「何か入力されていれば完了」であり、**必須項目が埋まったかを見ていない**（→ [検証・エラー設計](../03-detail-design/04-validation-and-errors.md)）。
> ユーザーは「完了」バッジを見て提出できると誤解しうる `[推定]`。
