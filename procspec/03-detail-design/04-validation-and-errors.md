# 検証・エラー設計

- **出典**: 実装の棚卸し `[実装]` / 設計助言 §2-3・§2-4 `[資料]`
- **最終更新**: 2026-07-25

> ⚠️ **検証は「型」レベルのみで、業務ルールの検証はほぼ実装されていない。** `[実装]`
> エラー表示の方針も統一されていない。**設計されないまま実装された領域。**

## 1. 検証の方針

| 項目 | 方針 | 現状 | 出所 |
|---|---|---|---|
| 検証定義の置き場所 | `packages/schema` の Zod スキーマを単一ソースとし、フロント・API双方で共有 | ✅ 守られている | `[資料]` → [ADR-0002](../02-architecture/05-adr/0002-schema-single-source.md) |
| フロント検証の役割 | 即時フィードバック（UX）。認可・整合性の担保ではない | ◐ **実質機能していない**（→ §2） | `[推定]` |

| 検証タイミング | 下書きは緩く、提出時に厳しく | ❌ **提出が無いため後段が存在しない** | `[推定]` |
| 未入力の扱い | 下書き段階では許容（全項目 optional） | ✅ | `[実装]` |

## 2. フロント検証が機能していない ★

**問題** `[実装]`: `react-hook-form` と `@hookform/resolvers` は依存に含まれ、[ADR-0002](../02-architecture/05-adr/0002-schema-single-source.md) の想定でもあるが、**実際の入力は `setField` による直接的な state 更新が主体**であり、Zod の検証ルールが入力時に走らない。

**影響**

- 型の不整合（数値欄に文字列など）は HTML の `type=number` で防がれるのみ
- **業務ルール（配点合計100、日付の前後関係）は保存を止めない**
- ユーザーは誤りに気づかないまま先へ進める

**意図的な簡略化か実装漏れかは不明** `[未確認]`。

> ただし「**強制ブロックしない＝下書き文化の尊重**」`[資料]` という原則があるため、**保存をブロックしないこと自体は正しい。**
> 問題は「ブロックしないが**知らせもしない**」点にある `[推定]`。警告として提示する設計が必要。

## 3. 検証レベル（あるべき姿）

| レベル | 意味 | ユーザーの進行 | 現状 |
|---|---|---|---|
| **エラー** | 業務上あり得ない値 | ブロックする | 型違反のみ（400） |
| **警告** | 不備の可能性があるが進めてよい | 進める | **仕組みが無い**（配点合計のみ表示） |
| **情報** | 補足・推奨 | 進める | ガイド文として常時表示 |

> **「警告」レベルが存在しないことが、現状の最大の設計欠落** `[推定]`。
> 下書き文化を尊重しつつ不備を知らせるには、警告が不可欠。

## 5. 提出前チェック（未実装）

**あるべき姿** `[推定]`

| 項目 | 方針 |
|---|---|
| チェック対象 | 必須項目の充足、配点合計100、日付の整合性 |
| 未完了の提示 | 一覧表示＋該当ステップへのジャンプ |
| 未完了でも提出可能か | **要判断** `[未確認]` → [状態遷移設計 §4](./03-state-transitions.md) |

**現状**: `review` ステップは存在するが、**入力内容の確認表示のみで検証を行わない** `[実装]`。
「AIによる提出前セルフチェックはプランB以降で追加予定です」と表示される `[実装]`。

> ⚠️ **AI によるセルフチェック（B/C）と、基本的な必須検証（A）は別物。** `[推定]`
> 前者が無くても後者は必要だが、**現状はどちらも無い。** UI文言が「B以降」と述べているため、
> 基本検証まで B の扱いになっていると誤読されうる。

## 6. ステップ状態バッジの判定が緩い

**問題** `[実装]`: `done` 判定が「該当項目が1つでも入力されていれば完了」となっているステップがある（ステップ4・5）。

**影響**: ユーザーは全ステップが `done` になったのを見て「書き終えた」と判断するが、**必須項目が空のまま提出しうる。**

判定条件の詳細は [画面設計 §4](./01-screen-design.md)。**判定条件の根拠は資料に無い** `[未確認]`。

**改善案** `[推定]`: 必須項目の定義を `STEP_DEFS` に持たせ、`done` を「必須項目がすべて充足」に変更する。
「一部入力あり」は `part` で表す。**これは §5 の提出前チェックと同じ必須定義を使えばよい。**

## 7. エラーメッセージの方針

**現状**: 統一された方針が無い `[実装]`。

| 箇所 | メッセージ | 文体 |
|---|---|---|
| 案件作成 | 「件名は必須です」 | 丁寧・断定 |
| スキーマ違反 | 「入力内容がスキーマに違反しています」 | **技術用語が漏れている** |
| 認証失敗 | 「未知のユーザーです（開発用シード未実行の可能性）: {email}」 | **開発者向けの文言が本番に出る** |
| 競合 | 「新しい版があります。最新の内容を取得してください。」 | 適切 |
| 案件なし | 「案件が見つかりません」 | 適切 |
| 保存失敗 | 「保存に失敗しました」相当 | — |

> ⚠️ **「スキーマに違反」はユーザーに意味が伝わらない** `[実装]`。「入力内容に誤りがあります」等に改めるべき `[推定]`。
> ⚠️ **`DevAuthGuard` のメッセージに「開発用シード未実行の可能性」が含まれる** `[実装]`。仮認証の差し替え時に必ず消すこと。

**あるべき方針** `[推定]`

| 項目 | 方針 |
|---|---|
| 文体 | 「〜です」「〜してください」で統一 |
| 含める情報 | 何が問題か／どうすればよいか |
| 技術的な詳細 | ユーザーには出さない。ログに記録し参照IDのみ提示 |
| 禁止 | 内部用語（スキーマ、バリデーション）、開発環境固有の説明 |

## 9. API エラー応答の形式

**現状** `[実装]`

| ステータス | 用途 | レスポンス |
|---|---|---|
| 400 | スキーマ違反 | `{ message, issues: ZodIssue[] }` |
| 401 | 未知のユーザー | `{ message }` |
| 404 | 案件・下書きなし | `{ message }` |
| 409 | 版の競合 | `{ message, currentVersion }` |
| 500 | サーバエラー | NestJS 既定 |

**未対応** `[実装]`: 403（認可が未実装）、422（業務ルール違反）、`traceId`（ログ追跡ID）。

**あるべき形式** `[推定]`

```json
{
  "code": "VALIDATION_ERROR",
  "message": "入力内容に誤りがあります",
  "details": [{ "field": "eval", "code": "WEIGHT_SUM", "message": "配点の合計を100にしてください" }],
  "traceId": "..."
}
```

現状は `code` と `traceId` が無く、**クライアントがエラー種別を機械的に判定できない**（`status` と `message` 文字列に依存）`[実装]`。

## 10. 競合・障害時の挙動 ★

| 事象 | ユーザーに見えるもの | 取れる行動 | データの扱い | 評価 |
|---|---|---|---|---|
| **保存の競合（409）** | 競合バナー | 「最新を取得」 | **未保存の直近変更は失われる** | ◐ 最小限だが機能する |
| **通信断** | 「エラー」表示 | **なし** | **入力は画面上に残るが保存されない** | ❌ |
| **保存失敗（500）** | 「エラー」表示 | **なし** | 同上 | ❌ |
| **セッション切れ** | 401 → エラー表示 | **なし** | 同上 | ❌ |

### ⚠️ 未保存データが保護されていない

**本システムの中核価値は「途中保存できる」ことにある**（→ [プロダクトビジョン](../00-overview/01-product-vision.md)）。
**保存に失敗した状態で画面を離れると、入力内容は失われる** `[実装]`。リトライもローカル退避も無い。

助言 §2-3 も推奨している `[資料]`:

> ブラウザ障害対策として、送信失敗時のローカル退避（IndexedDB）→復帰時サーバ同期、を保険で持たせるとなお良い（必須ではない）。

**対応の選択肢** `[推定]`（コストの低い順）

1. **保存失敗時に自動リトライする**（指数バックオフ）— 一時的な通信断の大半を吸収できる
2. **未保存の変更がある状態での画面離脱を警告する**（`beforeunload`）— 実装が最も簡単
3. **ローカル退避（IndexedDB / localStorage）→復帰時に同期** — 最も確実だが実装コストが高い

→ [バックログ §1-7](../06-roadmap/02-backlog.md)

> **補足**: プロトタイプは `localStorage` に保存していた `[実装]`。
> サーバ状態へ移行した結果、**「通信できないと何も残らない」という新たな弱点が生まれた** `[推定]`。
> 移行にあたって失った性質を補う設計が必要だった。
