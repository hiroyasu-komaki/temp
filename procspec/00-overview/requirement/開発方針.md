## 1. スコープ定義（プランA）

見積書「サマリ・プラン比較」シートの定義に基づく。

**含む主な機能**
スキーマ駆動フォーム＋ウィザード＋オートセーブ/保存再開＋認証・RBAC＋基本の添付・プレビュー、簡易な提出フロー、最小限の監査ログ、基本アクセシビリティ、性能・脆弱性診断、UAT。

**含まない機能（B/Cとのトレードオフ、意図的に除外）**

| 除外項目 | 理由・扱い |
|---|---|
| AI一式（下書き生成・チャット・RAG・セルフチェック） | プランB/Cで追加。プロトタイプのAIパネルはUIモックのまま残し、本番Aでは非表示/非実装とする |
| 多言語（EN） | Aは日本語のみ。プロトタイプの `data-ja/data-en` 相当の仕組みは実装するが辞書はJAのみ用意 |
| 凍結制御・テンプレ管理画面 | 評価項目・標準条項のサーバ側ロックや、条項/評価のマスタ管理画面はB以降 |
| ウイルススキャン連携・NDA条件別アクセス制御 | 添付は受け取るがスキャン連携・条件付き権限制御はB以降 |
| 高度な監査ログ | Aは最小限（誰が・いつ・何を変更したかの記録のみ。差分の高度な可視化や凍結連携はなし） |
| 本格的な承認ワークフロー | Aは「提出のみ」の簡易フロー（VMO確認・差戻しの状態遷移は持つが、権限分界や複雑な分岐は簡略化） |

この境界は**プランA→B→Cの段階アップグレードを前提**としており、Aの実装がB/Cの追加実装を阻害しない設計（§6 参照）とする。

## 2. 設計の3原則

設計アドバイス文書の結論を、そのままAスコープの設計土台とする。トライアルで出た「項目が多い／迷子／テキスト入力ばかり／途中保存できない」という不満は、いずれも現行モックが「状態を持たない静的1枚もの」であることに起因するため、UIの微調整ではなく以下3点を構造として実装する。

1. **プログレッシブ開示** — 契約類型選択後、必要なステップだけをウィザード形式で提示する（現行モックの `RULES` 分岐ロジックをステップ定義として資産化）。
2. **サーバ状態を持つ下書き（autosave＋再開）** — 常時オートセーブ＋楽観ロックにより、いつ中断しても続きから書ける。Aスコープの中核。
3. **入力を「書かせる」から「選ばせる」へ** — 非機能要件・SLA・予算・期日など半構造化できる項目はフォーム部品化する。自由記述はAIで補助しない代わりに、ガイド文・入力例の見せ方（トグル表示等）で負担を下げる。

## 3. 技術スタック

```
[Browser]  Next.js (React)
  ├ フォーム: React Hook Form + Zod（フロント/API共有スキーマ）
  ├ サーバ状態/autosave: TanStack Query（楽観更新）
  └ i18n: next-intl（辞書はJAのみ実装、EN拡張に備えた構造）
        │ REST/JSON（OpenAPI）
        ▼
[API]  NestJS（推奨）
  ├ 認証: OIDC/OAuth2（社内IdP SSO）+ RBAC（作成者/所属長/VMO/閲覧）
  ├ ドラフト/提出ワークフロー（簡易版）
  └ ファイル: 署名付きURL直PUT
        │
        ▼
[Data]
  ├ PostgreSQL（案件・回答・版・監査）
  └ Object Storage（S3互換：添付本体）
```

- **ORM**: Prisma または Drizzle。マイグレーション管理必須。
- **スキーマ駆動レンダリング**: セクション/項目定義をJSON化し、UIがそれを解釈して描画。現行モックの `CATS` `RULES` `SECNAME` を定義の原型として抽出・資産化する。
- AI/RAG関連のインフラ（ベクトルDB等）は**Aでは導入しない**。ただしAPI層にAIオーケストレーション用の差し込み口（インターフェース）だけは意識した設計とし、B/C導入時の付け替えを容易にする。

## 4. データモデル方針

設計アドバイス文書のハイブリッド方針（案件・提出メタは列で正規化、回答本体はJSONBで柔軟に）を採用。

```
cases            案件（id, case_no, title, contract_period, primary_type, secondary_types,
                  status[draft|submitted|vmo_review|approved|returned], created_by, dept, timestamps）
case_answers      回答本体（case_id, version, data(jsonb), is_current, updated_by/at）— 楽観ロック・履歴の要
attachments       添付（case_id, section_key, file_name, size_bytes, mime, storage_key,
                  uploaded_by/at）※ scan_status/provision_condition 列はB以降で追加
evaluations       評価項目・配点（Aでは locked 列は将来拡張用に持つが機能としては未使用）
audit_log         監査（case_id, actor, action, field_path, before, after, at）— Aは最小項目のみ記録
users/roles/case_roles  認証・権限
```

JSONBに回答本体を持たせることで、様式改訂やB/Cでの項目追加が**マイグレーション不要**で吸収できる。集計が必要な値（予算合計・類型など）は生成列/ビューで別途抽出する。

## 6. 拡張性への配慮（B/Cへの段階アップグレード前提）

Aは「まず作って終わり」ではなく、B/Cへの土台であることを設計判断の基準にする。

- スキーマ駆動フォームエンジン・JSONBデータモデルは、B/Cの構造化部品追加・項目拡張を**コード改修なしの定義追加**で吸収できる形にする。
- `evaluations` の `locked` 列、`attachments` の `scan_status`/`provision_condition` 列は、Aでは未使用でもテーブル設計としては最初から確保しておく（後付けマイグレーションでの手戻りを避ける）。
- API層はAIオーケストレーションやRAG検索を将来差し込めるよう、ドラフト取得/更新の処理をサービス層で分離しておく（コントローラに直書きしない）。
- 監査ログ・承認ワークフローは「簡易」だが、状態遷移とログのデータ構造自体はB相当の項目（差戻し理由、承認者ロール）を持たせておき、Bでは主にUI・権限制御の拡張で済むようにする。

## 8. 前提条件・除外事項・リスク（見積書準拠）

**前提条件**
- 様式（14セクション・契約類型・標準条項・評価テンプレ）の定義が確定していること
- 認証は既存の社内IdP(OIDC/SSO)を利用でき、権限管理基盤が提供されること
- クラウド環境・CI/CD・ウイルススキャン等の基盤が調達済みまたは並行調達可能なこと
- 事業部門・VMOのレビュー要員が定例で確保されること
- 1人月=20人日、標準的な稼働を前提

**除外事項（全プラン共通）**
- ハードウェア・ライセンス・クラウド利用料等のランニングコスト
- 様式2以外の帳票・周辺システムの開発
- 既存データの大規模クレンジング
- 本番運用・保守（SLA運用、監視、恒常的な問合せ対応）の運用フェーズ費用
- JA/EN以外の多言語拡張、ネイティブモバイルアプリ開発

**リスク**
- Aは承認・監査・凍結が簡易なため、調達ガバナンスの厳格運用が必要になった時点でB以降への移行が前提となる
- 要件・様式定義の未確定は手戻り要因（コンティンジェンシー20%で一次吸収）
- GxP/個人情報等の規制対象が含まれる場合、CSV/監査対応で追加工数が発生し得る
- 精度レンジ：本見積は概算のため実績は±30%程度で変動し得る。スコープ確定後に詳細見積で精緻化する

## 9. 成功指標

トライアルで出た4つの不満に対応させ、フェーズごとに定量測定する。

- 入力完了までの所要時間（プログレッシブ開示・オートセーブの効果）
- 途中離脱率
- VMOへの差戻し回数（Aでは簡易フローのため参考値扱い、Bで本格測定）
- ユーザー満足度（UAT時のアンケート）

### 一言で

**プランA＝「静的1枚もの」から「サーバ状態を持つスキーマ駆動のウィザード」への移行を、AI・多言語・凍結制御・高度監査を持ち越さずに最短で実現するスコープ。** B/Cへの段階アップグレードを前提に、データモデルとAPI設計だけは拡張性を確保しておく。
