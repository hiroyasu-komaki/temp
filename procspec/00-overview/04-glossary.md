## 1. 業務用語

| 用語 | 意味 | コード上の表現 | 出所 |
|---|---|---|---|
| 様式2 | 社内の競争調達で使う調達仕様書の様式。本システムの対象 | — | `[資料]` |
| 案件 | 1件の調達仕様書に対応する業務上の単位 | `CaseRecord`（テーブル `cases`） | `[実装]` |
| 案件番号 | サーバが自動発番する識別子。形式 `C-YYYY-NNNN` | `caseNo` | `[実装]` |
| 下書き（ドラフト） | 案件が持つ未提出状態の回答データ | `CaseAnswer`（テーブル `case_answers`） | `[実装]` |
| 契約類型 | 調達の種別。ステップ構成を決める分岐点 | `CONTRACT_TYPES` / `primaryType` | `[資料]` |
| 主分類 | 契約類型コードの先頭1文字（A/B/C/D/G） | `primaryCategoryOf()` | `[実装]` |
| セクション | 様式2 上の章立て（0. 案件情報、1. 目的・背景 …） | — | `[資料]` |
| ステップ | ウィザードの1画面。おおむねセクションに対応 | `StepKey` / `STEP_DEFS` | `[実装]` |
| 標準条項 | 調達契約に適用する定型条項。プランB で管理画面化 | （未実装） | `[資料]` |
| 評価項目・配点 | 競争で何をどの比重で評価するか。合計100 | `eval: EvalRow[]` | `[資料]` |
| 凍結 | VMO承認をもって評価項目・条項を変更不可にすること。開札後も変更不可 | （未実装。プランB） | `[資料]` |
| 開札 | 応札内容を開封し評価を開始すること | — | `[資料]` |
| 応札者 | 調達に応じて提案・見積を提出する事業者 | — | `[資料]` |
| 見積可能性 | 応札者が第三者としてリスクを織り込んだ見積を作れる状態か | （プランB/C のセルフチェック観点） | `[資料]` |
| 差戻し | VMO等が内容不備を理由に作成者へ戻すこと | `CaseStatus.returned` | `[資料]` |

> 現状はほぼ1対1だが、`sla`（4-2）のようにセクション内のサブ項目が独立ステップになっている例がある `[実装]`。

## 4. 紛らわしい語の使い分け

| 区別すべき語 | 使い分け |
|---|---|
| 「案件」と「下書き」 | 案件＝業務上の単位（`cases`）。下書き＝案件が持つ未提出状態の回答データ（`case_answers`） |
| 「セクション」と「ステップ」 | セクション＝様式上の章立て。ステップ＝ウィザードの1画面 |
| 「版（version）」と「履歴」 | 版＝`case_answers.version`（楽観ロックのキー兼世代番号）。履歴＝版の集合 |
| **「非機能要件」の2つの意味** | **①本システム自体の非機能要件**（→ [非機能要件](../01-requirements/04-non-functional.md)）／**②様式2 のセクション4で調達対象システムについて書かせる項目**（`ck_perf` 等）。**混同に注意** |
| **「規制対象」の2つの意味** | ①本システムが規制対象か ②調達対象システムが規制対象か（`reg_gxp`/`reg_pi`/`reg_sox`）。**別問題** |
| 「プランA」と「フェーズP0〜P3」 | プラン＝スコープの段階（A/B/C）。フェーズ＝時間軸の区分（P0〜P3・M）。**A の中に P0〜P3 がある** |
