## 6. 段階アップグレードの前提

見積書のリスク欄より `[資料]`:

- **A→B→C は段階的アップグレード可能。Aで基盤を作れば、B/Cの機能は後から追加できる設計を前提とする。**
- Aは承認・監査・凍結が簡易のため、**調達ガバナンスの厳格運用にはB以上を推奨。**
- C（AI）の精度・データ取扱い制約により工数変動あり。段階リリースで低減。

### ⚠️ 「後から追加できる設計」の実際

> **本ドキュメントは後追い作成のため、この前提が実際に成立しているかを事実として確認できる。** `[実装]`

| 拡張の種類 | 前提どおりか | 実際に必要な作業 |
|---|:--:|---|
| 契約類型の追加 | ✅ | 定義追加のみ |
| 分岐ルールの変更 | ✅ | 定義追加のみ |
| 項目の追加（既存セクション内） | ◐ | スキーマ追加＋該当コンポーネント改修 |
| **セクションの追加** | **❌** | **入力コンポーネントの新規実装が必要** |
| **テンプレ管理画面（B・14人日）** | **❌** | **現状の構造では成立しない。フォームエンジンが前提** |
| 承認ワークフロー（B） | ✅ | `CaseStatus`・`User.role` の受け口あり。**ただしAの提出フロー自体が未実装** |
| スキャン/NDA（B） | ✅ | `Attachment` の先取り列あり。**ただし添付機能自体が未実装** |
| 凍結制御（B） | ◐ | 版管理・監査は土台になる。**評価配点のテーブル移行が必要な可能性** |
| i18n（B・10人日） | ❌ | 文言抽出が必要。**さらに移行元のEN文言が存在しない** |
| AI差し込み（C） | ◐ | サービス層は分離済み。**フロントの書き戻しUIの受け口は無い** |

**結論** `[推定]`: 「Aで基盤を作ればB/Cは追加で済む」という前提は、**データ層とAPI層では概ね成立しているが、フロントエンドでは成立していない。**

→ 詳細と改修コストの見積は [拡張性への配慮 §4](../02-architecture/04-extensibility.md)、[ADR-0007](../02-architecture/05-adr/0007-hardcoded-step-components.md)。

## 7. B/C 移行の判断基準

| 次段階への移行が必要になる条件 | 判定方法 | 出所 |
|---|---|---|
| 調達ガバナンスの厳格運用（監査・承認・凍結）が必要になった | 内部統制／監査部門の要求 | `[資料]` |
| 様式2 の残りセクションを使う運用に移行する | 業務側の判断 | `[推定]` |
| VMOへの差戻し回数が想定を超え、事前チェックの自動化が必要になった | 成功指標の測定（→ [プロダクトビジョン §5](./01-product-vision.md)） | `[推定]` |
| 海外拠点での利用が決まった（EN対応） | 業務側の判断 | `[推定]` |

> **B に着手する前に、[拡張性への配慮 §10](../02-architecture/04-extensibility.md) の優先順位1〜4を済ませることを推奨する** `[推定]`。
> 特に入力部品の汎用化は、B のテンプレ管理画面（14人日）の前提であり、後回しにすると B の工数が膨らむ。
