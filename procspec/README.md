# procspec 開発ドキュメント

様式2 調達仕様書システム（procspec）の開発者向けドキュメント。

> **本ドキュメントは後追いで作成されている。**
> procspec は先に実装され、その後に本ドキュメント群を整備した。作成方針は [devdoc-template / 使い方②](../devdoc-template/USAGE-02-retrofit.md) に従う。
> **目的は「拡張準備」** — プランB/Cへの機能追加に耐える設計基盤を整えること。現状の説明書ではない。

---

## 0. このドキュメントの読み方

### 0-1. 出所タグ

**すべての記述に出所が付いている。** 記述の確度が異なるため、必ず確認して読むこと。

| タグ | 意味 | 扱い |
|---|---|---|
| `[資料]` | 一次資料に根拠がある | 確定情報 |
| `[実装]` | 実装から読み取った事実 | 事実だが、**意図的な設計とは限らない** |
| `[推定]` | 意図が不明で、実装から推測した | **合意なしで覆してよい** |
| `[未確認]` | 関係者への確認が必要 | [decision-log](./_templates/decision-log.md) に登録済み |

`[推定]` と `[実装]` が付いた記述は、**「そうなっている」だけで「そうすべき」ではない。** 変更の障害と見なさないこと。

### 0-2. 一次資料と本ドキュメントの関係

- 一次資料は [`00-overview/requirement/`](./00-overview/requirement/) に原本のまま置く。**改変しない。**
- 本ドキュメントはその二次資料。対応関係と**食い違い**は [一次資料との対応](./00-overview/03-source-materials.md) に記録している。
- **資料と実装の間に4件の食い違いを発見した。** 読む前に [対応表 §4](./00-overview/03-source-materials.md) に目を通すこと。

### 0-3. プロファイル判定

[devdoc-template / 使い方①](../devdoc-template/USAGE-01-tailoring.md) による判定結果は **L（重厚）／合計13点**。全章を作成対象とした。判定の内訳は [§4](#4-プロファイル判定の記録)。

## 5. 運用ルール

- **スコープ判断の正は [機能スコープ](./01-requirements/03-functional-scope.md)。**
- **設計を変えたら [ADR](./02-architecture/05-adr/) を残す。** 既存ADRは書き換えず、新規に起こして旧を「置換済み」にする。
- **`[推定]` の裏が取れたらタグを外す。** 根拠を追記する。
- **`[未確認]` は [decision-log](./_templates/decision-log.md) で管理する。** 関係者と話す機会に解消していく。

### 「正」への切り替え

> ⚠️ **本ドキュメントはまだ設計の「正」ではない。**
> `[未確認]` 事項の主要なものが解消され、[バックログ §1](./06-roadmap/02-backlog.md) の認可対応が完了した時点で、以下を宣言して切り替える。
>
> ```
> 本ドキュメントは YYYY-MM-DD をもって設計の「正」とする。
> 以降の変更は、実装より先にドキュメントを更新する。
> ```
>
> 切り替えまでの間、**実装と本ドキュメントが食い違った場合は実装を正とし、本ドキュメントを直す。** 切り替え後は逆になる。

## 6. 一言で

**「静的1枚もの」から「サーバ状態を持つスキーマ駆動のウィザード」への移行** — これがプランAの本質 `[資料]`。
現在の実装はその中核（ウィザード・オートセーブ・構造化入力）を満たしているが、**認可・提出フロー・添付・テストが欠けており、このままでは運用できない** `[実装]`。
拡張の受け口は概ね確保されている（→ [拡張性への配慮](./02-architecture/04-extensibility.md)）が、**確保が意図的だったか偶然かの判別がついていない項目がある**。そこを [ADR](./02-architecture/05-adr/) で明示した。
