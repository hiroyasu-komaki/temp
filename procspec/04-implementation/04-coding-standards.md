## 4. コメント

**実装での実態** `[実装]`: **コメントの質は高い。**「なぜ」が書かれている箇所が複数ある。

| 良い例（実装より） | 何が良いか |
|---|---|
| `// B/C向けの拡張列（Aでは未使用。§6 拡張性への配慮に基づき先取りして確保）` | **先取りの理由**が書かれている。この列が削除されずに済む |
| `/** ... 実IdPの接続情報が無いと本物の認証は組めないため ... */` | **暫定実装の理由**が書かれている。ADR-0005 の復元がこれで可能になった |
| `/** 案件番号のサーバ発番。実運用では専用シーケンス採番に置き換える想定の簡易実装。 */` | **簡易実装であることと、あるべき姿**が書かれている |
| `// 開発用: SQLite（ゼロセットアップ）。本番はPostgreSQL(JSONB)を前提とする` | 移行方法が書かれている（**ただし理由は無い**） |

**方針**

| 書くべき | 書かなくてよい |
|---|---|
| **なぜその実装にしたか**（意図） | 何をしているか（コードを読めば分かること） |
| **簡易実装であることと、あるべき姿** | |
| **先取りした列・定義の理由** | |
| 直感に反する処理の理由 | |
| 業務ルールの根拠（本ドキュメントへのリンク） | |

**TODO コメント**: 現状 0件 `[実装]`。今後書く場合は `// TODO({担当}, {期限}): {内容}` とし、**期限の無い TODO は書かない** `[推定]`。

> **本プロジェクトの教訓**: コメントが残っていた箇所は [ADR](../02-architecture/05-adr/) を復元でき、残っていなかった箇所は「復元できず」となった。
> **「なぜ」のコメント1行が、後から数日分の調査を節約する。**

## 9. レビュー観点

> **レビュアーが毎回見るチェックリスト。判定できる項目のみ。**

**セキュリティ（最優先）**

- [ ] 案件を扱うエンドポイントに**所有者チェック**が入っているか
- [ ] 認可判定を**サーバ側**で行っているか（フロントの表示制御は認可ではない）
- [ ] 状態に応じた**編集可否**を検証しているか（提出後の編集を防ぐ）
- [ ] エラーメッセージに内部情報・開発環境固有の文言が漏れていないか

**設計への準拠**

- [ ] 検証定義を `packages/schema` にのみ置いたか（二重定義していないか）
- [ ] ビジネスロジックを controller に直書きせず **service 層**に置いたか
- [ ] 様式項目の追加を、テーブル変更ではなく**定義追加**で吸収できたか
- [ ] **新しい入力パターンを作る前に、既存3パターンで表現できないか**検討したか
- [ ] `cases` への非正規化コピーを**増やしていない**か
- [ ] レイヤーの責務（→ [リポジトリ構成 §5](./02-repo-structure.md)）を越えていないか

**正しさ**

- [ ] エラー時・空データ時の挙動が実装されているか
- [ ] トランザクション境界は適切か
- [ ] `packages/schema` を変更した場合、`build:schema` の必要性をPR説明に書いたか

**保守性**

- [ ] **将来使う列・定義に、先取りの理由をコメントで残したか**
- [ ] **簡易実装であれば、その旨とあるべき姿をコメントに書いたか**
- [ ] 期限の無い TODO を残していないか
- [ ] 簡易実装・既知の制限を [バックログ](../06-roadmap/02-backlog.md) に登録したか
- [ ] 文言を後で辞書化しやすい単位にまとめたか

**ドキュメント**

- [ ] 設計と実装が食い違った場合、設計側を更新したか
- [ ] 設計判断を変えた場合、[ADR](../02-architecture/05-adr/) を追加したか
- [ ] `[推定]` の裏が取れた場合、タグを外して根拠を追記したか

## 10. レビューの進め方

| 項目 | 方針 `[推定]` |
|---|---|
| 指摘の重要度表示 | `must` / `should` / `nits` の3段階を明示する |
| 議論が長引いた場合 | 同期で話す。PR上で往復しない |
| 設計そのものへの疑義 | PRで解決せず、[ADR](../02-architecture/05-adr/) の議論に上げる |
