## 1. 目的と範囲

予算移管の後、業務アプリケーションについて「誰が何に責任を持ち、何を判断し、何をしてはいけないか」をあらかじめ定める。窓口担当が移管対象部門とIT関連業務の扱いを合意するときの標準として使う。

| 対象 | 対象外 |
|---|---|
| 移管対象部門の業務アプリケーションと、その関連ツール（予算移管の対象のほぼすべて） | もともと IT部門が管掌している全社横断の領域（インフラ、データ、セキュリティなど）。従来どおり IT部門が担う |

---

## 2. 原則：プロセスオーナー原則（交渉不可）

> 業務アプリケーションの Accountability（最終責任）は、その業務プロセスと便益に責任を持つビジネス側（プロセスオーナー）に残る。IT部門はシステムオーナーとして関与を強めるが、Accountability は引き取らない。

予算の所在が IT部門に移っても、この原則は変わらない。案件ごとの合意で変えることもできない。

根拠の原文と、各ソースに書かれていること・書かれていないことは、[プロセスオーナー原則の根拠](./02-principle-evidence.md)（BTR-APX-02）に示す。下の表はその要約である。

| 対象 | 根拠 | 根拠が示すこと |
|---|---|---|
| GxP 対象の部門 | EU GMP Annex 11（Glossary・2 Personnel） | プロセスオーナー（業務プロセスに責任を持つ者）とシステムオーナー（システムの可用性・保守、データのセキュリティに責任を持つ者）を分けて定義し、両者と IT の密接な協力を求める |
| | PIC/S PI 011-3 | システムの利用者を所有者（owners）とし、社内・社外の供給者と利用者（regulated user businesses）の責任を分けて管理する。責任は文書で明確に定める |
| | 厚生労働省 コンピュータ化システム適正管理ガイドライン | 各組織の責任と権限をコンピュータ化システム管理規定に明確にする |
| 本社機能（人事・総務・財務） | GxP 規制下のプロセスオーナー原則を援用する | GxP の対象ではないが、同じ原則を全社共通のメッセージとして適用する |
| | 経済産業省「システム管理基準 追補版（財務報告に係るIT統制ガイダンス）」令和6年12月 | IT統制の評価で、「業務プロセスの責任者」を「開発責任者」「システム管理者」と分けて扱う（第Ⅲ章 図表Ⅲ.5-1、p.Ⅲ-35）。IT部門・ユーザ部門・委託先の役割と責任を職務分掌規程等で定め、周知することを統制の例とする（第Ⅳ章 2-(1)-③、p.Ⅳ-9） |
| | 経済産業省「システム管理基準」令和5年版 | 業務要件は利用者・関係者と合意し、文書化して承認を得る（Ⅱ.3.2）。運用の変更・インシデント対応の優先度・サービスレベルは IT部門と利用部門の間で合意し、インシデント対応は利用部門の判断の下で完了する（Ⅱ.5）。IT に関する権限は、それを行使するのに最適な立場にある者に委ねる（ITガバナンス編、p.19） |
| | 金融庁「財務報告に係る内部統制の評価及び監査の基準」（2023年改訂） | 経営者が内部統制の整備・運用に最終的な責任を持ち、組織内のその他の者も自らの業務との関連で整備・運用に役割を担う（Ⅰ.4(1)・(5)） |
| 共通 | Val IT（ISACA）原則6 | 能力の提供と便益の実現について、関係者に適切な Accountability を割り当てる |

- Annex 11 の改訂案（2025年）では、プロセスオーナーとシステムオーナーの定義がなくなる。代わりに、規制を受ける側が全面的に責任を持ち、社内の IT部門は SLA・KPI で監督される運用の担い手として扱われる（BTR-APX-02 §2.2）。どちらの版でも、本書の原則は変わらない。
- ISPE GAMP 5 は原文を確認できていないため、根拠としては引用しない。

## 3. 業務の3つの層

| 層 | 内容 | 例 | 予算移管での扱い |
|---|---|---|---|
| 直接業務 | 組織のミッション・業務分掌に基づく本来の業務 | 業務要件の決定、システムを使った業務、受け入れの確認、部門で行う運用 | 移さない（当然に部門に残る） |
| IT関連業務（中間層） | 直接業務と間接業務の間にあり、予算があったために部門が担ってきた業務 | 投資：予算承認までの企画・見積の取得・申請資料の作成／経費：運用のモニタリング、改善活動、契約の見直しに向けた活動 | **案件ごとに合意する。本書の RACI（After）を標準とする** |
| 間接業務 | 予算に基づく管理と手続き | 予算の管理、契約、発注・検収・支払い | 移す（当然に IT部門に移る） |

## 4. 役割の定義

| 役割 | 略号 | 担う者 | 責任 |
|---|---|---|---|
| ビジネスオーナー（プロセスオーナー） | BO | 移管対象部門の部門長 | 業務プロセスと、業務アプリケーションの要否・目的・便益に最終責任（A）を負う。GxP 対象では Annex 11 のプロセスオーナー |
| 部門担当 | BU | 移管対象部門の担当者 | 業務アプリケーションを使って直接業務を行う。IT関連業務のうち業務側の実務（業務への適合、効果、要望、受け入れの観点）で R を持つ |
| システムオーナー | SO | IT部門の担当（普段の窓口のメンバー） | システムの可用性・保守・データのセキュリティに責任を持ち、IT関連業務のうち技術側の実務（システム化の方針、見積・費用、運用のモニタリング、改善の実施、契約の見直しの材料）で R を持つ。BO に専門的な判断材料を出し、必要なら異を唱える |
| ベンダーマネジメント担当 | VM | IT部門 | 契約と委託先の管理を一元的に担い、SO を支援する（RACI では SO に含める） |
| 事務担当 | AD | IT部門（既存の事務の体制を増強） | 予算の計上・執行の管理と、発注・検収・支払いの手続きを担い、SO を支援する（RACI では SO に含める） |
| 決裁者 | — | 新しいITガバナンス（Tier）で定める（検討中） | 投資の決裁 |

## 5. RACI（標準）

### 5.0 記号の定義とプロジェクト体制

| 記号 | 定義 | 役割（例） |
|---|---|---|
| A | 最終責任。結果に責任を持ち、承認する（1つの活動に1人） | プロジェクトオーナー |
| R | 実行。成果物を作り、期限までに完了させる | プロジェクトマネジャー、領域リード（業務）、技術リード（IT）、開発・導入ベンダー |
| C | 相談。意見を出し、レビューする（成果物の責任は負わない） | SME（有識者） |
| I | 連絡。結果の報告を受ける | 関係部門 |

成果物ごとの RACI（例）

| 成果物 | プロジェクトオーナー | プロジェクトマネジャー | 領域リード（業務） | 技術リード（IT） | 開発・導入ベンダー | SME | 関係部門 |
|---|---|---|---|---|---|---|---|
| プロジェクトチャーター | A | R | C | C | | | I |
| RFP（提案依頼書） | A | C | R | R | | C | |
| 業務要件 | A | C | R | C | C | C | I |
| システム要件 | A | C | C | R/C | R | C | |
| 移行要件 | A | C | R | R/C | R | C | |
| テスト計画 | A | C | C | R/C | R | | |
| 受け入れ基準書 | A | C | R | C | C | C | |

- R を持つリードが成果物を作る。R が複数の成果物は協力して作る。R/C は、ベンダーと分担して作るか、レビューするかを案件ごとに決める。
- IT関連業務は、部門と SO の両方が R を持って協力する。どちらがどこまでを担うかは、案件ごとに協議する。どちらかが C に下がって相手に任せる形にはしない（部門からの丸投げと、IT部門の負担の集中を防ぐ）。
- プロジェクトマネジャーを部門と IT部門のどちらから出すかは、案件ごとに協議し、合意文書に書く。目安：個別開発に近いほど IT部門、パッケージの構成設定が中心なら部門。

RACI は BO・BU・SO の3役で表す。ベンダーマネジメント担当と事務担当は SO を支援するが、RACI では SO に含める。

**Before（初版は1パターン）**：ビジネス側が単独で行っている状態。全ての活動で BO が A、BU が R で、IT部門は関与しないか、相談（C）を受けて関わる。実際の Before が違う案件は、合意のときに Before を書き直してから比べる。

**After**：IT部門の関与を強め、直接業務と IT関連業務の A は BO に残す。IT関連業務は BU と SO で R を分けて持つ。間接業務は SO が A/R を持つ。決めること（要件、サービスレベルの要求、利用ルール、契約を続けるかどうか）は直接業務として部門に残す。

### 5.3 カスタマイズの範囲

案件ごとの合意文書では、標準 RACI を次の範囲でだけカスタマイズする。

| 区分 | 扱い |
|---|---|
| 変えられないもの | A の列（直接業務と IT関連業務は BO、間接業務は SO）。直接業務の行の全体。間接業務の行の全体（ただし経過措置を除く） |
| カスタマイズできるもの | IT関連業務の行のうち、R の分け方（BU と SO がどこまでを担うか）。SO が R を持ち始める時期（段階的に移してよい。上限は2027年度末） |
| 経過措置 | 今の担当が承認済みの文書や記録で定められていて、担当の変更に正式な手続き（例：GxP の変更管理）が要る業務は、手続きが完了するまで Before の担当のまま行う。IT関連業務の扱いが合意の目安（12/11）までに合意できない部分も、合意できるまで Before のまま行う（憲章 第9条第3項・第4項） |
| 書き方 | 標準との差分、理由、見直しの時期、経過措置の手続きの内容と完了予定を書く。事務局が全案件を横並びで確かめる |

## 7. 判断すべきこと・してはいけないこと

| 役割 | 判断すべきこと | してはいけないこと |
|---|---|---|
| ビジネスオーナー（BO） | 投資の要否・目的・期待効果、業務要件、サービスレベルの要求、利用ルール（ライセンスの割当て方針など）、受け入れの可否、改善の優先順位、契約を続けるかどうか、ベンダーの選定（業務への適合）、効果の評価 | IT部門を通さずにベンダーと契約・発注する、全社横断の領域（インフラ・データ・セキュリティ）の方針を単独で変える、Accountability を IT部門に預ける（「IT に任せた」） |
| 部門担当（BU） | 日々の業務での使い方、要望を出すこと、受け入れの確認、IT関連業務の業務側の部分（業務への適合・効果） | 委託先に契約外の作業を直接頼む、追加の発注を約束する、IT関連業務の業務側の R を SO に任せる（丸投げ） |
| システムオーナー（SO） | 技術的な解決策と既存システムとの整合、見積の妥当性、運用品質（SLA）の評価と是正の要求、変更の技術的な影響 | 業務要件や優先順位を決める、投資の要否を決める、BO の承認なしに仕様を変える、Accountability を引き取る、IT関連業務の業務側の R を引き取る |
| ベンダーマネジメント担当（VM） | 契約の条件・形態、交渉の進め方、更新・解約の手続きの時期 | 契約を続けるかどうかを単独で決める、業務要件を変える |
| 事務担当（AD） | 支払い・予算執行の手続きが形式を満たしているか | 検収の中身（業務要件を満たすか）を判断する |

---

## 8. 案件ごとの合意のしかた

1. 窓口担当は、移管対象部門の今のやり方を Before として確かめる（初版の Before と違えば書き直す）。
2. §5 の After をもとに、§5.3 の範囲で IT関連業務の行をカスタマイズし、標準との差分と理由を書く。
3. 担当の変更に正式な手続きが要る業務を洗い出し、経過措置として手続きの内容と完了予定を書く。
4. 1〜3 を合意文書としてまとめ、移管元の責任者（BO）の承認を得る。A が BO に残ることは合意の対象にしない（§2）。
5. 承認された合意文書を保存し、決定記録に登録する（手順は Runbook 窓口担当編 §3.4・§3.5）。
