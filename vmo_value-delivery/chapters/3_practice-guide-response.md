# 第III部：実務ガイド（相談への対応編）

VMOの実務は、利用者からの相談を起点に始まる。相談は「VMOの業務プロセス」の順番ではなく、**利用者が困った順番**でやってくる。したがって本部は、業務プロセス別ではなく、**利用者との接点＝相談の入口別**に実務を整理する。

想定読者はVMOの実務担当者である。相談を受けるときの共通の型と、相談に応じるための基盤業務は第II部で扱った。本部では、第7章〜第10章で11の相談の入口それぞれの実務を扱う。

各節は次の構成で統一している。

- **相談の言葉** — 利用者が実際に口にする形
- **この相談の背後で起きていること** — 相談に至った状況の見立て
- **最初に確認すること** — 初回のやり取りで押さえる項目
- **進め方** — VMOが実行するステップ
- **成果物**／**標準的な所要期間**
- **つまずきどころ** — 実務で失敗しやすい点

<br>

## 第7章：探索フェーズの実務

### 7.1 「どんな選択肢があるのか、相場感を知りたい」

**この相談の背後で起きていること**

予算要求や企画立案の前段階で、まだ何も決まっていない。社内に相談先がなく、ベンダーに直接聞くとそのベンダーの提案に引き寄せられてしまう、という状況にある。この段階で相談が来ることは、VMOにとって最も望ましい。選択肢も交渉余地も最大だからである。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| 解きたい業務課題 | 「製品が欲しい」ではなく「何を解決したいか」に戻す |
| 必須要件と、譲れる要件の区別 | 全部必須にすると選択肢が1つに収束し、価格が動かなくなる |
| 利用規模（ユーザー数、拠点、データ量、想定の増減） | 費用レンジを出すための最低限の変数 |
| 導入を検討している時期 | 予算年度との関係 |
| 既存システムとの関係（置き換え／併用／連携） | 移行コストの有無が総額を左右する |

**進め方**

1. 業務課題を言語化し、要件を必須／任意に分ける
2. 市場にある選択肢を類型で整理する（自社開発／パッケージ／SaaS／既存の拡張など）
3. 類型ごとの費用レンジを、**前提条件を明記して**提示する
4. 次の一手を提案する（情報提供依頼、PoC、予算化、いったん見送り）

**成果物**：選択肢マップ、費用レンジ表（前提条件つき）、次のステップの提案
**標準的な所要期間**：2〜4週間

**つまずきどころ**

- 相場を**単一の数字**で答えてしまう。規模・前提で数倍変わるため、必ずレンジと前提条件をセットで示す
- 1社からの情報だけで組み立てる。少なくとも類型の異なる複数の選択肢を並べる
- この段階でベンダーに具体的な引き合いを出してしまう。以降の競争性が落ちるため、情報収集であることを明示する

<br>

## 第8章：選定・契約フェーズの実務

### 8.1 「RFP・見積依頼の準備を手伝ってほしい」

**この相談の背後で起きていること**

公平に競わせたいが、要件整理・評価基準づくり・比較表作成の工数が重い。現行ベンダーの代替を探すケースでは、現行ベンダーに気づかれる前に準備を進めたい、という事情が加わることがある。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| 要件が文書化されているか | 未文書化なら要件整理から始まり、期間が倍近くなる |
| 評価に参加する人と、その重み付け | 後から評価者が増えると基準が揺れる |
| 候補ベンダーの数と、その選定理由 | 実質1社なら競争は成立しない |
| 現行契約の解約条件と、切替可能な時期 | 切替できない時期にRFPをかけても交渉力にならない |
| スケジュールの制約（稼働希望日、予算年度） | 逆算して各工程の期限を置く |

**進め方**

1. 要件を「必須／任意／評価対象外」の3分類に整理する
2. **評価基準と配点を、提案を受け取る前に確定**し、相談者と合意する
3. RFP／RFQ文書を作成する（要件、評価基準、提出形式、見積の内訳指定、スケジュール）
4. 配布・質疑応答を運営する（質疑と回答は全候補に同一内容で共有する）
5. 回答を比較表に落とし、評価会に提出する

**成果物**：RFP／RFQ一式、評価基準表、比較表、質疑応答記録
**標準的な所要期間**：4〜8週間（要件が未整理なら＋2〜4週間）

**つまずきどころ**

- 評価基準を**提案受領後**に決める。結論に合わせた基準になり、選定の正当性が失われる
- 「一式」の見積を受け入れる。単価と数量の内訳、前提条件の記載を必須にする
- 候補が実質1社。せめて相場検証のための見積を別途取得し、価格の妥当性の根拠を作る
- 準備段階の情報が現行ベンダーに漏れる。文書の配布範囲と保管場所を最初に決める

<br>

### 8.2 「もう決まっている案件を、契約前に確認したい」

**この相談の背後で起きていること**

現場ではすでに実質的に決まっており、内示に近い状態のこともある。この段階でVMOにできるのは選定のやり直しではなく、**条件の妥当性検証と、見落としているリスクの洗い出し**である。ここを取り違えると信頼を失い、次から相談が来なくなる。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| ベンダーにどこまで伝えたか（内示の有無、予算額の開示） | 価格交渉の余地がどれだけ残っているかが決まる |
| 見積の内訳 | 一式表記なら分解を要求する |
| 契約書ドラフトの有無と、どちらの雛形か | ベンダー雛形なら不利な条項が入っている前提で読む |
| 稼働希望日と契約締結の予定日 | 交渉に使える日数の上限 |
| 他社見積の有無 | 比較対象がないと価格の妥当性を主張できない |

**進め方**

1. 価格の妥当性を検証する（内訳の分解、過去案件・他社水準との比較）
2. 契約条項を点検する（SLA、未達時の措置、解約、自動更新、データ返還、再委託）
3. リスクを洗い出し、重大度をつける
4. 交渉可能な論点を抽出し、優先順位をつける（すべては通らない前提で順番を決める）
5. 相談者の代理としてベンダーと交渉する

**成果物**：条件の妥当性メモ、リスク一覧、交渉論点リスト、交渉結果
**標準的な所要期間**：1〜3週間（契約予定日から逆算する）

**つまずきどころ**

- 選定のやり直しを迫る。この段階の役割ではない
- 時間切れで交渉できない。**契約予定日の3週間前**が実質的な相談期限であることを、平時から周知しておく
- 価格だけを見て、自動更新・解約通知期限・データ返還を見落とす

<br>

### 8.3 「契約条件をどう詰めればいいか分からない」

**この相談の背後で起きていること**

価格は交渉できても、SLA・未達時の措置・解約条件といった条項は何を書けばよいか分からない。これらは数年後に効いてくるが、締結時には影響が見えにくい。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| サービスの重要度（停止したときの事業影響） | SLA目標値はここから逆算する |
| 許容できる停止時間と、営業時間外の扱い | サポート提供時間モデルの選定に直結する |
| 扱うデータの機密区分と、保管場所の制約 | データ保護条項の要否 |
| 希望する契約期間と更新方式 | 自動更新にするか、都度更新にするか |
| 想定される利用の増減 | 数量変更の条項が必要か |

**進め方**

1. 重要度を設定する（停止時の事業影響から逆算）
2. SLA項目と目標値を設計する。**計測方式（暦時間か営業時間換算か）と時計の停止条件を必ず定義する**
3. 未達時の措置を設計する（減額、改善計画の提出義務、連続未達時の解約権）
4. 出口条項を設計する（解約通知期限、自動更新の可否、データ返還の形式・期限・費用）
5. ベンダーと交渉する

**成果物**：契約条件シート、SLA定義、交渉記録
**標準的な所要期間**：2〜6週間

**つまずきどころ**

- SLAの計測方式を決めない。「4時間以内に解決」が暦時間か営業時間換算かで、期限が数日ずれる
- 減額幅が小さすぎて抑止力にならない。金額よりも、連続未達時の解約権のほうが効くことが多い
- 自動更新の解約通知期限を管理する仕組みがない。条項を結んだ時点でカレンダーに登録する
- データ返還の形式・期限・費用を決めない。契約終了時に高額な作業費を請求される

> **前提**：SLAは単独では成立せず、SOW（作業範囲記述書）で定義された業務に対してのみ設定できる。契約文書の構造とSOW・SLAの設計は付録F、データ保護・セキュリティの要件は付録Gを参照する。

<br>

### 8.4 契約締結後の引き渡し（オンボーディング）

契約締結は終点ではない。次を済ませたうえで現場に引き渡す。

1. ベンダー台帳への登録（分類、契約金額、満了日、解約通知期限）
2. 業務窓口・技術窓口の任命（自社側とベンダー側の双方）
3. エスカレーション経路の設定（機能的エスカレーションと、管理者への報告経路）
4. アクセス権・アカウント発行（最小権限の確認）
5. キックオフと、SLA／KPIの相互確認
6. 初回レビュー日の設定

実施チェックリストは付録B（B.7）を参照する。

<br>

## 第9章：運用・改善フェーズの実務

### 9.1 「ベンダーの対応品質に納得がいかない」

**この相談の背後で起きていること**

多くの場合、「なんとなく質が悪い」という段階で相談が来る。事実を積み上げないと交渉にならないため、最初の仕事は不満の言語化と証拠化である。サービス仕様やSLAが実態に合っていないことが原因のこともある。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| 具体的な事象と発生日時（できれば3件以上） | 1件では偶発として処理される |
| SLA項目と実績値の有無 | 定義がある項目とない項目を切り分ける |
| すでにベンダーに伝えた内容と、その回答 | 同じ話を繰り返さないため |
| 契約上の該当条項 | 契約に書いていない期待は交渉材料にならない |
| 相談者が望む着地点（改善／減額／担当交代／契約見直し） | ゴールが違えば打ち手が変わる |

**進め方**

1. 事象を記録化する（いつ、何が起き、どの条項・どの期待に反したか）
2. SLA実績と突き合わせ、定義のある未達と、定義のない不満に仕分ける
3. ベンダーへ**書面で**改善を要求する
4. 改善計画を受領し、期限と確認方法を合意する
5. 改善が見られない場合の措置に進む（減額請求、体制変更要求、契約見直し）
6. 定義のなかった項目は、次回更新でSLAに条項化する

**成果物**：事象記録、改善要求書、改善計画、進捗の追跡記録
**標準的な所要期間**：初回要求まで2〜3週間、改善確認まで1〜3ヶ月

**つまずきどころ**

- 感覚のまま伝え、「対応済み」と返されて終わる
- 契約に定義のない項目で改善を求め、平行線になる。定義がないこと自体を次回の交渉論点にする
- 口頭のやり取りだけで記録が残らず、更新交渉のときに材料がない

<br>

### 9.2 「ベンダーから値上げを要請された」

**この相談の背後で起きていること**

値上げ幅が妥当かどうかは、単独の案件だけでは検証できない。他案件の情報と突き合わせて初めて判断できる。ここはVMOの蓄積がそのまま効く領域である。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| 値上げ幅と、根拠として示された内容 | 根拠が示されていないことも多い |
| 通知の時期と、適用希望日 | 交渉に使える日数 |
| 契約上の価格改定条項 | 合意が必要か、通知のみで足りるか、通知期限は守られているか |
| 同一ベンダーとの他の契約 | 交渉テーブルに載せられる材料 |
| 切替の現実性（移行コスト、期間） | 交渉の後ろ盾になるかどうか |

**進め方**

1. 値上げ根拠を分解する（人件費、為替、ライセンス改定、サービス内容の変更、単なる利益率改善）
2. 契約条項を確認する。**通知期限が守られていなければ、その期の適用自体を争える**
3. 他案件・他社水準と比較する
4. 代替案を準備する（他社見積、数量・機能の見直し、複数年契約との引き換え、値上げ時期の分割）
5. 交渉する。同一ベンダーとの他契約もあわせてテーブルに載せる

**成果物**：値上げ根拠の検証メモ、代替案、交渉結果
**標準的な所要期間**：3〜6週間（適用希望日から逆算）

**つまずきどころ**

- 適用日の直前に相談が来て、交渉する時間がない。値上げ通知を受け取った時点でVMOに回す運用にしておく
- 単価だけを見て、数量やスコープの変更を見落とす。実質的な値上げ幅は単価×数量で見る
- 同じベンダーとの他の契約を交渉材料にしない

<br>

### 9.3 「来年度の予算をどう積めばいいか分からない」

**この相談の背後で起きていること**

見当がつかないまま数字を置くと、超過するか、余らせて翌年度の枠を削られる。社内に説明できる根拠を持った数字が要る。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| 対象範囲（どのシステム、どの契約まで） | 範囲が曖昧なまま進めると積み残す |
| 現行の年間実績（契約額と実支払額の両方） | 契約額と実績が乖離していることがある |
| 来年度の増減要因（利用者増、機能追加、値上げ通知、契約満了） | 増減の根拠になる |
| 予算提出の期限 | 見積取得に使える日数 |
| 求められる精度（概算でよいか、確度の高い数字が要るか） | 見積の取り方が変わる |

**進め方**

1. 現行契約の年間実績を集計する（契約額、実支払額、その差の理由）
2. 増減要因を洗い出し、金額影響を見積もる
3. 複数ベンダーから概算見積を取得する（**調達の引き合いではないことを明示する**）
4. 過去の契約実績と突き合わせて妥当性を確認する
5. 前提条件を明記した予算案を作る

**成果物**：予算案（前提条件つき）、根拠資料、増減要因の一覧
**標準的な所要期間**：3〜6週間

**つまずきどころ**

- 概算見積の依頼が調達の引き合いと誤解され、ベンダーに期待を持たせてしまう
- 単年度だけを見て、複数年契約の階段状の増加や、無償期間終了後の増額を見落とす
- 前提を書かずに数字だけを出す。前提がないと、状況が変わったときに説明できない

<br>

### 9.4 「契約が入り組んで、全体が見えない」

**この相談の背後で起きていること**

長年の取引で契約が積み重なっている、1つのシステムに複数ベンダーが関わっている、契約書の原本が見当たらない。この状態では、値上げ交渉も更新判断も切替検討もできない。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| 対象システムと、関与しているベンダー | 分かる範囲でよい。抜けは調査で埋める |
| 契約書の所在（原本、写し、電子） | 見つからない契約があることを前提にする |
| 発注・支払実績データの入手可否 | 契約書がなくても支払実績から実態を復元できる |
| いつまでに整理が必要か | 更新時期や監査対応が背景にあることが多い |

**進め方**

1. 契約書と、発注・支払実績を収集する
2. 突き合わせる。**契約のない支払**と**支払のない契約**を検出する
3. 契約関係図を作成する（システム、ベンダー、契約、金額、満了日）
4. 重複（同一機能に複数契約）と空白（誰も責任を負っていない領域）を特定する
5. 整理案を提示する（統合、解約、更新時期の揃え、契約主体の見直し）

**成果物**：契約関係図、契約一覧、論点と整理案
**標準的な所要期間**：4〜8週間（対象範囲による）

**つまずきどころ**

- 契約書の原本が見つからず止まる。発注・支払実績から実態を復元し、次回更新時に再締結する
- 「とりあえず全部解約」に走る。サービス停止や、他契約の前提条件を壊すリスクを先に確認する
- 整理案を作って終わりにする。実行時期と担当を決めないと元に戻る

<br>

## 第10章：見直し・転換フェーズの実務

### 10.1 「いまの体制が実態に合っていない」

**この相談の背後で起きていること**

利用が増えて手が回らない、あるいは伸びが止まって過剰になっている。どちらも契約時の想定と実態がずれた状態である。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| どの指標で「合っていない」と判断したか | 感覚か、実績データか |
| 利用実績の推移（直近12ヶ月以上） | 一時的な変動か、構造的な変化か |
| 契約上の数量・上限・変更条件 | 契約期間中に変更できるか |
| 変更が可能になる時期 | 更新日まで待つ必要があるか |
| 必要な水準の見立て | 増減の目標値 |

**進め方**

1. 利用実績データを確認し、ずれの大きさと方向を定量化する
2. 契約上、期中に変更できる条件を確認する
3. 必要水準を設定する（過大にも過小にもしない根拠を作る）
4. ベンダーと条件変更を交渉する
5. サポート提供時間の見直しが必要なら、提供時間モデルの選定に進む（付録D）

**成果物**：実態と契約の差分表、変更案、交渉結果
**標準的な所要期間**：4〜8週間

**つまずきどころ**

- 増強は急がれるが、縮小は先送りされる。過剰分は毎月流出し続けるため、同じ優先度で扱う
- 「契約期間中だから変更できない」と諦める。増額を伴う変更はもちろん、減額方向でも次期更新とセットで交渉余地があることが多い

<br>

### 10.2 「いまのベンダーを続けるべきか迷っている」

**この相談の背後で起きていること**

不満はあるが、切り替えるコストとリスクが読めないため判断できない。判断材料を並べるのがVMOの仕事であり、決めるのは相談者である。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| 迷いの理由（価格／品質／技術の陳腐化／体制の不安） | 理由によって打ち手が変わる |
| **現行契約の満了日と解約通知期限** | 最優先で確認する。期限を過ぎていれば今期の選択肢は消える |
| 切替時に許容できる業務停止時間 | 移行方式の制約 |
| 移行に使える自社要員と期間 | 切替の現実性 |
| 現行ベンダーに検討を伝えてよいか | 交渉の進め方が変わる |

**進め方**

1. **継続した場合の条件を、まず交渉で引き出す**（比較の基準になる）
2. 切替候補を調査し、概算費用を取得する
3. 切替コストを積算する（移行作業、**二重稼働期間**、教育、データ移行、業務停止の影響）
4. 継続案と切替案のコストとリスクを並べる
5. 判断材料を提示する。切替を選ぶ場合は移行の段取りと引き継ぎ条件まで設計する

**成果物**：継続案／切替案の比較表、切替時の移行計画案、交渉結果
**標準的な所要期間**：6〜12週間

**つまずきどころ**

- 解約通知期限を過ぎてから検討を始め、自動更新される。**満了日ではなく通知期限から逆算する**
- 切替コストに二重稼働期間を含め忘れ、切替が安く見える
- 現行ベンダーへの伝え方を設計しないまま検討が漏れる。条件改善を引き出せる場合もあれば、サービス品質が落ちる場合もあるため、伝える／伝えないを意図的に決める

<br>

### 10.3 「システムの縮小・廃止を控えている」

**この相談の背後で起きていること**

保守体制の縮小や契約終了に向けて、複数ベンダーにまたがる契約を整理する必要がある。期限のある作業が多く、1つ逃すと費用が丸1年分発生することがある。

**最初に確認すること**

| 確認項目 | 補足 |
|---|---|
| 廃止・縮小の予定日 | すべての逆算の起点 |
| 関与している契約の一覧 | 保守、ライセンス、回線、監視など漏れやすい |
| 各契約の解約通知期限 | **最も期限が早いものが実質的な決定期限になる** |
| 残すべきデータと、その保存期間 | 法令・監査要件を確認する |
| 後続システムの有無と移行の要否 | 並行期間の必要性 |

**進め方**

1. 契約を棚卸しする（契約書、支払実績の両面から）
2. 解約通知期限から逆算してスケジュールを作る
3. データの返還・削除を要求する（形式、期限、削除証明の取得）
4. ドキュメント・ナレッジの引き渡しを受ける
5. 最終精算を行う（**前払分の返還、未払分の確定、違約金の確認**）
6. アクセスを遮断し、台帳を更新する

**成果物**：契約棚卸し表、解約スケジュール、データ削除証明、最終精算結果
**標準的な所要期間**：90日前の着手が目安（解約通知期限が長い契約があればさらに前倒し）

**つまずきどころ**

- 解約通知期限を1社でも逃し、1年分の費用が発生する
- 前払い分の精算を請求し忘れる
- ドキュメントとデータを受け取る前にアクセスを遮断してしまい、取り返せなくなる

実施チェックリストは付録B（B.7）を参照する。
