# 構成メモ ── 理論・分析／設計／実践 の3層整理

自分用の設計メモ。各層で何を言い、何を言わないかを固定するためのもの。
拡張子（md / html / docx / pptx / png）で分かれている現状を、**論の階層**で切り直す。

---

## 0. 切り方の原則

| 原則 | 内容 |
|---|---|
| 層は「読者」で決まる | 同じ内容でも、誰に向けて何を言うかが変われば別の層の別ファイルになる |
| 拡張子は層を決めない | md/html/docx/pptx は表現形式であって階層ではない。生成物（HTML・統合版）は層から外に出す |
| 語彙が層の境界 | 経済学の言葉 → ガバナンスの言葉 → 業務の言葉。翻訳されずに下の層へ漏れたら設計ミス |
| 上の層は処方箋を語らない | 診断が処方箋を含むと、診断の中立性（＝説得力）が落ちる |

---

## 1. 理論・分析層 ── 「なぜそうなるのか」

**論旨（一文）**
> IT共通基盤の過小投資も、投資委員会の機能不全も、規律や意識の問題ではなく、外部性から演繹される構造的必然である。

**守備範囲 — 二本の診断が並ぶ**

| 系譜 | 問いの起点 | 導かれる症状 |
|---|---|---|
| Part 2（予算配分の層） | 予算を誰が持つか | ① 基盤が育たない（公共財）② 負債が溜まる（負の外部性）③ IT部門が飽和する（コモンズ）④ 是正の起点がない（情報の非対称性） |
| Part 2-B（審議機構の層） | 決定を誰が・どこで作るか | ① 会議が判断の場にならない（コモンズ）② 資料が膨らむ（影響活動コスト）③ 決定が遅れる（取引コスト）④ 承認が終点になる（不完備契約） |

両者は別問題ではなく、**同じ外部性の二つの発現層**。予算構造の外部性を是正するために置かれた機構（投資委員会）が、その内部で同じ外部性を再生産している。

- 共通の理論基盤：外部性・コモンズの悲劇・フリーライダー問題と、確立された処方箋の型（Part 1）
- 結論として引き渡す設計要件
  - Part 2 から：**測定 / 所有権 / インセンティブ再設計**
  - Part 2-B から：**チャネルの分離 / 生産主体の分離 / 時間軸の延長と主体の分離**

**言わないこと**

- 具体的な制度案（IT Materiality、投資委員会、CMS、AI）── すべて設計層
- 特定部門・特定案件の名指し。犯人探しの匂いが出た時点で診断として死ぬ
- 「だから◯◯すべきだ」。要件の提示までで止める

**語彙** — 外部性 / 過小供給 / コモンズ / フリーライダー / ピグー / Ostrom

**所属ファイル**

| ファイル | 位置づけ |
|---|---|
| 統合版 Part1（＝html/00_Externality_and_Commons.html） | 一般理論。自社の話は一切出さない |
| 統合版 Part2（＝html/01_IT_Investment_Market_Failure.html） | 予算配分の層の診断 |
| 審議機構の構造分析_Part2B.md | 審議機構の層の診断。企画書1章の P1〜P4 を分析層へ引き上げたもの |
| it_governance_framework.png | 全体の見取り図。Materiality が ITガバナンス6原則の1つであることの位置づけ |

**現時点の欠落**

- Part 2・Part 2-B の症状はいずれも「構造から演繹された」もので、**自社の実データによる裏づけがない**。事実項目の蓄積（実践層）が回り始めたら、ここに実証を足せる
- Part 2-B を書いたことで、企画書1章の P1〜P4 は**診断ではなく参照**になった。企画書側を「Part 2-B のとおり」と受ける形に書き換えるか、現状の重複を許すかは要判断

## 2. 設計層 ── 「どう解くか」

**論旨（一文）**
> 外部性を測る軸を立て、共通層の持ち主を定め、判定を予算に接続する。そのうえで、それを回す事務局機能自体を非同期・文書駆動へ作り替える。

**守備範囲 — この層は二階建てになっている**

| 系譜 | 何を決めるか | 応答している診断 | 主ファイル |
|---|---|---|---|
| A. 判断ルール | 全社として何を・どの軸で判断するか（第3の軸／共通層オーナー／予算接続／段階導入） | Part 2 の4症状 | 統合版 Part3 |
| B. 運営プロセス | それを誰が・どう回すか（4ステップ／権限分離／CMS／AIエージェント事務局） | Part 2-B の4症状 | 投資委員会プロセス改善企画.docx |

二階建てであること自体は問題ではない。**それぞれが分析層に足場を持っている**ことが条件で、Part 2-B の追加でその条件は満たされた。

**言わないこと**

- 理論の再説明。Part1・Part2 を参照するだけにとどめる（引き写すと論の重心がぼやける）
- 実装詳細（画面仕様、ツール選定）。設計論点として何を確定すべきかまでで止める

**語彙** — 判断軸 / オーナーシップ / 予算接続 / 権限分離 / framing / reviewability / SLA

**所属ファイル**

| ファイル | 位置づけ |
|---|---|
| 統合版 Part3（＝html/02_IT_Materiality_Proposal.html） | 系譜A。判断ルールの設計 |
| 企画書/投資委員会プロセス改善企画.docx | 系譜B。運営プロセスの設計。図1・図2・シーケンス図はその挿図 |
| practice/投資委員会_審議プロセス.md | 系譜Bのプロセス定義（Mermaidソース）。運用の**規範**なので設計層に置く |

**解消済みの論点（2026-07-26）**

かつて系譜Bは分析層に足場を持たず、企画書1章の P1〜P4 が診断と設計を兼ねていた。Part 2-B を分析層に置いたことで、A・B とも「診断 → 設計」の一直線に整列した。企画書1章は今後、Part 2-B の**要約と参照**に位置づけを変える。

**未決の設計論点**（企画書5.3、確定させないと運用に落とせない）

- Q1. AIエージェントの設定（ルール・閾値・プロンプト）を誰が所有し、変更に誰の承認を要するか
- Q2. トリアージで軽レーンに振った案件のサンプリング監査／異議申立ての制度化

## 3. 実践層 ── 「実際に相手に渡すもの」

**論旨（一文）**
> 相手に求めるのは事実だけ。判断の理屈は、こちらが平易な業務言語で説明する。

**守備範囲**

- 事業部門への依頼（何を書いてほしいか、なぜ評価は不要か）
- 起案者への回答（どう判断したか、条件は何か）
- その実例

**言わないこと ── ここが最も重要**

- 経済学用語を一切使わない。企画書2.2 が自ら課しているルール（理論は事務局内部の運用規律であり、対外文書では前面に出さない）
- 「フレームワークに基づき」という説明。判断根拠は毎回、その案件の言葉で述べる
- 設計の未完了部分（Q1・Q2、AI事務局構想）。対外文書に滲ませない

**語彙** — 受益範囲 / 連携システム / 保守期限 / 条件付き承認 / レビューゲート / 較正

**所属ファイル**

| ファイル | 読者 | 何を言っているか |
|---|---|---|
| ppt/IT投資予算_申請プロセスと注意事項.pptx | 事業部門 全体 | 事実項目を書いてください、評価は不要です／不採択でもIT枠で拾う道がある |
| practice/論点整理書_グローバルタレントデータ基盤.md | 起案者（Step1） | 事務局が整理した論点はこれです、異論があれば出してください |
| practice/審議回答書_グローバルタレントデータ基盤.md | 起案者（Step2） | 論点ごとにこう判断しました、承認条件はこれです |

**検証** — 実践層の3ファイルを読み返し、経済学用語が1つも出てこないことを確認する。出てきたら層の境界が破れている。現状の回答書は「通常の費用対効果基準ではなく、どれだけ多くの部門が必要としているか」と書いており、外部性という語を使わずに外部性を説明できている。この水準を基準線にする。

## 5. 正本の所在（2026-07-26 決定）

**HTMLを正本とする。** 層はフォルダではなく、index.html の3ブロックとページ採番で表現する。Markdownで層フォルダを作る案は採らなかった（拡張子が md / docx / pptx に散らばったままでは、どのみち一元化できないため）。

| 種別 | 扱い |
|---|---|
| html/00〜05 | **正本**。以後の加筆修正はここに入れる |
| docx・pptx | **副本**。配布用。内容は html/04・05 と同一に保つ |
| practice/ の3つの md | **参考資料**。Mermaidソースと実案件の Step1・Step2 文書。HTMLからリンクする |

| 本書 | **内部台帳**。対外HTMLには出さない。層の設計思想・未決論点・次にやることを管理する |
