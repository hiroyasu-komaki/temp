# 第8章　社内共通AIリスク評価テンプレートの設計

> **この章の位置づけ**：すべての生成AI案件に使う共通の評価テンプレートと審査の仕組みを設計する
> **対象読者**：セキュリティガバナンス担当、審査担当、案件担当

## 要旨

- テンプレートは4つの柱で設計する：①**事前分類による設問の絞り込み**、②**ガバナンス設問（NIST）と技術設問（OWASP）の2層構成**、③**リスク水準に応じた段階的審査（Tier）**、④**結果の集約と報告**。
- 事前分類の3軸（データの機密性・アーキテクチャ・出力の自律性）に **Rule of Two** を加え、Tier を機械的に判定できるようにする。
- 現場は OWASP の ID で回答・記録し、経営には NIST の機能と AI 600-1 のリスク区分で集約して報告する。**同じ回答データから両方の目線の報告を出す**ことが、経営と現場の目線合わせの仕組みになる。
- 本章の判定ロジックと閾値は**設計案**であり、リスク許容度（GOVERN 1.3、MAP 1.5）の決定とあわせて確定する。

## 8.1 設計の柱

| 柱 | 内容 | 狙い | 根拠（AI RMF） |
|---|---|---|---|
| ① 動的テーラリング | 事前分類の回答に応じて、回答すべき設問だけを展開する | 低リスク案件の負担を減らし、高リスク案件に審査資源を集中する | GOVERN 1.3（リスク許容度に応じた活動レベル） |
| ② 2層構成 | 全案件共通のガバナンス設問＋構成に応じた技術設問 | 「責任と判断」と「実装と検証」の両方を漏れなく確認する | GOVERN 1〜6／MEASURE 2.7 |
| ③ 段階的審査 | Low／Medium／High で審査者と必要な証跡を変える | 審査の質と速度の両立 | GOVERN 2.3、MANAGE 1.1 |
| ④ 集約と報告 | 回答を NIST・OWASP の両方の切り口で集計する | 経営と現場の目線合わせ、監査対応 | GOVERN 4.2、MANAGE 1.4 |

## 8.2 事前分類（最初に答える5問）

| # | 分類軸 | 選択肢 | 展開される設問 |
|---|---|---|---|
| Q1 | 入力・参照するデータの機密性 | 公開／社内限定／機密（個人情報・未公開財務・営業秘密など） | 「機密」で LLM02 の強化段階、LLM09 の分離要件を追加 |
| Q2 | アーキテクチャ | 単体チャット／RAG／エージェント（ツール実行・MCP）／ファインチューニング | RAG：LLM02・LLM09／エージェント：LLM03・LLM06 と Agentic Top 10 全体／ファインチューニング：LLM04・LLM05 |
| Q3 | 出力の自律性 | 下書き（人が使う）／人の承認後に実行／完全自動実行 | 「承認後」「完全自動」で LLM03・LLM07・ASI09 を追加 |
| Q4 | 提供形態 | 外部SaaSの利用／社内構築（外部APIのモデル）／社内構築（自社運用のモデル） | 外部SaaS：提供者審査・契約（LLM04、GOVERN 6）／自社運用：推論基盤の堅牢化（LLM06）・モデルの出所（LLM04） |
| Q5 | Rule of Two | (A)非信頼入力を扱う／(B)機密データにアクセスする／(C)状態変更・外部通信ができる（それぞれ有無） | 3つそろう：操作ごとの人の承認を必須／2つ：残留リスク評価を必須 |

## 8.3 Tier 判定（設計案）

| Tier | 判定条件（いずれかに該当） | 例 |
|---|---|---|
| **High** | Q5 で A・B・C の3つがそろう／Q3 が「完全自動」かつ Q5 の C が有り／Q1 が「機密」かつ Q2 が「エージェント」または「ファインチューニング」／社外の顧客・取引先が直接使う | 社内システムを更新する業務エージェント、顧客対応の自動返信 |
| **Medium** | Q5 で2つがそろう／Q1 が「機密」／Q2 が「RAG」または「エージェント」 | 機密文書を検索する社内FAQボット、参照のみのエージェント |
| **Low** | 上記に該当しない | 公開情報のみを扱う文章作成支援、翻訳 |

## 8.4 Tier ごとの審査

| 項目 | Low | Medium | High |
|---|---|---|---|
| 評価 | セルフチェック | セルフチェック＋セキュリティ担当の確認 | セルフチェック＋専門部会（セキュリティ・法務・AI推進）の審査 |
| 必須の検証 | チェックシートの記入 | 導入前テスト（間接注入・権限外文書・出力のエスケープ） | 独立した評価者による**レッドチーミング**（防御仕様を開示した適応型攻撃を含む） |
| 残留リスクの受容者 | 案件オーナー | 部門長 | 経営層（エグゼクティブ・リーダーシップ） |
| 再評価の契機 | 構成変更時 | 構成変更時＋年次 | 構成・モデル変更時＋半期＋インシデント時 |
| 根拠（AI RMF） | GOVERN 1.3 | MEASURE 1.3（第一線の開発者以外の評価者） | GOVERN 2.3（経営の意思決定責任）、MANAGE 1.4（残留リスク） |

## 8.5 設問の2層構成

### 第1層：ガバナンス設問（全案件共通・NIST）

AI RMF のサブカテゴリと、Playbook の「Transparency & Documentation」の問いから設問を作る。

| 区分 | 設問例 | 根拠 |
|---|---|---|
| 目的と法規制 | 利用目的・利用者・利用環境が文書化されているか。適用される法規制（個人情報、各国のAI規制）は特定されているか | MAP 1.1、GOVERN 1.1 |
| 台帳 | AI資産台帳に登録したか（基盤モデルとバージョン、データの来歴、既知の問題、ヒューマンオーバーサイトの役割、知的財産・機密データの扱い） | GOVERN 1.6、AI 600-1 GV-1.6-003 |
| 責任 | 案件オーナー、運用責任者、停止の判断者は誰か | GOVERN 2.1、MANAGE 2.4 |
| 人の関与 | どの操作で人が確認・承認するか。知識の限界は利用者に示されているか | MAP 2.2、MAP 3.5 |
| サードパーティ | モデル・データ・ツールの提供者の審査と、障害時のコンティンジェンシーはあるか | GOVERN 6.1、6.2 |
| 監視と対応 | 稼働中の監視項目、インシデントの通知先、停止・廃止の手順はあるか | MEASURE 2.4、MANAGE 4.1、4.3、GOVERN 1.7 |

### 第2層：技術設問（事前分類で展開・OWASP）

第7章のチェックシートを設問化する。各設問には OWASP の ID を付け、回答は「実施済み（証跡あり）／一部／未実施／該当なし」の4択とする。

| 展開条件 | 設問の例 | ID |
|---|---|---|
| 全案件 | 外部コンテンツを非信頼として扱い、指示と分離しているか／隠されたコンテキストに資格情報や認可ロジックを置いていないか／出力を下流に渡す前に検証・エンコードしているか／トークン・コストの上限はあるか | LLM01, LLM08, LLM10, LLM06 |
| RAG | 権限をインデックス照会の中で適用しているか／機密区分の異なる文書を分離しているか／出典を表示しているか | LLM02, LLM09, LLM07 |
| エージェント | ツールの機能・権限は最小か／ユーザーのコンテキストで実行するか／不可逆操作に人の承認があるか／ステップ数・コストの上限とキルスイッチはあるか／MCPサーバのバージョン固定と署名検証をしているか | LLM03, ASI02, ASI03, ASI08, ASI04 |
| ファインチューニング・自社運用 | 学習データの出所と検証、モデル成果物の署名とハッシュ固定、トリガー探索のレッドチーミング | LLM04, LLM05 |

## 8.6 集約と報告：経営と現場の目線合わせ

### 現場が記録するもの（案件単位）

- 事前分類の回答と Tier
- 技術設問ごとの回答（OWASP の ID 付き）と証跡
- 未実施項目の理由、代替策、残留リスク、受容者

### 経営に報告するもの（全社集約）

同じ回答データを、第6章の公式対応表で NIST の切り口に変換して集計する。

| 報告の切り口 | 内容 | 使う対応表 |
|---|---|---|
| Tier 別の案件数と審査状況 | High 案件の件数、審査待ち、受容された残留リスクの件数 | — |
| AI RMF 機能別の充足状況 | GOVERN／MAP／MEASURE／MANAGE ごとの未実施項目 | Top 10 付録A（AI RMF） |
| AI 600-1 リスク別の露出 | 情報セキュリティ・データプライバシー・情報の完全性などの未対策件数 | Top 10 付録A（AI 600-1） |
| CSF 2.0 との接続 | 既存の CSF 運用で手当てが必要なサブカテゴリ | GenAI Security Crosswalk（CSF 2.0） |
| 頻出する未対策リスク | OWASP ID 別の未実施件数（全社で弱い対策の特定） | — |

**運用上のポイント**：経営からの方針（例：「エージェントの不可逆操作は必ず人が承認する」）は、技術設問の「必須」指定として現場に降ろす。現場の未実施項目は、上の切り口で経営の判断材料に上がる。この往復が回っている状態を、第1章で定義した「ガバナンスが安定した状態」とする。

## この章の結論

- 事前分類5問（Rule of Two を含む）で Tier と設問を決め、審査資源を高リスク案件に集中させる。
- ガバナンス設問は AI RMF と Playbook、技術設問は OWASP から作り、両者を ID で追跡できるようにする。
- 同じ回答データから、現場向け（OWASP）と経営向け（NIST）の両方の報告を出す。
