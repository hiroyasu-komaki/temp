# 第7章　ユースケース別リスクチェックシート

> **この章の位置づけ**：代表的な2つの構成について、NIST AI RMF の機能ごとに OWASP のチェック項目を展開した実例を示す
> **対象読者**：案件担当、アーキテクト、セキュリティレビュー担当

## 要旨

- 2つの代表構成を扱う：**ケース1 社内FAQボット（RAG型）**と**ケース2 チャットUI＋ハーネス型（エージェント型）**。NIST COSAiS の区分では、それぞれ「生成AIの適応・利用」「AIエージェントシステムの利用（単一エージェント）」に当たる。
- RAG型の焦点は**データの境界**（検索前の認可・漏洩・誤情報）、エージェント型の焦点は**行動の境界**（権限・承認・ループ・出力の描画）である。
- 各行は「NIST の機能 → チェックポイント → OWASP のリスク → 対策・運用要件 → 根拠サブカテゴリ」で構成し、現場の記録（OWASP）がそのまま経営向けの集約（NIST）につながるようにしている。

## 7.1 構成の比較

| 観点 | ケース1：社内FAQボット（RAG型） | ケース2：チャットUI＋ハーネス型（エージェント型） |
|---|---|---|
| 主な処理 | 社内文書を検索し、根拠付きで回答を生成する | AIが外部ツール・API・MCPサーバを動的に選んで実行する |
| モデルの役割 | 部品 | 行為者 |
| 適用するリスクリスト | LLM Top 10 | LLM Top 10 ＋ Agentic Top 10 |
| Rule of Two（第4章 LLM01） | (A)非信頼入力：文書経由で有り得る／(B)機密データ：有り／(C)状態変更・外部通信：**無し**（参照のみに限定） | (A)(B)(C) **すべて有り得る** → 操作ごとの人の承認が必要 |
| 最優先で審査するリスク | LLM02 × LLM09（漏洩と検索の権限）、LLM07（誤情報） | LLM03 × LLM01（権限と注入）、ASI02／ASI05、LLM06 |

## 7.2 ケース1：社内FAQボット（RAG型）

| NIST 機能 | チェックポイント | 関連 OWASP | 対策・運用要件 | 根拠（AI RMF） |
|---|---|---|---|---|
| **GOVERN** | 入力ルールの明確化 | LLM02 | 入力禁止データ（個人情報・未公開の財務情報など）を利用方針に明記。提供者との契約で学習不使用・保持なしを確認し、技術的にも強制する | GOVERN 1.1, 6.1 |
| GOVERN | 機能と権限の限定 | LLM03 | ボットの役割を「情報参照」に限定し、書き込み・送信の機能を持たせない（Rule of Two の C を外す） | GOVERN 1.3 |
| GOVERN | 台帳への登録 | LLM04 | モデル・バージョン、埋め込みモデル、接続するデータソース、責任者を AI資産台帳に登録（AI 600-1 GV-1.6-003） | GOVERN 1.6 |
| **MAP** | データソースの権限と機密区分の特定 | LLM02, LLM09 | 接続するドライブ・ナレッジベースの権限設定を棚卸しし、過剰共有を解消してから接続する（直すべきはデータ側）。機密区分の異なる文書は同じインデックスに混在させない | MAP 4.2 |
| MAP | 間接プロンプトインジェクションの経路 | LLM01, LLM05 | 外部・利用者投稿など、誰が文書を書き込めるかを特定し、信頼度で区分する | MAP 4.1 |
| MAP | 誤情報の業務影響 | LLM07 | 回答が使われる業務判断を特定し、誤答時の影響と人による確認の要否を決める | MAP 3.5, 5.1 |
| **MEASURE** | 導入前テスト | LLM01, LLM02, LLM10 | 文書に仕込んだ指示による間接注入テスト、権限外の文書が回答に出ないかの確認、画面表示前のエスケープの検証 | MEASURE 2.7 |
| MEASURE | 根拠性の評価 | LLM07 | 回答と参照元の一致（根拠性）・一貫性を評価指標にする。確信度だけに頼らない | MEASURE 2.5 |
| MEASURE | 稼働中のモニタリング | LLM06, LLM09 | 利用量・コスト・検索の異常（特定文書の過剰な検索ヒット）を監視 | MEASURE 2.4 |
| **MANAGE** | **検索前の認可** | LLM02, LLM09 | 質問者の権限（ロール）をインデックス照会の中で適用し、チャンク単位で制御する。検索後のフィルタに頼らない | MANAGE 1.3 |
| MANAGE | 出典の表示 | LLM07 | 回答に参照元の文書名・該当箇所を必ず表示し、利用者が検証できるようにする | MANAGE 2.2 |
| MANAGE | 入出力ガードレール | LLM01, LLM02, LLM10 | 不可視文字の除去、個人情報・機密語の分類器によるマスク、Markdown 画像・外部リンクの自動描画を無効化 | MANAGE 1.3 |
| MANAGE | 利用上限 | LLM06 | ユーザー単位のトークン上限と、アカウント単位の上書き不能な支出上限 | MANAGE 1.3 |
| MANAGE | 埋め込みのライフサイクル | LLM09 | 元文書削除時に埋め込みも削除。ベクトルDBのバックアップを元文書と同じ機密区分で管理。インシデント手順で「埋め込みのみの漏洩」を原データ漏洩として扱う | MANAGE 4.1, 4.3 |

## 7.3 ケース2：チャットUI＋ハーネス型（エージェント型）

| NIST 機能 | チェックポイント | 関連 OWASP | 対策・運用要件 | 根拠（AI RMF） |
|---|---|---|---|---|
| **GOVERN** | 承認が必要な操作の定義 | LLM03, ASI02, ASI09 | 不可逆・外部に見える操作（削除・送信・支払・デプロイ）を方針で定義し、人の承認（Human-in-the-loop）を必須にする。可逆・軽微な操作は自動承認とする段階的な運用 | GOVERN 1.3, MAP 3.5 |
| GOVERN | ツール・MCPサーバの審査 | LLM04, ASI04 | 利用するハーネス・MCPサーバ・プラグインを台帳に登録し、バージョン固定・署名検証・脆弱性スキャンを行う。ツール説明文に隠された指示がないか確認 | GOVERN 6.1, MANAGE 3.1 |
| GOVERN | エージェントのID管理 | ASI03 | エージェントを非人間IDとして管理し、短命でタスクに紐づく資格情報を発行する | GOVERN 2.1 |
| **MAP** | Rule of Two による構成評価 | LLM01, LLM03 | 非信頼入力・機密データ・状態変更／外部通信の3要素の有無を記録。3つそろう場合は操作ごとの承認、2つの場合は残留リスク評価 | MAP 4.1 |
| MAP | 間接注入の経路 | LLM01, ASI01 | ツールの取得データ（Web、メール、課題管理、他エージェントの出力）を非信頼として列挙し、指示プロンプトと分離して渡す | MAP 4.1 |
| MAP | 隠されたコンテキストの中身 | LLM08 | システムプロンプト・ツール定義に資格情報や認可ロジックを置いていないか確認（**隠されたコンテキストは見つかる前提**で設計し、非表示に頼らない） | MAP 4.2 |
| **MEASURE** | 適応型攻撃者を想定したレッドチーミング | LLM01, ASI01 | 防御仕様を開示した状態で、目標の乗っ取り・ツール誤用シナリオを検証。静的テストの成功率だけで判断しない | MEASURE 2.7, 1.3 |
| MEASURE | 出力描画の検証 | LLM10 | チャットUIでの XSS、Markdown 画像経由のデータ持ち出し、制御文字の扱いをテスト | MEASURE 2.7 |
| MEASURE | ループ・消費の検証 | LLM06, ASI08 | 再試行・自動呼出の暴走、ツール呼出のファンアウトを負荷試験で確認 | MEASURE 2.6 |
| **MANAGE** | 完全仲介 | LLM03, ASI02, ASI03 | 許可の判断をLLMに任せず、ツールまたは独立したポリシー判定点で各操作を検証。ユーザーのコンテキストと認可範囲を多段の呼出でも引き継ぐ | MANAGE 1.3 |
| MANAGE | 出力のサニタイズ | LLM10, ASI05 | HTML/JS のサニタイズ（DOMPurify 等）、CSP、Markdown 画像・リンクプレビューの既定無効化。生成コードはサンドボックスで実行し、レビューなしにデプロイしない | MANAGE 1.3 |
| MANAGE | サーキットブレーカー | LLM06, ASI08 | ステップ数・再帰深度・実行時間・実行ごとのコスト上限を設定し、状態ハッシュでループを検知 | MANAGE 1.3 |
| MANAGE | セッション・メモリの隔離 | LLM02, ASI06 | ユーザー・セッション単位でメモリを分離。メモリへの書き込みを特権操作として記録し、指示を含む記憶の永続化には承認を求める | MANAGE 1.3 |
| MANAGE | 監視とキルスイッチ | LLM03, ASI10 | 目標・ツール呼出・エージェント間メッセージを記録し、基準値からの逸脱を検知。緊急時にセッション遮断・資格情報失効・ロールバックができる | MANAGE 2.4, 4.1 |

## 7.4 チェック項目が異なる理由

| | ケース1（RAG型） | ケース2（エージェント型） |
|---|---|---|
| 主なリスクの源 | 静的な文書の検索と回答生成 | AIが外部ツールやAPIを動的に判断・実行すること |
| 焦点 | **データの境界**：誰がどの文書を見られるか、何が漏れるか、誤答をどう検証させるか | **行動の境界**：何をしてよいか、誰が承認するか、暴走をどう止めるか、出力をどう安全に描画するか |
| 決定的な対策 | 検索前の認可、データ側の過剰共有の解消、出典表示 | 最小エージェンシー、完全仲介、人の承認、サーキットブレーカー |
| 侵入された場合の被害 | 情報漏洩、誤った業務判断 | 情報漏洩に加え、データ破壊・不正送信・不正実行 |

## この章の結論

- 同じ「生成AI」でも、RAG型はデータの境界、エージェント型は行動の境界が審査の中心になる。
- Rule of Two で3要素を記録すると、承認の要否を機械的に決められる（第8章の Tier 判定に使う）。
