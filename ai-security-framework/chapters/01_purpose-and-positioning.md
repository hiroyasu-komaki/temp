# 第1章　目的と位置づけ

> **この章の位置づけ**：本資料が何を解決し、NIST を前提とした既存のセキュリティガバナンスにどう AI セキュリティを組み込むかを示す
> **対象読者**：経営層・CISO、IT部門（セキュリティガバナンス担当・アーキテクト・案件担当）

## 要旨

- **目的**：NIST を前提としたセキュリティガバナンス（CSF 2.0 導入済み）のもとで **AIセキュリティのケイパビリティを導入し、ガバナンスを安定させる**こと。
- 生成AI（LLM・RAG・AIエージェント）は、従来の管理では捕捉しきれないリスク（プロンプトインジェクション、過剰な権限委譲、誤情報に基づく自動実行など）を持ち込む。既存の枠組みを置き換えるのではなく、**NIST AI RMF／AI 600-1 を既存のガバナンスに追加**し、**OWASP GenAI Security Project で具体化**する。
- OWASP にはもう1つの役割がある。**経営と現場の目線を合わせる共通言語**である。経営は「どのリスクを、どの水準で受容するか」を NIST の言葉で判断し、現場は「何を防ぎ、どう確かめたか」を OWASP の言葉で報告する。両者を公式の対応表でつなぐことで、同じリスクを同じ物差しで語れるようにする。
- 成果物は、ユースケース別チェックシート（第7章）、社内共通AIリスク評価テンプレートの設計（第8章）、段階的な導入計画（第9章）である。

## 1.1 なぜ既存のセキュリティ管理だけでは足りないのか

生成AIには、従来のアプリケーションにない構造的な性質がある（AI RMF 付録B「AIのリスクは従来のソフトウェアのリスクとどのように異なるか」も参照）。

| 性質 | 何が起きるか | 代表的なリスク |
|---|---|---|
| 指示とデータの区別がない | LLMはシステムプロンプト・ユーザー入力・検索結果・ツール出力を同じトークン列として処理するため、SQLのパラメータ化に相当する「確実な分離」が存在しない | LLM01 プロンプトインジェクション |
| 出力が確率的 | 同じ入力でも出力が変わり、もっともらしい誤り（作話）が混ざる | LLM07 誤情報 |
| 権限の委譲 | エージェントはツールを自律的に選び、ユーザーの権限で外部システムを操作する | LLM03 過剰な権限、ASI02 ツールの誤用 |
| データの残留 | 学習・埋め込み・メモリに入ったデータは、元データを消しても抽出されうる | LLM02 機密情報の漏洩、LLM09 ベクトル・埋め込みの弱点 |
| 新しいサプライチェーン | 事前学習モデル・LoRAアダプタ・MCPサーバなど、検査が難しい部品に依存する | LLM04 サプライチェーン、ASI04 |

OWASP（2026年版）は冒頭で「騙されないモデルを作ろうとするのをやめ、モデルが騙されても重要なものが壊れないようにシステムを設計せよ」と述べている。本資料もこの立場を採る。**モデル単体の安全性ではなく、モデルを取り囲むシステム（権限・データ境界・出力処理・人の承認・監視）を管理対象とする。**

## 1.2 前提：NIST を前提としたセキュリティガバナンス

| 項目 | 前提・方針 |
|---|---|
| 既存のガバナンス | **NIST CSF 2.0 が導入済み**。方針、リスク評価、資産管理、サプライチェーン管理、監視、インシデント対応が CSF に沿って運用されている |
| 追加するもの | **NIST AI RMF 1.0 と AI 600-1** を、AIシステムに固有の管理観点として既存のガバナンスに組み込む |
| 具体化の手段 | **OWASP LLM Top 10 2026／Agentic Top 10 2026** をチェック項目・設計原則・テスト観点として案件に適用する |
| 新設しないもの | AI専用の別体系・別組織。既存の CSF の運用（監視・データ保護・権限管理・サプライチェーン管理）の範囲に生成AIを含めることを優先する |

AIセキュリティを独立した別体系として立てない理由は2つある。

1. **AIリスクの多くは既存の統制の延長で扱える**。サプライチェーン管理（CSF GV.SC）、アクセス制御、脆弱性管理、インシデント対応はAIにもそのまま必要で、追加すべきはAI特有の観点である。OWASP Crosswalk でも、10リスクの主要な対応先は DE.CM（監視）、PR.DS（データ保護）、PR.AA（権限）など既存の CSF サブカテゴリに集中している（第6章）。
2. **NIST自身が CSF と AI RMF を接続する方向にある**。NISTは CSF 2.0 を AI に適用する「Cyber AI Profile（NIST IR 8596、準備草案 2025年12月）」を策定中で、AI RMF とのマッピングも予定している（第2章）。

## 1.3 「ガバナンスが安定した状態」とは

導入の到達点を、次の状態として定義する。第9章のロードマップはこの状態に向けて段階を切る。

| 観点 | 安定した状態 | 根拠（AI RMF） |
|---|---|---|
| 把握 | 社内の生成AIシステムがすべて台帳に載り、構成要素（モデル・データ・ツール）と責任者が分かる | GOVERN 1.6、MAP 4 |
| 判断 | AI案件がリスクに応じた水準で審査され、残留リスクを誰が受容したかが記録されている | GOVERN 1.3、GOVERN 2.3、MANAGE 1.4 |
| 実装 | 案件ごとに OWASP の対策が適用され、テストで確かめられている | MEASURE 2.7 |
| 監視・対応 | 稼働中のAIが監視され、異常時に停止でき、インシデントが通知される | MEASURE 2.4、MANAGE 2.4、MANAGE 4.3 |
| 説明 | 経営・監査に対し、NIST と OWASP の両方の言葉で準拠状況を説明できる | GOVERN 4.2 |

## 1.4 二層構造と目線合わせ

```
  経営・ガバナンス              「どのリスクを、どの水準で受容するか」
 ┌──────────────────────────────────────────────────────────┐
 │ ガバナンス層：NIST CSF 2.0（既存） ＋ NIST AI RMF 1.0 / AI 600-1（追加）│
 │   GOVERN ─ MAP ─ MEASURE ─ MANAGE                           │
 └──────────────────────────────┬───────────────────────────┘
               公式の対応表（OWASP Top 10 付録A／GenAI Security Crosswalk）
 ┌──────────────────────────────┴───────────────────────────┐
 │ 技術対策層：OWASP LLM Top 10 2026（モデル＝部品）                 │
 │             OWASP Agentic Top 10 2026（モデル＝行為者）          │
 └──────────────────────────────────────────────────────────┘
  現場・案件                    「何を防ぎ、どう確かめたか」
```

| 層 | 問い | 主な担い手 | 使う言葉 | 成果物 |
|---|---|---|---|---|
| ガバナンス層 | どのAIを使ってよいか、誰が承認し、どう監督するか | 経営層、セキュリティガバナンス、法務 | NIST（GOVERN 2.3 の意思決定責任、MANAGE 1.4 の残留リスク など） | 方針、AI資産台帳、審査プロセス、報告 |
| 技術対策層 | このシステムで何が起きうるか、何で防ぐか、どう検証したか | 案件担当、アーキテクト、開発・運用 | OWASP（LLM01〜10、ASI01〜10） | チェックシート、テスト結果、ガードレール設定 |

**目線合わせの仕組み**：現場は案件ごとに OWASP の ID でリスクと対策を記録し、それを対応表で NIST の機能・カテゴリに集約して経営に報告する。経営は NIST の言葉でリスク許容度と審査水準を決め、それが OWASP のチェック項目の必須・任意として現場に降りる。どちらの方向でも、同じリスクが同じ ID で追跡できる（第6章・第8章）。

## 1.5 扱う範囲・扱わない範囲

| 扱う | 扱わない |
|---|---|
| 社内で利用・開発する生成AIアプリケーション（チャット、RAG、エージェント、ファインチューニング） | 基盤モデルそのものの開発（事前学習） |
| AIに起因する情報セキュリティリスク（機密性・完全性・可用性）と、業務判断を誤らせる誤情報リスク | AI倫理全般（公平性・環境影響など）の詳細。AI RMF／AI 600-1 上の位置づけのみ示す |
| ガバナンス（方針・審査・監督）と技術対策（設計・実装・検証）の接続 | 個別製品・ベンダーの選定 |
| | AIを使ったサイバー防御（SOCでのAI活用）。Cyber AI Profile の "Defend" 領域にあたるため別テーマとする |

## この章の結論

- 目的は、NIST 前提のセキュリティガバナンスに AI セキュリティのケイパビリティを導入し、ガバナンスを安定させることである。
- 生成AIのリスクは「モデルは騙される」前提でシステム側を管理する。
- NIST（経営の言葉）と OWASP（現場の言葉）を公式の対応表でつなぎ、経営と現場が同じリスクを同じ物差しで扱えるようにする。
