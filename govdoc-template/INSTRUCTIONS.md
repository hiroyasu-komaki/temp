# 初期セットの作成指示書

このテンプレートから、あるテーマ（導入する機能）の**初期セット**を作るときの作業指示。作る人（担当者、または作成を任されたAI）は、この指示書に従う。

README が「何を作るか（文書の定義・区分・決まり）」を、[記述仕様書](./SPEC.md) が「各文書をどう書くか（構成・文体・表記・図表の記法）」を、この指示書が「初期セットをどこまで、どの順で作るか」を定める。食い違ったら README ＞ 記述仕様書 ＞ この指示書 の順で正とする。

---

## 1. 「初期セットを作る」の範囲

「初期セットを作る」と依頼されたら、README §4 の**手順1〜6まで**を行う。ファイルをコピーして変数を置き換えただけの状態は、初期セットではない。

| README §4 の手順 | この指示書での扱い |
|---|---|
| 1 コピー | 行う（§3-1） |
| 2 機能の型を決める | 行う。作る人の判断は「案」として扱う（§3-2） |
| 3 初期セットを決める | 行う（§3-2） |
| 4 作らない文書のファイルを削除する | 行う（§3-2） |
| 5 変数を置き換える | 行う。不明な値は推測せず、依頼者に聞く（§3-3） |
| 6 本文を書く | **行う。全文書の本文を、テーマの資料から書く**（§3-4、§4） |
| 7 承認 | 行わない（承認者が行う） |
| 8 運用開始の判定 | 行わない。判定に必要な状態（README §4-1 の #1〜#6）まで整える |

**完成の状態**: 初期セットの各文書が、承認者がそのまま読んで承認を判断できる文章になっている。残っているのは、資料から決められない事項の `（TBD: 〜）` だけで、そのすべてが決定記録に登録されている。

---

## 2. 入力

作り始める前に、次の4つをそろえる。そろわないものは依頼者に聞く。

| 入力 | 内容 | 例 |
|---|---|---|
| 出力先 | 初期セットを置くフォルダ | `02_concepts/governance/<テーマ>/docs` |
| テーマの資料 | 機能の定義・導入方針・実務をまとめた既存の資料。本文の材料になる | 本編（定義・導入・実務の章）、付録、提案資料 |
| 変数の値 | README §5 の15個 | 組織名、所管部署、承認者 |
| 機能の責任者 | 型・初期セット・作る人の判断を確認する人 | 運営主体の責任者 |

- **テーマの資料は全部読んでから書き始める。** 文書ごとに必要な箇所だけを拾い読みすると、文書の間で定義や役割がずれる。
- 資料に載っていない事項は、本文に推測で書かない（§5）。

---

## 3. 手順

### 3-1. コピー

1. テンプレートの `rules/` `process/` `reference/` と `README.md` を出力先にコピーする。この指示書もコピーしてよい。
2. 出力先の `README.md` の冒頭に、このフォルダが何のテーマの文書一式かを1〜2行で書く（型と初期セットの要約、決定記録の該当行）。

### 3-2. 型と初期セット

1. テーマの資料から「誰が決めるか」「何がきっかけで動くか」を読み取り、README §2-2 の型を当てはめる。根拠になった資料の箇所を控えておく。
2. **当てはまらない型も、理由とともに残す。** 特に README §2-2 の例に挙がっている機能（例: 委託先の評価・監督＝D）を採らない場合は、なぜ採らないかを書く。
3. README §2-3 の区分から初期セットを決め、作らない文書のファイルを削除する。推奨の文書を作らない場合は理由を書く。
4. 1〜3の結果を、決定記録「決定事項」に登録する（案件ID は「—」）。**作る人が判断した事項は、機能の責任者の確認が済むまで決定ではない。** 決定者の欄には機能の責任者を書き、あわせて「確認依頼」シートに確認を依頼する行を登録する。

### 3-3. 変数

1. README §5 の「本テーマの値」を埋め、全文書を一括置換する。Office ファイルは、置換のあとで `{{` が書式の区切りで分かれて残っていないかも確認する（README §5）。
2. **資料から確定できない値（組織名、承認者、施行日など）は、推測で埋めずに依頼者に聞く。** 聞けない場合は置換せずに残し、完了報告で一覧にする。
3. 変数を置き換えた結果、不自然な文になった箇所（例: 会議体＝なし のときの「次の会議体を置く。なし」）は、§3-4 の本文の記入で書き直す。

### 3-4. 本文の記入

README §2-4 の依存関係の上流から書く。上流で決めた条番号・用語・役割名を、下流の文書が参照するためである。

| 順 | 文書 | 先に書く理由 |
|---|---|---|
| 1 | 用語集 | 役割名・相談の区分などの呼び方を先に固定する |
| 2 | 憲章 | 目的・範囲・役割・決める者の条番号を、他の全文書が参照する |
| 3 | （運用基準・決裁権限表） | 作る場合。判定基準の条番号を下流が参照する |
| 4 | 業務フロー定義 | プロセスの番号を、Runbook の節と1対1で対応させる |
| 5 | Runbook | 業務フロー定義の箱ごとに手順を書く |
| 6 | その他の process/ | チェックリスト、SOP、Playbook など |
| 7 | reference/ の残り | 利用者ガイド、年間カレンダー、FAQ など |
| 8 | 決定記録 | 書く途中で出た決定・TBD・確認依頼を、最後にまとめて照合する |

文書ごとに資料から拾うものは §4 に、記入のルールは §5 に従う。**構成・文体・表記・図表の記法は [記述仕様書](./SPEC.md) に従う。**

### 3-5. 仕上げ

1. **自由記述（`{{日本語の説明}}`。Excel の「使い方」の `{{この表の使い方}}` を含む）をすべて書き換える。** Excel の「使い方」は、記述仕様書の文書別の「使い方シートの標準の文」をもとに書く。
2. **記入例を残さない。** `{{例: …}}`、`{{ }}`、Excel の灰色斜体の記入例の行は、テーマの内容に書き換えるか削除する。表の空行は削除する。
3. 型により書かない章・条は、削除せずに `⛔` で理由と見直す条件を書く（例: 会議体を置かない場合の憲章 第4章）。
4. 作らない文書を参照している記述（例: 「詳しくはガイドライン（…-R-05）」「運用基準 第○条」）を、作った文書の参照に直すか削除する。
5. §6 の完了の条件をすべて確認する。
6. 完了を報告する（§7）。

## 4. 文書ごとに資料から拾うもの

「拾うもの」は、テーマの資料から本文に持ってくる情報。資料にない場合は `（TBD: 〜）` にする（§5）。書き方（構成・文体・図表の記法）は [記述仕様書](./SPEC.md) の該当する文書の節に従う。

### rules/（規範）

| # | 文書 | 拾うもの |
|---|---|---|
| 01 | 方針 | 経営層が決めた目的・原則 |
| 02 | 憲章 | 機能の定義、担う仕事・担わない仕事、役割（内部の役割を含む）、意思決定の所在（RACIのA）、利害関係の扱い、報告の仕組み |
| 03 | 運用基準 | 判定基準、閾値、判断区分、提出要件、過去の判断事例 |
| 04 | 決裁権限表 | 判定軸、金額の閾値、決裁者、委任の条件 |
| 05 | ガイドライン | よく指摘される点、良い例・悪い例 |

### process/（プロセス）

| # | 文書 | 拾うもの |
|---|---|---|
| 06 | 業務フロー定義 | 開始点と終了点、関係者、処理の段階、受け渡すもの、RACI、他部門との接点 |
| 07 | SOP | 規制・監査上の要求、証跡、保管期間 |
| 08 | Runbook | 業務フロー定義の箱ごとの作業、担当、期限、使う様式・台帳、定期作業の周期、例外の事例 |
| 09 | Playbook | 手順どおりに進まなかった状況、判断者、判断の観点 |
| 10 | 作業指示書 | システムの画面と操作 |
| 11 | チェックリスト | 確認項目と根拠、確認の周期、過去の漏れ |

### reference/（参照）

| # | 文書 | 拾うもの |
|---|---|---|
| 12 | 利用者ガイド | 利用者から見た入口、流れ、締切、依頼の書き方、返ってくるもの、問い合わせ先 |
| 13 | FAQ | 実際の問い合わせと回答 |
| 14 | 用語集 | 資料で定義されている用語、役割名、略語、混同しやすい語 |
| 15 | 決定記録 | 型・初期セットの決定、書く途中で出た決定・TBD・確認依頼 |
| 16 | 様式のひな型 | 依頼票・記録の項目 |
| 17 | 年間カレンダー | 基準日、周期的な作業、外部の締切 |

## 5. 記入のルール

### 5-1. 資料にあることだけを書く

- 本文は、テーマの資料・依頼者の回答・依頼者が決めたことから書く。**作る人が思いついた数値・期限・連絡先・役職を書かない。**
- 資料にない事項は `（TBD: 〜）` とし、決定記録「保留課題」に登録する（担当と確定期限を付ける。決まっていなければ、担当は機能の責任者、確定期限は運用開始の判定日またはその直前の日付を案として置き、確認依頼にも登録する）。
- 資料から読み取れるが資料に明記されていない事項（作る人の解釈）は、本文に書いてよいが、決定記録「確認依頼」に登録して機能の責任者に確認する。

### 5-2. 書き写さず、参照する

- 基準・定義は1か所にだけ書き、他の文書は条文・節を参照する（README §2-1）。
- テーマの資料（本編など）は、正式な文書体系の外にある説明資料である。**本文に資料の章番号を書かない。** 資料の内容は、文書の役割に合わせて書き直して取り込む。

### 5-3. 書き方は記述仕様書に従う

- 文体・表記・番号・参照の書き方は [記述仕様書](./SPEC.md) §1 に、文書ごとの構成と記法は同 §2〜§4 に従う。
- テンプレートの書式（スタイル、表、図形、Excel の数式・入力規則）を壊さない。表の行は既存の行を複製して増やす。
- 書き終えたら、各ファイルをアプリで開ける状態か確認し、可能なら画像に書き出して目で確認する。

## 6. 完了の条件

| # | 確認項目 | 確認方法 |
|---|---|---|
| 1 | 初期セットのファイルだけがあり、作らない文書のファイルが残っていない | フォルダの中身と決定記録の突き合わせ |
| 2 | 英大文字の変数が残っていない（依頼者が値を示していないものを除く。その場合は完了報告に一覧を書く） | README §5 の確認コマンド |
| 3 | 自由記述（`{{日本語の説明}}`）が残っていない | README §5 の確認コマンド |
| 4 | `{{例: …}}`、`{{ }}`、記入例の行、表の空行が残っていない | `{{` で検索し、残りが自由記述でないことを確認する |
| 5 | 作らない文書への参照が残っていない | 作らない文書の文書番号（例: `-R-03`）で検索する |
| 6 | 本文中の `（TBD: 〜）` が、すべて決定記録「保留課題」に登録されている | 件数を突き合わせる |
| 7 | 作る人が判断した事項（型、初期セット、資料からの解釈）が、決定記録「確認依頼」に登録されている | 決定記録 |
| 8 | 業務フロー定義のプロセス一覧と Runbook の節が1対1で対応している | 両方の番号の突き合わせ |
| 9 | 役割名・用語の表記が全文書でそろっている | 用語集の語で検索する |
| 10 | 全ファイルがアプリで開ける | 開く、または画像に書き出す |
| 11 | 記述仕様書の文書別の仕様（構成、必須の列・行、図の記法）を満たしている | 記述仕様書の該当する節と突き合わせる |

---

## 7. 完了の報告

依頼者には次を短く報告する。

- 作った文書の一覧（初期セット）と、採った型
- 残っている `（TBD: 〜）` の件数と、主なもの
- 機能の責任者に確認してほしい事項（確認依頼の件数と、主なもの）
- 依頼者が値を示していない変数（あれば）
