# 文書記述仕様書

このテンプレートの17文書を**どう書くか**を定める仕様。文書の構成、文体と表記、図表の記法を、文書ごとに1か所で決める。作る人が変わっても、同じ書き方の文書ができるようにするためにある。

| ファイル | 定めること |
|---|---|
| [README](./README.md) | 何を作るか（文書の定義・区分・依存関係・変数・記法・文書管理） |
| **この仕様書** | **各文書をどう書くか（構成・文体・表記・図表の記法）** |
| [作成指示書](./INSTRUCTIONS.md) | 初期セットをどう作るか（作業の範囲・手順・完了の条件） |

- **テンプレートは文書の雛形（構成・表・変数・記入例）だけを持つ。何をどう書くかの指示は、テンプレートに置かずにこの仕様書にだけ書く。**
- テンプレートの各ファイルは、この仕様書に従って作る。テンプレートと仕様書が食い違ったら、仕様書を正としてテンプレートを直す。
- 文書の定義・区分（何を書く文書か、必須か）は README を正とする。
- この仕様書にない書き方が必要になったら、先にこの仕様書を改訂してから文書を書く。
- 文書別の仕様（§2〜§4）は、**規則**（守ったかどうかを確かめられること）と**補足（理由・例）**に分ける。補足は規則を言い直さない。
- 機能の型（README §2-2）による書き分けは §5 の表にだけ書き、§2〜§4 には型ごとの例を書かない。

**目次**

1. 共通仕様（全文書に適用）
2. rules/（01〜05）
3. process/（06〜11）。06 では業務フロー図の記法（BPMN 2.0 のサブセット）を定める
4. reference/（12〜17）
5. 型別の書き分け表

## 1. 共通仕様

### 1-1. 文体

| 層 | 文体 | 書き方 | 例 |
|---|---|---|---|
| rules/ | 条文体（である調） | 「〜とする」「〜しない」「〜できる」で言い切る。義務は「〜する」、禁止は「〜しない」、権限は「〜できる」 | 「運営主体は、案件の可否を決めない。」 |
| process/ | 手順文（である調） | 1文1動作。主語（担当）を書く。動詞で終える | 「受付担当は、依頼を案件台帳に登録する。」 |
| reference/ | 読み手に向けた文 | 利用者ガイドとFAQは「です・ます」調でよい。用語集・決定記録・年間カレンダーは体言止め・である調 | 「伝える前に相談してください。」 |

- ガイドライン（05）だけは推奨であることが分かるように「〜するとよい」「〜を推奨する」で書く。「〜しなければならない」は使わない。
- **あいまいな語を使わない。** 「適切に」「速やかに」「必要に応じて」「十分に」「等」は、条件・期限・列挙に置き換える（例: 「速やかに」→「2営業日以内に」、期限が決まらなければ `（TBD: 期限）`）。
- 1文は60字程度までを目安にする。超える場合は文を分けるか、号・箇条書きにする。

### 1-2. 表記

| 対象 | 決まり | 例 |
|---|---|---|
| 日付 | `YYYY-MM-DD` | 2026-10-01 |
| 数字・英字 | 半角 | 12か月、SLA |
| 括弧 | 全角（ ）。ただし Markdown のリンクと変数 `{{ }}` は半角 | 憲章（ITG-R-02） |
| 期間 | 「〜か月」「〜営業日」「〜日（暦日）」。営業日と暦日を区別する | 受付から2営業日以内 |
| 用語 | 用語集（14）の見出し語と同じ表記にする。同じものを別の語で書かない | 「相談者」と書いたら「依頼者」と混ぜない |
| 人 | 役職名か役割名で書く。個人名・個人のメールアドレスは書かない | IT企画グループ長 |
| 連絡先 | 組織の窓口（窓口名、共有のメールアドレス、問い合わせフォーム、チャネル名）だけを書く。書く場所は利用者ガイドの問い合わせ先と Runbook の関係者表（§1.3）に限る | IT投資事務局（共有アドレス） |
| 文書の呼び方 | 初出は「文書名（文書番号）」、以降は文書名だけでよい | Runbook（ITG-P-08） |

### 1-3. 番号と見出し

| 形式 | 番号の体系 |
|---|---|
| Word の rules/ | 章「第1章　総則」→ 条「第1条（目的）」→ 項「1　」（全角スペース）→ 号「(1)　」。条番号は文書全体の通し番号 |
| Word の SOP（07）・様式（16） | 「1.」「5.1」の数字見出し |
| Markdown | H1 は文書名だけ。章は H2「## 1. 概要」、節は H3「### 1.1 目的」。§番号で参照される節は番号を変えない |
| PowerPoint | スライドのタイトルが見出し。番号は付けない（ページ番号で参照する） |
| Excel | シート名が見出し。1シート1表 |

### 1-4. 参照

- **下位の層から上位の層を参照する。上位の層の文書が下位の層の文書の内容に依存してはならない**（README §2-1）。同じ層の中の参照はよい。
- 参照の書き方を統一する。

| 参照先 | 書き方 | 例 |
|---|---|---|
| rules/ の条 | 文書名 第○条（第○項） | 憲章 第8条第2項 |
| rules/ の別表 | 文書名 別表○ | 憲章 別表1 |
| Markdown の節 | 文書名 §番号 | Runbook §3.1 |
| PowerPoint のスライド | 文書名 p.番号 | 相談者ガイド p.6 |
| Excel のシート | 文書名「シート名」 | 年間カレンダー「定期作業」 |

- Markdown では文書名を相対リンクにする（例: `[憲章](../rules/02-charter.docx) 第8条`）。
- **基準・定義・日付を書き写さない。** 参照先に書いてあることは、参照で済ませる。
- **例外は利用者ガイド（12）のスケジュールだけ。** 申請者・依頼者は年間カレンダーを見ないため、日付を転記してよい。転記元（年間カレンダーの行）をスライドに書き、年間カレンダーを改訂したら利用者ガイドも同時に改訂する。
- 作っていない文書は参照しない。作っていない文書の内容が必要な場合は、作った文書（多くは憲章）の条を参照する。

### 1-5. 記法

README §6 の記法を使う。加えて次を守る。書き終えたかどうかは、英大文字の変数・`{{日本語の説明}}`・`{{例: …}}`・記入例の行が残っていないことで判定する。

| 記法 | 書き方 |
|---|---|
| `⛔` | 「⛔ 本テーマでは〜しない。理由: 〜。見直す条件: 〜。条番号をそろえるため、この章（条）は意図的に残している。」と書く。使わない章・条は削除せず、**番号も詰めない**（後から使うことになっても、他の文書の参照が変わらないようにするため） |
| `（TBD: 〜）` | 「（TBD: 決まっていない内容）」。決定記録「保留課題」の「課題」と同じ言葉にする。1つのTBDに1つの保留課題 |

### 1-6. 文書管理情報と改訂履歴

| 形式 | 文書管理情報の置き場所 | 項目 | 改訂履歴 |
|---|---|---|---|
| Word | 文書名の直下の2列の表 | 文書番号、版、所管、承認者、制定日、最終改訂日、施行日（rules/ のみ）、上位文書、見直し周期（rules/ のみ） | 末尾の章「改訂履歴」の表 |
| PowerPoint | 表紙の下部の1行（文書番号・版・最終改訂日）と、2枚目の表。2枚目は、06 は「文書管理情報」のスライド、10 は「概要」、12 は「このガイドについて」とする。10・12 は表の末尾に「文書番号・版」（最終改訂日を括弧書き）「所管・承認者」「上位文書」「見直し周期」の行を置く（12 は「正式なルール（上位文書）」の行で上位文書を兼ねる） | 文書番号、版、所管、承認者、最終改訂日、上位文書、見直し周期 | 最後のスライド |
| Excel | 「使い方」シートの上部 | 文書番号、版、所管、承認者、最終改訂日、上位文書 | 最後のシート「改訂履歴」 |
| Markdown | H1 の直下の2列の表 | 文書番号、版、所管、承認者、最終改訂日、上位文書 | 末尾の章「改訂履歴」（番号を付けない） |

- 改訂履歴の列は「版・日付・改訂内容・改訂者・承認者」で固定する。未記入の空行は置かない。
- 随時更新する文書（FAQ・用語集）は、改訂履歴の前に「追加・更新の記録」を置き、承認前の追加・更新を1件1行で記録する。定期見直しで承認したら版を上げ、改訂履歴に「追加・更新の記録の○件を承認」のように1行で記録する。
- 様式（16から作るもの）は例外とし、冒頭には様式の文書番号と版だけを置く。所管・承認者・最終改訂日・上位文書と改訂履歴は、末尾の章「様式の管理（記入不要）」に置く（16 の節）。
- 所管と承認者は README §7-2 に従う。

### 1-7. ファイル形式ごとの体裁

全形式で、書体は Yu Gothic、色は次のパレットだけを使う。

| 用途 | 色 |
|---|---|
| 濃紺（表の見出し行、表紙の背景、強調の文字） | `1C2B45` |
| 見出しの塗り（Word の表の見出し行、PowerPoint のレーンのラベル） | `DCE3EC` |
| ラベル列・箱の塗り | `F4F6F9`、`F7F8FA` |
| 線・補助の文字 | `5E7391`、`3F4F6A`、`9AA5B5`、`CFCABE` |
| Excel の入力セル | `FFF9DB`（黄） |
| Excel の「使い方」シートの説明欄 | `EAF1F8` |

**Word**: A4縦、余白 20mm。本文 10.5pt、表 9.5pt。条見出しは太字、項・号は左に1字下げる。表は全幅（17cm）で罫線あり。図は原則として置かない（図が必要なら 06 業務フロー定義に置いて参照する）。

**PowerPoint**: 16:9。タイトルは左上、フッター（文書番号と文書名）は左下、ページ番号は右下。本文の文字は10pt以上。**文字や表がスライドからはみ出さない**。入りきらないときはスライドを分ける。表は1枚14行まで。1枚に1つのことだけを示す。

**Excel**: 先頭のシートは「使い方」、最後は「改訂履歴」。「使い方」シートは、文書管理情報 → 使い方（この表を使う人向けの説明。3〜5行）→ 凡例 の順に置く。使い方の標準の文は、文書別の仕様に示す。表の見出し行は濃紺の塗りに白字。人が入力するセルは黄、数式のセルは塗らない。選択肢のある列は入力規則（リスト）にする。日付は日付型（表示形式 `yyyy-mm-dd`）で入れる。

- **列の定義**: Excel の文書のシート・列の順番・列名・入力の種類・行の範囲は、文書別の仕様の「シートと列」で定める。テンプレートはこれに合わせて作り、食い違ったら「シートと列」を正とする。ここにない列を足すときは、先にこの仕様書を改訂する。
- **表の位置**: 1行目にシートの表題、2行目は空ける、3行目に見出し、4行目からデータ（例外はチェックリストの「記録」シート）。
- **入力の種類**: 「シートと列」の「入力」の欄は次のどれかで書く。

| 入力 | 意味 | セルの体裁 |
|---|---|---|
| 番号 | 1からの連番 | 黄 |
| 文章 | 自由記述 | 黄 |
| 選択 | 入力規則（リスト）。選択肢を「／」で区切って書く | 黄 |
| 日付 | 日付型（`yyyy-mm-dd`） | 黄 |
| 数値 | 数値型 | 黄 |
| 数式 | 人が入力しない。式の意味を「書き方」の欄に書く | 塗らない |

- **行の範囲**: 入力規則と数式は、「シートと列」に書いた行の範囲の全体に設定する（記入例の行を含む）。行数が決まっていない台帳は4〜300行目とする。
- **記入例の行**: 灰色の斜体にし、No. の列に「記入例」と書く（集計の数式は「記入例」の行を数えない）。書き換えるか削除する。
- **共通のシート**: 全ての Excel の文書に、次の2つのシートを置く。

| シート | 列と行 |
|---|---|
| 使い方 | A・B の2列。1行目に文書の表題、3〜8行目に文書管理情報（A列のラベル: 文書番号・版・所管・承認者・最終改訂日・上位文書。ラベルの塗り `F4F6F9`）、10行目に「使い方」、11行目から説明（3〜5行。塗り `EAF1F8`）、その下に「凡例」（黄色のセル、（TBD: 〜）、その文書だけの記号） |
| 改訂履歴 | 版（文章）・日付（日付）・改訂内容（文章）・改訂者（文章）・承認者（文章）の5列（§1-6）。4行目が制定の行 |

**Markdown**: 表は GitHub 形式。図（Mermaid など）は置かない。強調（`**`）は1節に1〜2か所までにする。

## 2. rules/（規範）

rules/ の文書は条文で書く。全条に見出し（括弧書き）を付ける。1条に定める事項は1つにする。

### 01 方針（Policy）

| 項目 | 仕様 |
|---|---|
| 読み手 | 全社の関係者、経営層 |
| 構成 | 第1章 総則（目的・適用範囲・定義）／第2章 基本原則（基本原則の条1つ）／第3章 体制と役割／第4章 遵守と例外／第5章 見直し／附則／改訂履歴 |
| 分量 | A4で2ページ以内 |

**規則**

- 目的の条は1〜2文。「〜を実現するため、〜する」の形で、機能を置く理由を書く。
- 基本原則は「基本原則」の条1つに、号で3〜7個並べる。号は「(n)　原則の名前　行動の文」の形にし、行動の文は判断に迷ったときに引ける文（「〜する」）で書く。理念・スローガンは書かない（原則の数で条番号が動かないように、1原則1条にしない）。
- 会議体・基準・手順・金額は書かない。体制の条の表は役割の大枠（最終責任者・会議体・運営主体）だけにし、詳細は憲章（02）を参照する。
- 例外を承認する者と、例外の記録先（決定記録）を書く。
- 旧制度から切り替える場合は、附則に経過措置（施行日時点で審議中の案件の扱いなど）を書く。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| 基準・会議体を書かない | 方針に基準額などを書くと、改訂のたびに経営層の承認が要る |
| 原則を3〜7個に絞る | 多すぎる原則は判断の拠り所にならない |
| 目的の条の例 | 全社のIT投資を経営戦略と整合させ、限られた資源を優先度の高い案件に配分するため、〜する |

### 02 憲章（Charter）

| 項目 | 仕様 |
|---|---|
| 読み手 | 機能の責任者、運営主体、関係部署、承認者 |
| 構成 | 第1章 総則（目的・定義）／第2章 機能の目的と範囲／第3章 役割と責任／第4章 会議体 [任意]（会議体の構成・各会議体の定めの2条）／第5章 利害関係の回避／第6章 報告と改廃／附則／別表（会議体ごと）[任意]／改訂履歴 |
| 分量 | A4で4〜6ページ |

**規則**

- **第2章「目的」**は、機能を受け取る側（申請者・依頼者・利用者）を主語にして「〜が〜できるようにする」で書く。号で3つまで。「〜を管理する」とは書かない。
- **第2章「範囲」**は、機能の型・提供するもの・利用者・対象・対象外・前後の機能の6行の表で書く。対象外には、誰が担うかを添える。
- 提供の方法に原則がある場合は、第2章に条を立てて書く（§5）。
- **第3章「役割」**は5列の表（役割・担う者・責任・持つ権限・持たない権限）。行は、機能の責任者 → 運営主体の内部の役割 → 申請者・依頼者 → 関係部署の順。**全ての行に「持たない権限」を書く**（ない場合は「—」）。活動ごとの RACI は書かない（業務フロー定義に書く）。
- **第3章「決める事項と決める者」**は3列の表（事項・決める者・この機能の関わり）。この機能が決める事項と、他者が決めこの機能は支援する事項の両方を並べ、決めない事項は関わりの欄に「（決めない）」と書く。表の後に、この機能が最終責任を負う範囲を1項で書く。
- 判定の基準・閾値は運用基準（03）に書き、憲章からは「運用基準 第○条に定める」と参照する。運用基準を作らない場合は、第3章に条を立てて書く。
- **第4章**は、会議体を置く場合だけ書く。置かない場合は章と2つの条を残して ⛔ を書き、条番号は詰めない（§1-5）。「別表」の見出しも残して ⛔ を書く。
- 会議体ごとの定めは、附則の後の別表（別表1、別表2…）に、同じ9行の表（目的・議長・構成員・付議事項・決定事項・開催頻度・定足数と決議方法・上申と差し戻し・記録）で書く。本文は「各会議体の定め」の条から別表を参照する（会議体の数で条番号が動かないようにするため）。別表の数は会議体の数に合わせ、余った別表は削除する。付議基準の閾値は運用基準の条を参照する。固定メンバーを置かない会議体（案件ごとに編成するもの）は、「構成員」に任命の方法と任命者を書く。
- 報告の条には、報告者・報告先・周期・報告事項（号で列挙）を書く。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| 「〜を管理する」と書かない | 範囲の判断に使えない |
| 持たない権限を書く | この機能が他部門の決定を取り上げると受け取られるのを防ぐ（例: ベンダーの選定は支援するが、選定は依頼部門が決める） |
| 会議体ごとに同じ項目の表 | 項目をそろえると、会議体の間の権限の重なりや抜けが見える |

### 03 運用基準（Standard）

| 項目 | 仕様 |
|---|---|
| 読み手 | 運営主体、審議・決裁する者、申請者・依頼者（利用者ガイドを通じて） |
| 構成 | 第1章 総則／第2章 対象と分類／第3章 扱いの判定／第4章 依頼・提出の要件／第5章 判断・対応の区分／第6章 決裁権 [任意]／第7章 サービスレベルとモニタリング／附則／改訂履歴 |

**規則**

- **1条1基準。** 1つの条に基準を2つ以上書かない。
- 分類・判定・区分は表で書く。判定の表は「条件 → 扱い」の形にし、**全ての案件がどれか1行だけに当てはまる**ようにする（抜けと重なりを作らない）。
- 閾値（金額・件数・期間）には、根拠（なぜその値か）を同じ条の次の項に書く。
- 未確定の閾値は `（TBD: 〜）` とし、決定記録の保留課題に登録する。空欄のまま運用を始めない。
- 判断・対応の区分は3列（区分・意味・後続の扱い）。区分は §5 の本テーマの型のものを使う。複数の型を持つ機能は、型ごとに表を分ける。
- 章・条は型に合わせて取捨する（§5）。使わない条は削除せず、条番号も詰めずに ⛔ を書く（§1-5）。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| 判定を表で書く | 文章で書くと、条件の組み合わせで解釈が分かれる |
| 条番号を動かさない | Runbook・FAQ・利用者ガイド・チェックリストが、ここの条番号を参照する |

### 04 決裁権限表（DoA）

| 項目 | 仕様 |
|---|---|
| 読み手 | 決裁者、運営主体、財務部門 |
| シート | 使い方／判定軸／決裁権限表／委任記録 [任意]／改訂履歴 |

**規則**

- **1行1ルール。** 判定軸は左の列から順に評価する。判定軸の定義（区分・判定の基準・根拠条文）は「判定軸」シートに置き、「決裁権限表」シートは区分の値だけを書く。
- 決裁者の列には1者だけを書く。合議・同意・報告を受ける者は「関与」の列に書く。
- 全ての組み合わせがどれか1行に当てはまるようにする。当てはまらない組み合わせは「対象外」の行を作る。
- 金額は税抜・年額か総額かを列の見出しに明記する。
- 委任を認める場合は、案件ごとに「委任記録」シートに記録する。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| 抜けと重なりの見つけ方 | 1つの案件が2行以上に当てはまる、またはどの行にも当てはまらない組み合わせがあれば、表に抜けか重なりがある |

**シートと列**

「判定軸」（4〜7行目。4行目が判定軸1、7行目が判定軸4）

| 列 | 入力 | 書き方 |
|---|---|---|
| 順番 | 番号 | 1〜4をあらかじめ入れておく。「決裁権限表」の「判定軸n」の n と同じ |
| 判定軸 | 文章 | 軸の名前（例: 予算区分） |
| 区分1〜区分6 | 文章 | 軸がとる値を1セルに1つずつ、左から書く。抜けと重なりを作らない。ここに書いた値が「決裁権限表」の選択肢になる |
| 判定の基準 | 文章 | どの区分に当たるかの見分け方。境目は運用基準の条を参照する |
| 根拠条文 | 文章 | 運用基準（作らない場合は憲章）の条 |

- 判定軸を4つ使わない場合、使わない行は空けておく（行の位置で「決裁権限表」の列と対応しているため、行を詰めない）。

「決裁権限表」（4〜300行目）

| 列 | 入力 | 書き方 |
|---|---|---|
| No. | 番号 | |
| 判定軸1〜判定軸4 | 選択（「判定軸」シートの n 行目の区分1〜区分6） | 見出しは「判定軸n」の下に軸の名前を書く。軸は4つまで。使わない軸の列は削除する |

| 報告義務 | 文章 | 決裁の後に、誰へ何を報告するか。ない場合は「なし」 |
| 根拠条文 | 文章 | 運用基準（作らない場合は憲章）の条 |
| 備考 | 文章 | |

「委任記録」[任意]（4〜300行目）

| 列 | 入力 | 書き方 |
|---|---|---|
| 案件ID | 文章 | 案件台帳の ID |
| 件名 | 文章 | |

| 決定した会議体 | 文章 | 委任を決めた会議体・決定者 |

**「使い方」シートの標準の文**

- 判定軸を左の列から順に当てはめ、当てはまる1行の「決裁者」が決裁する。
- 「関与」の列の者には、決裁の前に合議・同意を求めるか、決裁の後に報告する。

### 05 ガイドライン（Guideline）

| 項目 | 仕様 |
|---|---|
| 読み手 | 申請者・依頼者、運営主体 |
| 構成 | 1. 目的／2. 適用範囲／3. 推奨事項／4. 判断に迷ったとき／5. 関連文書／改訂履歴 |
| ファイル | 主題ごとに1ファイル（枝番。README §7-1） |

**規則**

- 「1. 目的」は1〜3行で、改善したい現状（例: 定量効果が作文的になっている）に触れて書く。
- 推奨事項は1つにつき「推奨 → 理由 → 良い例・悪い例の表」の順で書く。理由と例のない推奨は書かない。
- 推奨事項は1ファイル7つまで。超える場合は主題を分ける。
- 義務（守らないと違反になること）は書かない。義務は運用基準（作らない場合は憲章）に書く。
- 「4. 判断に迷ったとき」には、推奨どおりにできない場合の相談先と、Playbook の該当する状況へのリンクを書く。
- 主題は型に合わせて選ぶ（§5）。ファイル名に主題を英語で付ける（例: `05-guideline-01-benefit.md`）。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| 理由と例を必須にする | 理由のない推奨は守られない。抽象的な推奨だけでは行動が変わらない |
| 義務を書かない | 義務を書くと「推奨なのか義務なのか」で揉める |

## 3. process/（プロセス）

### 06 業務フロー定義（Process Definition）

| 項目 | 仕様 |
|---|---|
| 読み手 | 運営主体、関係部署、承認者 |
| 形式 | PowerPoint 16:9 |
| スライドの構成 | 表紙／文書管理情報／目的と適用範囲／全体フロー（1枚以上）／プロセス一覧／RACI（1枚以上）／他のプロセス・部署との受け渡し／改訂履歴 |

- 手順の細部は書かない（Runbook に書く）。この文書には「どの順で・誰から誰へ・何が渡るか」と、誰が何に責任を持つか（RACI）だけを書く。

#### 06-1. 目的と適用範囲

2列の表で、目的・開始・終了・対象・対象外・関係者の6行を書く。開始と終了は、全体フローの開始イベント・終了イベントと同じ言葉にする。複数のフローがある場合は、フローごとに改行して書く。

#### 06-2. 全体フローの記法（BPMN 2.0 のサブセット）

フロー図は BPMN 2.0 の要素の意味に従って描く。ただし、使う要素を次の表に限る。**表で「使わない」とした要素は描かない。**

| 区分 | BPMN の要素 | 使う | 描き方 | ルール |
|---|---|:---:|---|---|
| 枠 | プール | 使わない | — | 1枚のフロー図＝1つのプロセス。プールの枠は描かず、レーンの集まりをプロセス全体とみなす |
| 枠 | レーン | 使う | 横長の長方形（塗り `F7F8FA`、枠 `CFCABE` 0.75pt）。左端にラベルの箱（塗り `DCE3EC`、太字 11pt） | 1レーン＝1関係者（役割・部署・会議体）。システムはレーンにしない。1枚2〜5レーン。レーンの高さは3.3cmまで |
| イベント | 開始イベント（なし） | 使う | 円（白）、細線（`3F4F6A` 1.25pt）、直径 0.8cm。レーンの中央に置き、ラベル（9pt）は円の下 | 申請・依頼・相談など、人の行為で始まるとき |
| イベント | 開始イベント（タイマー） | 使う | 開始イベント（なし）と同じ円。ラベルの先頭に「⏱」を付け、周期を書く（例: ⏱ 毎月の抽出日） | 周期・期日で始まるとき（型との対応は §5） |
| イベント | 終了イベント | 使う | 円（白）、太線（`3F4F6A` 3pt）、直径 0.8cm。レーンの中央に置き、ラベル（9pt）は円の下 | 終わった状態を書く（例: 判断材料を引き渡した） |
| イベント | 中間イベント、境界イベント（タイマー・メッセージ・エラー・シグナル・補償など） | 使わない | — | 待ち時間や期限は、プロセス一覧の「期限」と Runbook に書く |
| アクティビティ | タスク | 使う | 角丸長方形（塗り `F7F8FA`、枠 `5E7391` 1.25pt）、幅 3.0cm × 高さ 1.6cm。文字 10pt、3行まで | 運営主体のタスク: 「丸数字＋名詞を動詞する」（2行まで）と、最後の行に Runbook の節（例: ① 相談を受け付けて登録する／§3.1）。運営主体以外のタスク: 番号と節を付けず、枠を `9AA5B5` にする |
| アクティビティ | サブプロセス（折りたたみ） | 使う | タスクと同じ図形。下辺の中央に「＋」の小さな四角 | 別のフロー図に描いたプロセスを呼ぶときだけ使う。ラベルは「フロー（2）へ」のように呼び先を書く |
| アクティビティ | サブプロセス（展開）、コールアクティビティ、ループ・多重インスタンスのマーカー | 使わない | — | 繰り返しは、排他ゲートウェイの戻りで描く |
| ゲートウェイ | 排他ゲートウェイ | 使う | ひし形（白、枠 `3F4F6A` 1.25pt）、1.0cm 角。中は空白 | 直前に判断があるとき。ひし形の上か下（矢印と重ならない側）に問いを書く（「〜か？」、9pt）。出る矢印には条件のラベル（「はい」「いいえ」や条件）を必ず付ける |
| ゲートウェイ | 並列ゲートウェイ | 使う | 排他ゲートウェイと同じひし形の中に「＋」 | 同時に進む作業があるとき。分岐と合流を必ず対で描く |
| ゲートウェイ | 包括・イベントベース・複合ゲートウェイ | 使わない | — | 排他または並列で描けるように、判断を分ける |
| 接続 | シーケンスフロー | 使う | 実線の矢印（`3F4F6A` 1.5pt、終端は三角）。水平・垂直の線分だけでつなぐカギ線にする（斜めの線は使わない） | **戻り（差し戻し・再確認）も実線で描き、必ず排他ゲートウェイから出す** |
| 接続 | メッセージフロー、アソシエーション | 使わない | — | **点線は使わない。** 関係者は全てレーンとして描くので、メッセージフローは要らない |
| データ | データオブジェクト、データストア | 使わない | — | 受け渡すもの（入力・出力）はプロセス一覧に書く |
| 成果物 | テキスト注釈、グループ | 使わない | — | 補足はスライド下部の注記欄（2行まで）に書く |

**描き方のルール**

1. **時間は左から右へ進む。** 戻りの矢印だけが右から左へ向かう。
2. **レーンの並び**は、上から「起点の関係者（申請者・依頼者）→ 運営主体の窓口 → 運営主体の担当 → 決定者・会議体 → 関係部署」とする。全てのフロー図とRACIで同じ並びにする。
3. **1枚のフロー図は、開始イベント1つから始まり、全ての経路が終了イベントに至る。** 起点が違うもの（依頼で始まるものと、周期で始まるもの）は別の図にする。
4. **1枚のタスクは7個まで**（ゲートウェイとイベントを含めて12個まで。横一列に並べて収まる上限）。超える場合は、型・フェーズごとに図を分け、サブプロセス（折りたたみ）でつなぐ。図のタイトルは「全体フロー（1）〜」「全体フロー（2）〜」とする。
5. **矢印を交差させない。** 交差が避けられない場合はレーンの並び以外の配置を見直し、それでも残る場合は1か所までとする。
6. 矢印はタスクの左右の辺から出入りさせる。レーンをまたぐ矢印だけ、上下の辺を使ってよい。
7. **番号の対応**: 運営主体のタスクの丸数字 ＝ プロセス一覧の No. ＝ Runbook の §3.No. とする。1つのタスクを複数の節に分けない。フロー図が複数あるときも、丸数字は全ての図を通して振る（図ごとに①から振り直さない）。
8. ラベルの文字数: タスクは14字まで（2行）、イベントは12字まで（周期の ⏱ を除く）、ゲートウェイの問いは16字まで。矢印の条件のラベル（9pt）は、矢印の出口の近くに置く。
9. 注記欄（フロー図の下、10pt、2行まで）の1行目には「丸数字はプロセス一覧の No.、§ は Runbook の節」を書く。
10. 複数のフロー図がある場合、「目的と適用範囲」の開始・終了には、図ごとの開始イベント・終了イベントのラベルを「（1）〜（2）〜」の形で並べる。

**型ごとの描き方**: 開始イベントの種類と、図に必ず描く要素は §5 に従う。

#### 06-3. プロセス一覧

- 7列の表（No.・プロセス・入力・出力・担当・期限・関連手順）。行は運営主体のタスクと1対1。
- 「プロセス」はフロー図のタスクと同じ言葉。「担当」はレーンの名前。「期限」は相対表記（例: 受付から2営業日以内、締結後30日以内）で書き、日付は書かない。「関連手順」は常に「Runbook §3.n」とする。手順を SOP に書くプロセスは「Runbook §3.n（SOP（文書番号）5.n〜）」と併記する。

#### 06-4. RACI

- 行: プロセス一覧の各プロセスと、憲章「決める事項と決める者」の主な事項。列: フロー図のレーンと同じ関係者を同じ並びで。
- 記号は R・A・C・I と「A/R」だけ。**1行に A は1つだけ。** A のない行を作らない。関与しない欄は空欄にする（「—」を書かない）。
- 関係部署を1列にまとめる場合は、記号の後に括弧で部署名を書く（例: R（購買））。
- 1枚14行まで。超える場合は「RACI（1）〜」「RACI（2）〜」に分ける（フロー図の分け方に合わせる）。
- 表の下の注記欄（2行まで）に凡例と、A の置き方の原則を書く。

#### 06-5. 他のプロセス・部署との受け渡し

5列の表（相手・渡すもの／受け取るもの・方向・タイミング・手段）。方向は「渡す」「受け取る」のどちらか。タイミングは相対表記か年間カレンダーの行名で書く。

#### 06-6. 補足（理由・例）

| 対象 | 理由・例 |
|---|---|
| この文書の目的 | 部署間の受け渡しで止まる箇所と、責任の重なり・抜けを見つける |
| 1行に A は1つ | A が2者以上ある活動、A が無い活動は、決定の責任が曖昧になっている箇所である |
| 他のプロセス・部署との受け渡し | 接点の定義がないと、決定の後に案件が止まる |

### 07 標準作業手順書（SOP）

| 項目 | 仕様 |
|---|---|
| 読み手 | 作業の担当者、品質保証、監査人 |
| 構成 | 1. 目的／2. 適用範囲／3. 責任／4. 定義／5. 手順／6. 記録の保管／7. 教育訓練／8. 逸脱時の対応／9. 参考文書／改訂履歴 |
| ファイル | 業務ごとに1ファイル（枝番） |

**規則**

- 品質・監査上の要求がある業務にだけ使う。それ以外の運営の業務は Runbook に書く。1つの SOP には1つの業務だけを書く。
- 冒頭に作成・確認・承認の署名欄を置く（署名と日付）。
- 手順は4列の表（No.・担当・作業・記録（証跡））。No. は「5.1」から振る。**全ての手順に証跡（監査で手順の実施を示すもの。何を、どこに残すか）を書く。** 証跡の残らない手順は SOP ではなく Runbook に書く。
- 1手順1動作。判断が入る手順は、判断の基準を運用基準の条で参照する。
- 記録の保管は4列（記録・保管場所・保管期間・保管責任者）。保管期間は規制・社内規程を根拠に書く。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| SOP の対象を絞る | SOP にすると改訂のたびに承認手続きが要り、運用の改善が遅くなる |
| 対象の例 | GxP対象システムに関わる審議、IT全般統制の評価 |

### 08 Runbook

| 項目 | 仕様 |
|---|---|
| 読み手 | 運営主体の担当者 |
| 構成 | 1. 概要（1.1 目的・1.2 対象範囲・1.3 関係者）／2. 年間の流れ／3. 手順／4. 例外対応／5. 記録とKPI／改訂履歴 |

**規則**

- **§3 の節は、業務フロー定義のプロセス一覧と1対1**（§3.n ＝ No.n）。節の見出しはプロセス名と同じにする。節は流れの順に並べる（型ごとの並びは §5）。複数の型を持つ機能は、型ごとに節のまとまりを分けてよい（例: §3.1〜§3.5 相談への対応、§3.6〜§3.8 台帳の維持）。
- 手順を SOP（07）に書くプロセスも、§3 に節を置いて番号を空けない。節には5行の表を書き、「作業」は「SOP（文書番号）5.n〜5.m に従う」の1行だけにする（手順は書き写さない）。
- 全ての節を同じ形式で書く: 5行の表（開始条件・入力・担当・期限・出力）→「作業」（番号付きの手順）→「例外」（1行。§4 への参照）。
- 作業の手順は1つ1動作で、主語（担当）を書く。担当が表の「担当」と同じなら省略してよい。1節10手順まで。超える場合は作業指示書（10）に分けるか、節を分ける（業務フロー定義も合わせて直す）。
- **判断が入る手順は書かない。** 判断が要る状況は「例外」として §4 に送る。
- **基準・閾値・日付は書かない。** 基準は憲章・運用基準の条を、日付は年間カレンダーの行を参照する。
- §1.3 関係者は3列（関係者・運営主体との関わり・連絡先）。運営主体から見た「誰に何を頼むか・誰から何を受け取るか」だけを書く（RACI は書かない）。連絡先は組織の窓口だけを書く（§1-2）。
- §2 は3列（時期（相対）・作業・参照する手順）。「何の何日前に何をするか」を相対で書く。周期的な作業や締切がない機能では、§2 を削除せずに ⛔ を書く（§番号を変えないため）。
- §4 例外対応は4列（状況・一次対応・エスカレーション先・詳細）。Playbook（09）を作る場合は、詳細の列に Playbook の節を書き、判断の観点はそちらに移す。
- §5 の KPI は4列（KPI・定義・目標・集計周期）。定義は、何を何で割るか・何を数えるかまで書く。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| 基準・日付を書き写さない | 書き写すと、基準の改訂のたびに Runbook がずれ、日付は毎年改訂が要る |
| 判断が入る手順を書かない | Runbook は手順どおりに実行すれば終わる作業だけを扱う。判断は Playbook（作らない場合は §4）で扱う |
| 5行の表を全節で書く | 入力・作業・出力・期限・担当のどれかが欠けた手順は、実行する人によって結果が変わる |

### 09 Playbook

| 項目 | 仕様 |
|---|---|
| 読み手 | 運営主体の担当者・責任者 |
| 構成 | 1. 状況の一覧／2. 状況ごとの対応／3. 事例／改訂履歴 |

**規則**

- 状況には `S-01` から番号を振る。状況の一覧は5列（#・状況・起きやすい時期・運営主体の権限・詳細）。本テーマの型に当てはまる状況だけを残す（例は §5）。テンプレートの「型」の列は書き終えたら削除する。
- 状況ごとの対応は、全て同じ9行の表（状況・見分け方・放置した場合のリスク・判断の観点・選択肢・決める人・運営主体がすること・運営主体がしてはいけないこと・記録）で書く。
- 「判断の観点」は判断の答えではなく、何を見て判断するかを書く。「決める人」は1者にする。
- 「3. 事例」には、実際に起きた状況と判断を書く。個人名は書かず、案件IDで参照する。
- 同じ判断が3回繰り返されたら、運用基準（作らない場合は憲章）への格上げを決定記録の保留課題に登録する。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| Runbook との違い | Runbook は手順を実行すれば終わる作業、Playbook は状況を見て判断が要る場面を扱う |
| してはいけないことを書く | 運営主体が権限外の判断を抱え込むと、決定の正当性が失われる |
| 事例を残す | 同じ状況の次の判断を速く、一貫させる |

### 10 作業指示書（Work Instruction）

| 項目 | 仕様 |
|---|---|
| 読み手 | 操作の担当者 |

**規則**

- 業務上の判断は書かない（Runbook・Playbook に書く）。
- 画面が変わったときは、この文書だけを改訂する（Runbook に画面の操作を書かない）。

### 12 利用者ガイド（Handbook）

| 項目 | 仕様 |
|---|---|
| 読み手 | 申請者・依頼者（`{{APPLICANT}}`） |
| 表題 | 「`{{APPLICANT}}`ガイド」（例: 起案者ガイド、相談者ガイド） |
| スライドの構成 | 表紙／このガイドについて／全体の流れ／申請・依頼の対象（できること・できないこと）／スケジュール／起案書・依頼の書き方／結果と次のステップ／よくある間違いと問い合わせ先／改訂履歴 |

**規則**

- 規程・基準の要点を平易に説明する。条文を言い換えすぎない。
- 読み手の言葉で書く。運営主体の内部の役割名（例: 基盤担当）や内部の手順番号は出さない。役割を出す場合は、読み手が接する役割（例: 受付担当）だけにする。
- 「全体の流れ」の直後に、対象 → スケジュール → 書き方の順で続ける。読み手が「出すべきか・いつまでか・何を書くか」を、この3枚で判断できるようにする。
- 各スライドの下に、根拠の条・節を1行で添える（「根拠: 憲章 第4条」）。
- 全体の流れは5段階以内の横並びの図（番号の丸＋段階名＋説明3行まで）。業務フロー定義のフロー図を簡略化したもので、段階の名前を合わせる。
- スケジュールは、年間カレンダーを作る場合は日付をそこから転記し、転記元の行を書く（§1-4 の例外）。作らない場合はこのスライドに直接書く。締切を過ぎた場合の扱いを1行添える。
- 書き方のスライドは4列の表（項目・書くこと・良い例・避けたい例）。例は架空の値であることが分かる書き方にする（「○○」や概数を使う）。様式（16）を作る場合は、表の下に様式の文書番号を書く。
- 作らない文書への案内は削除する（ガイドライン（05）を作らない場合は「詳しくはガイドライン」、FAQ（13）を作らない場合は「よくある質問は FAQ を参照」の文）。
- 申請・起案書・審議の結果などの語とスライドのタイトルは、型に合わせて置き換える（§5）。
- 広報資料（案内チラシ等）とは別の文書として作り、内容を流用しない。

### 14 用語集（Glossary）

| 項目 | 仕様 |
|---|---|
| 読み手 | 全ての読み手 |
| 構成 | 1. 業務用語／2. 会議体・組織・役割／3. 略語／4. 使い分け／5. 旧制度の用語との対応 [任意]／追加・更新の記録／改訂履歴 |

**規則**

- 規程・基準を書きながら、定義しないと読み違える語をその場で足していく。
- 業務用語の表は5列（用語・読み・定義・定義の出典・備考）。並びは五十音順か、業務の流れの順のどちらかに統一する。
- **定義は1〜2文で、体言止めで書く**（例: 「相談ごとに、運営主体が引き受けることを依頼者と合意すること」）。「〜をいう」は使わない。
- **定義の出典は作った文書の条・節**にする。テーマの説明資料（本編など）は出典にしない。出典の条に定義がある語は、条と同じ言葉で書く。
- 「4. 使い分け」には、混同しやすい2語を1行で対比する。少なくとも、申請者・依頼者と所属部門の区別、この機能が決めることと支援することの区別を書く（型ごとの例は §5）。
- 略語は正式名称（英語）と意味を書く。
- 「5. 旧制度の用語との対応」は、制度を切り替えた場合に書く。書かない場合は ⛔ を書く。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| 用語集を先に作る | 同じ言葉が関係者ごとに違う意味で使われることが、最大の混乱の元になる（例: 「承認」が予算の承認か実行の承認か） |
| 旧制度の用語との対応 | 移行期間中は旧名称で話す人が必ずいる |

### 16 様式のひな型（Template）

| 項目 | 仕様 |
|---|---|
| 読み手 | 申請者・依頼者（記入する人）、運営主体 |
| 構成 | 様式番号と版／様式名／1. 基本情報／2〜. 記入項目／添付資料／運営主体の記入欄／様式の管理（記入不要。所管・承認者・最終改訂日・上位文書の表と、改訂履歴） |
| ファイル | 様式ごとに1ファイル（枝番） |

**規則**

- テンプレートの 16 は、1つ目の様式（枝番01）の雛形である。「ひな型」だけの文書は作らず、コピーして様式ごとに1ファイルを作り、枝番（01、02…）を振る。版と改訂履歴は様式ごとに持つ。
- 冒頭には様式の文書番号と版だけを置く（文書管理情報の表は置かない）。所管・承認者・最終改訂日・上位文書と改訂履歴は、末尾の「様式の管理（記入不要）」に置き、記入する人に削除させない。
- 記入項目は2列の表（項目・記入欄）。**項目は運用基準（作らない場合は憲章）の提出要件と1対1**にし、要件の条を項目の見出しに添える。
- 選択式の項目は「□ 選択肢」で並べる。記入例は各記入欄の下に1行で添え、提出時に消してよいことを明記する。
- 運営主体の記入欄は、判断・対応の区分（運用基準の区分）をそのまま選択肢にする。
- 段階ごとに書き足す様式（例: 起案書）は、段階ごとに章を分け、前の段階の記載を後の段階で引き継ぐ。

**補足（理由・例）**

| 対象 | 理由・例 |
|---|---|
| 記入例を添える | 記入の質がそろう |
| 様式の例 | 起案書、依頼票、議事録、決定通知 |

**「使い方」シートの標準の文**

- 会議・締切・定期作業の日程を管理する表。外部の基準日から逆算するイベントは「カレンダー」シートに、自らの決まりで実施日が決まる作業は「定期作業」シートに書く。
